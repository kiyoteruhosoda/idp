# RP 統合ガイド —— assay につなぐアプリの作り方

assay に認証を任せるアプリ（**RP** = Relying Party。依拠当事者）を作るときの決まりごとを
まとめる。⚠ **これは「つながる方法」ではなく「正しくつなぐ方法」の文書である。**
OAuth2 / OIDC のライブラリを繋ぐだけなら大抵は動いてしまう。動いたうえで壊れている形が
いくつもあり、それが何かを書く。

判断の根拠は `docs/adr/0049-attribute-ownership-and-the-federation-key.md`
（何を IdP が持ち、何を RP が持つか）。本書はその適用手順にあたる。

- 実装の見本は **fastapitemplate** の `bounded_contexts/identity_federation/`
  （テンプレートなので、そこから作れば以下は既に満たしている）
- assay 自身の仕様は `docs/OIDC_INPUT.md`、権限は `docs/PERMISSIONS.md`

---

## 0. 用語

| 語 | 意味 |
|---|---|
| **IdP** | 認証する側。assay（画面は `assay.*`、発行者は `identity.*`） |
| **RP** | 認証を任せる側。あなたが作るアプリ |
| `sub` | assay がその利用者へ振る識別子（UUID）。**RP から見た利用者の正体** |
| `iss` | 発行者。テナントごとに `https://identity.example.com/{tenant_id}` |
| `sid` | セッション識別子。id_token と logout_token の両方に載り、同じセッションを指す |

**発行者はテナントごとに違う。** discovery は
`{issuer}/{tenant_id}/.well-known/openid-configuration` にある。
⚠ **テナント UUID を前置きしないと 404 になる**（権限不足に見えるが、単に道が無い）。

---

## 1. 結び付きの鍵は `(iss, sub)` である。メールアドレスではない

RP が持つ利用者の行には、**`(iss, sub)` の組**を保存する。これが federation の鍵になる。

⚠ **メールアドレスを鍵にしない。**

- assay では**メールアドレスの無い利用者を作れる**（ログイン識別子は社員番号でも電話番号でもよい）。
  鍵にしていると、そういう利用者は永久に入れない。
- メールアドレスは**変わる**。変わった瞬間に同一人物と見なせなくなる。
- 別テナントに同じアドレスの別人が居ることがある。`iss` を外すと衝突する。

**未登録の `(iss, sub)` が来たとき、同じメールアドレスのローカル口座へ黙って寄せない**
（ADR-0049 I9）。寄せてよいのは、そのアドレスの所有を両側が同じ意味で検証しているときだけで、
assay の `email_verified` は「テナント管理者がそう主張している」であり本人の証明ではない。
既定は寄せない。

### 結び付けは本人の操作として置く

「まだ結び付いていない人を入れる」導線は、**ログイン画面ではなく設定画面**に置く。

1. 本人がローカルの手段でログインする
2. 設定画面の「IdP と連携する」を押す
3. assay へ往復し、戻ってきた `(iss, sub)` を**その人の行へ**結び付ける

⚠ **往復の目的（ログインか連携か）をクエリ文字列に置かない。** 署名付き Cookie（または
サーバー側の行）に入れる。クエリに置くと、他人にリンクを踏ませて連携先を差し替えられる。

解除も本人の操作で置く。ただし ⚠ **最後の入り口は外させない** ——ローカルのパスワードも
パスキーも無い利用者が連携を解除すると、誰も入れない行が残る。

## 2. 往復のしかた

### `/authorize` へ送るもの

| パラメータ | 扱い |
|---|---|
| `response_type` | `code` のみ（implicit / hybrid は受けない） |
| `scope` | `openid` を必ず含む。他は `profile` `email` `offline_access` |
| `state` | ⚠ **必須。** 無いと `invalid_request` |
| `code_challenge` / `code_challenge_method` | ⚠ **必須。`S256` のみ。** 無いと `invalid_request` |
| `nonce` | **任意**（`response_type=code` だけなので）。送れば id_token に載って返る |
| `redirect_uri` | 登録値と**完全一致**。末尾のスラッシュ 1 つで落ちる |
| `acr_values` | 認証の強度を要求する（§3） |
| `prompt` | `none` / `login` / `consent` / `select_account` |

⚠ **PKCE を送らない実装は弾かれる。** 素の OAuth2 ライブラリを使うときはここを確認する。

### 戻りの検証

`id_token` は JWKS（`{issuer}/.well-known/jwks.json`）で署名を検証し、`iss` `aud` `exp`
を確かめる。`nonce` を送ったなら照合する。**RS256 のみ**。

⚠ **`email` が入っていないことがある。** `sub` 以外はすべて「あるかもしれない値」として扱う。
`claims_supported` に並んでいることは「毎回入る」を意味しない。

### 折り返しは何度でも開かれる

`/callback` は、利用者がブラウザの戻る・再読み込み・共有されたリンクで**もう一度開く**。
2 回目の `invalid_grant` を画面に出すと「入れているのにエラーが出る」になる。
⚠ **既にログインできているなら、黙って行き先へ戻す。**

## 3. 認証の強度（`acr`）—— 要求したら確かめる

assay が意味を定義して**要求されたら必ず効く**値は 2 つだけ。

| 値 | 意味 |
|---|---|
| `urn:assay:ac:mfa` | 多要素で認証した |
| `urn:assay:ac:single` | 単一要素で認証した |

`acr_values` を送ったら、**返ってきた `id_token.acr` が要求を満たしているか RP 側で照合する。**
満たしていなければログインを通さない。

⚠ **確かめないなら要求しない。** 要求だけして照合しない形がいちばん悪い ——設定画面には
「MFA を必須にした」と出ているのに、実際には素通しになる。

⚠ **`amr` を強度の判断に使わない。** `amr` は使われた方式（RFC 8176）で、監査と表示のためだけ。
外部 IdP を経由した先で何が使われたかは assay も知らない。

---

## 4. プロフィールの写しは IdP が正 —— RP では編集させない

`email` / `preferred_username` / `name` は assay が持つ。RP はそれを**写している**だけ。

- **ログインのたびに上書きする。** 初回の `provision` で 1 度書いて終わりにしない
  （assay で改名しても RP の表示が永久に古いままになる）。
- ⚠ **一意列でぶつかる値は飛ばす。** 別の利用者が既に使っているメールアドレスが降ってきたら、
  その項目だけ更新しないで先へ進む（ログインを落とさない）。ログには**値を残さない**。
- 結び付きのある利用者には、その項目を**画面から外す**（直す先は IdP である、と示す）。
  ⚠ 外さずに残すと、直しても次のログインで黙って戻る。
- ローカル口座の利用者は今までどおり直せること（ローカル口座を意図して持つアプリの場合）。

### グループ／ロールの対応表は作らない

⚠ **assay は `groups` クレームを発行しない。** グループ名からロールを引く設定を用意しても、
一度も効かない。RP 側のロールは RP が決める（既定ロールの付与と、ログインごとに同期するか
どうかだけ持てば足りる）。

権限も同じで、assay の `scope` に業務上の権限は載らない。⚠ **機械のトークン
（`client_credentials`）の `scope` は必ず空**で、`aud` も汎用である。呼ばれた側が
`client_id` を見て決める。

## 5. 止めたら届く —— 3 つで塞ぐ

管理者が利用者を止めたとき、RP のログイン状態も終わらせる必要がある。⚠ **どれか 1 つでは
足りない。** assay 側は ADR-0053 で「失効させたら知らせる」を実装済みで、**残りは RP 側**である。

### (1) back-channel logout の受け口

`POST {rp}/…/backchannel-logout`（`application/x-www-form-urlencoded` の `logout_token`）を
受ける口を作り、その URL をクライアント登録の `backchannel_logout_uri` に入れる。
⚠ **登録していない RP には何も届かない。**

`logout_token` の検証（Back-Channel Logout 1.0 §2.6）:

- JWKS で署名検証、`iss` `aud` `iat` を確認する
- `events` に `http://schemas.openid.net/event/backchannel-logout` が入っていること
- ⚠ **`nonce` が入っていたら拒否する**（仕様が禁じている）
- `jti` を控えて**重複配送を弾く**（再試行で同じ `jti` が来る）
- `sid` があればそのセッションだけ、無ければ **`sub` の全セッション**を終わらせる
  ——⚠ **管理者が利用者を止めたときは `sid` が入らない。** `sid` 必須で書くと、
  いちばん効いてほしい場面で何もしない

失敗は 400 で返す。**401 で返さない** ——送っているのは IdP であって利用者ではないので、
「認証し直せ」の意味になる応答は間違いになる。

### (2) アクセストークンを短命にする

⚠ **受け口が落ちていたときの上限時間は、RP のアクセストークンの寿命そのものである。**
検証のたびに DB を引かない作り（ステートレス）にするなら、寿命を短くして上限を作る
（fastapitemplate 系は **5 分**）。

そのうえで、**新しいトークンを出す経路と新しい入り口を作る経路だけは確かめる**:

| 経路 | DB を引くか |
|---|---|
| 読むだけ（普通の API） | 引かない |
| 新しいトークンを出す（refresh・ロール切り替え・パスワード変更） | ⚠ **引く** |
| 新しい入り口を作る（パスキー登録・連携の追加） | ⚠ **引く** |

引かないと、止まった利用者が 5 分ごとに新しいトークンを取り続けられる（＝止まらない）。

### (3) 定期照合

受け口も寿命も取りこぼしたぶんを拾う。RP 側の `last_login_at` を持っている利用者を、
assay の利用者一覧（管理 API）と突き合わせて、消えている・止まっている相手を無効化する。

## 6. サインアウトの範囲は RP が決める

「このアプリからサインアウト」が **assay からもサインアウト**するかは、アプリの性格で決める。

- **SSO でしか入れないアプリ** —— assay まで通す（RP-initiated logout）。通さないと、
  ログアウトしたのに次の瞬間に黙って再ログインする
- **ローカル口座も持つアプリ** —— 通さない。片方の都合で共有のセッションを切らない

通す場合は `end_session_endpoint` へ `id_token_hint` と `post_logout_redirect_uri`
（登録済みのもの）、必要なら `state` を付ける。

## 7. クライアント登録で決めること

| 項目 | 注意 |
|---|---|
| `client_id` | テナント内で一意 |
| 認証方式 | `client_secret_basic` / `client_secret_post` / `private_key_jwt` / `none`。**併存しない** |
| `redirect_uri` | 完全一致。開発用と本番を分けて登録する |
| `backchannel_logout_uri` | ⚠ **入れないと停止が届かない**（§5） |
| `post_logout_redirect_uri` | §6 を使うなら |
| `scopes` | 要求できる上限。`openid` を含める |

**秘密を持てない相手には `private_key_jwt`** を使う（共有秘密を配らずに済む）。
鍵の置き場は `/srv/secrets/oidc`。⚠ **stg は `private_key_jwt` に未対応**なので、
確認は prod で行う。

## 8. よくある落とし穴

- ⚠ **PKCE を送っていない** ——`invalid_request` で画面にすら着かない
- ⚠ **`redirect_uri` の末尾スラッシュ** ——完全一致なので 1 文字で落ちる
- ⚠ **テナント UUID を前置きしていない** ——404 になり、権限の問題に見える
- ⚠ **`email` が必ず来ると思っている** ——来ない利用者が居る
- ⚠ **`groups` でロールを配ろうとしている** ——assay は発行しない
- ⚠ **`acr_values` を送って照合していない** ——効いていないのに効いた顔になる
- ⚠ **`logout_token` を `sid` 必須で書いている** ——管理者による停止が素通りする
- ⚠ **認証を足したら PWA のインストールが消えた** ——`sw.js` を認証の内側に置かない
- ⚠ **`/callback` の 2 回目を紙にしている** ——入れているのにエラーに見える
