# ADR-0057: 名簿は「このアプリを使ってよい人」を答える（利用者一覧の管理 API）

## 背景

ADR-0049 の I7 は「利用者を止めたら RP に届く」を 3 つで塞ぐと決めている。back-channel logout の
受け口と、停止したときに送る側（ADR-0053）は入った。残っているのは **3 つ目の定期照合**である
——受け口が落ちていた・通知が失われたときの取りこぼしを、RP が定期的に拾い直す。

照合は「RP の `federated_identities` と IdP の利用者一覧を突き合わせる」と書かれているが、
⚠ **その一覧を引く口が assay に無い。** 近いものは 2 つあるが、どちらも用途が違う。

| いまあるもの | なぜ使えないか |
|---|---|
| `GET /{tenant_id}/admin/members` | ⚠ **`sub` を返さない**（内部 ID だけ）。RP の名簿の鍵は `(iss, sub)` なので突き合わせられない。アプリも見ない |
| `GET /{tenant_id}/admin/applications/{application_id}/current-users` | 画面が「全員」を「個別」へ倒すときの写し元。ページングが無く、上限 500 で黙って切れる |

## 決定

### 1. 答えるのは「このアプリを使ってよい利用者」——テナントの利用者一覧ではない

ADR-0054 でアプリの段ができ、「誰が使ってよいか」はアプリに付いた。したがって RP が問うべきは
**自分のアプリの名簿**であって、テナントの利用者全員ではない。

- ⚠ **割り当てのモードに関わらず同じ形で答える。** `EVERYONE` ならテナントの有効なメンバー、
  `INDIVIDUAL` なら割り当てられた利用者。RP は違いを知らない
- ⚠ **テナントの名簿を配らない。** 「個別」のアプリに全員を返すと、そのアプリを一度も使って
  いない人まで RP に見える

### 2. 宛先は **OIDC の `client_id`** で指す

> ⚠ **ADR-0059 で置き換えた。** 「呼んできたサービスアカウントはどのアプリのものか」を RP に申告させる
> 向きが逆だった。いまは `GET {issuer}/admin/applications/self/users` で、宛先は呼び出し元の
> サービスアカウントの名乗りから assay が決める。結び付いていなければ 404 ではなく 403。

`GET /{tenant_id}/admin/applications/oidc/{client_id}/users`

`client_id` は **RP が既に持っている唯一の値**である。アプリの内部 ID を持たせると設定が 1 つ増え、
⚠ **アプリを作り直した日に、RP は古い ID のまま静かに別の名簿を読む。** 解決は判定と同じ
`find_by_oidc_client_id`（アプリ ↔ binding ↔ client）を通す。

binding が無い client は **404**。⚠ **空の名簿を返さない** ——移行前・移行漏れの client を
「誰も使えない」と答えると、RP は全員を止める。判定側が同じ場合に**素通し**にしているのと同じ理由で
ある（ADR-0054）。

### 3. 載せるのは `sub` と、**3 つの状態**だけ

| 状態 | 意味 | RP がすること |
|---|---|---|
| `allowed` | いま使ってよい | そのまま |
| `blocked` | assay に居るが、いまは使えない | ローカル口座を止める。⚠ **結び付きは残す**（戻る可能性がある） |
| `unknown` | このテナントの利用者ではない（＝消えた） | 止める。結び付きごと落としてよい |

- ⚠ **プロフィールを載せない。** 属性の写しはログインのたびに渡っている（ADR-0049 の I5）。
  ここは棚卸しの口であって、属性を配る口ではない
- ⚠ **理由を細かく返さない。** 「割り当てが無い」と「アカウントが止まっている」を分けて返すと、
  ⚠ **割り当てのモードが RP に漏れる**（ADR-0054 の決定「RP にモードを知らせない」）。
  そのうえ **RP の行動は同じ**である ——どちらも「入れない・結び付きは残す」。分ける意味が無い
- 3 つは assay の内部状態ではなく、**RP が取る行動そのもの**である

聞き方は 2 つあり、返る形は同じである。

| 聞き方 | 返るもの |
|---|---|
| そのまま引く | **このアプリの候補**を `sub` 昇順で 1 ページ分（`EVERYONE` ならテナントのメンバー、`INDIVIDUAL` なら割り当てのある利用者）。状態は `allowed` か `blocked` |
| `subs=` で聞く | 聞いた `sub` それぞれの状態。⚠ **`unknown` が返るのはこちらだけ** |

⚠ **候補を絞ってから返さない**（`allowed` だけにしない）。絞ると、状態を決める規則が SQL 側にも
必要になり、⚠ **判定と一覧で規則が 2 つ**になる。候補をそのまま出して状態を添えれば、規則は
[`Application::roster_state`] の 1 つで済む。

### 4. 規則は判定と同じ関数から作る

一覧が判定と食い違うと、⚠ **「名簿に居るのに入れない」「居ないのに入れる」が起きる**。そこで
状態の決定は `Application::admits`（ADR-0054）を通す。SQL が返すのは事実
（アカウントの状態・メンバーシップの状態・割り当ての有無）だけで、可否の判断はしない。

⚠ **判定に無い条件を足さない。** `INDIVIDUAL` でメンバーシップを見ないのは判定がそうだからで
あり、一覧だけが厳しいと「名簿に居ないのに入れる」側へずれる。`EVERYONE` がメンバーシップを見る
のは、「全員」がテナントの中だけを指すため（ADR-0054）。

### 5. ⚠ 差分（`updated_since`）は入れない。照合は**全件**で回す

一見あると嬉しいが、**この用途では安全でない近道**になる。

- ⚠ **外した割り当ては差分に出てこない。** 行そのものが消えるので、変更として観測できない
  ——照合がいちばん拾いたい変化が、いちばん伝わらない
- ⚠ **新しい割り当ては `users.updated_at` を動かさない。** 利用者の行は触られないので、
  利用者の更新時刻で差分を取ると**足された人も漏れる**
- `users.updated_at` に索引も無い（足すなら移行が要る）

代わりに、**ページング**（`limit` / `offset`、既定 50・上限 200）と、
**`subs` で問い合わせる形**（RP が持っている `sub` を渡し、その 1 つずつの状態を受け取る。
⚠ 一度に 100 件まで）を用意する。前者は「このアプリの候補」、後者は「私が持っているこの人たちは
どうなったか」で、⚠ **`unknown`（消えた）を答えられるのは後者だけ**である（消えた人は、
いない以上、候補には現れない）。

### 6. ⚠ 止めたアプリは「空」ではなく「全員 `blocked`」で返る

アプリを止める（`DISABLED`）と、候補は消えず、**全員が `blocked`** になる（判定と同じ意味
——止めたアプリは誰も使えない。ADR-0054）。⚠ **空にしないのは、「誰も使えない」と「引けなかった」
を取り違えさせないため**である。

名簿が本当に空になるのは、候補が 0 件のときだけである ——「個別」で名簿が空（⚠ ADR-0054 の
とおり、これは「全員」ではなく「誰も入れない」）か、「全員」でメンバーが 1 人も居ないとき。

RP 側は、**引けなかったとき（404・5xx・タイムアウト）には何もしない**こと（ADR-0049 の I7）。
⚠ 「一覧が空＝全員辞めた」と読むと、障害のたびに全員を止める。

### 7. 権限は既存の `idp.applications:read` を使う（新しいコードを作らない）

> ⚠ **ADR-0059 で置き換えた。** 権限コードでは通さず、アプリの名乗り（サービスアカウント）として
> 結び付いていることで通す。下に書いた「サービスアカウントにはアプリが無い」は、アプリを持つのでは
> なく**アプリの名乗りになる**ことで解けた。

この口が返すのは「アプリと、そこに割り当てられた利用者」であり、`idp.applications:read` の説明
そのものである（migration `0045` / `0054`）。

⚠ **これは「自分のアプリだけ」には絞れない。** 付与された機械は、そのテナントの**他のアプリ**の
名簿も読める。絞るには「機械をアプリへ結び付ける」段が要るが、⚠ **サービスアカウントにはアプリが
無い**（ADR-0054 の決定 7。利用者がブラウザで入る RP だけをアプリとして開く）。したがって
自己参照（`self`）では解決できない。**ここでは踏み込まず**、必要になったときに別の ADR で決める。

## 捨てた案

### A. テナントの利用者一覧を返す（当初の案）

「テナントの利用者を `sub` と状態で引く口」。⚠ 採らないのは、**アプリごとの答えにならない**ため
である。RP が知りたいのは「私を使ってよい人」であって、テナントの全員ではない。加えて「個別」の
アプリへ全員の名簿を渡すことになる。

### B. `updated_since` による差分同期

決定 5 のとおり、**照合がいちばん拾いたい変化（外された・消えた）が伝わらない**。⚠ 動くように
見えて取りこぼす口は、無いより悪い。

### C. アプリの内部 ID（`application_id`）で指す

RP に設定が 1 つ増える。⚠ **アプリを作り直すと ID が変わり、RP は古い ID のまま静かにずれる**
——しかも「読めている」ので気付けない。

### D. 断る理由を細かく返す（`not_assigned` / `account_disabled` / `not_a_member`）

⚠ 割り当てのモードが漏れる（「個別」でなければ `not_assigned` は返り得ない）。しかも **RP の
行動は同じ**なので、分岐だけが 7 本の RP に増える。

### E. 専用の権限コードを新設する（`idp.application-users:read`）

⚠ **狭くならない。** 決定 7 のとおり自分のアプリには絞れないので、「他のアプリの名簿も読める」
点は変わらないまま、権限の語彙だけが増える。

## 帰結

- RP は `client_id` と管理トークンだけで名簿を引ける（新しい設定項目は無い）
- ⚠ 照合は全件で回す。差分は無い
- ⚠ アプリを止めると、その RP は全員を止める（意図した意味ではあるが、**止める操作の重さが変わる**）
- 「消えた」を答えられるのは `subs` を渡した問い合わせだけ
