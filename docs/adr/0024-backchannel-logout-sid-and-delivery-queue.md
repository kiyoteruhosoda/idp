# ADR-0024: `sid` は発行経路を辿って運び、ログアウト通知は署名済みトークンを保存しないキューで再送する

- 日付: 2026-08-08
- 状態: 採用
- 関連: ADR-0018（Cookie 非依存の api/web ハンドオフ）、OpenID Back-Channel Logout 1.0 §2.1、
  `migrations/0021_backchannel_logout_deliveries.up.sql`

## 背景

バックチャネルログアウトには 2 つの欠けがあった。

**1. ID Token に `sid` が無い。** `sid`（セッション識別子）が無いと、RP は届いた
`logout_token` を「どのログインセッションのログアウトか」に対応づけられず、`sub` 単位で
全セッションを落とすしかない。同じ利用者が複数の端末から使っている場合、片方のログアウトが
もう片方も落とす。

`sid` は SSO セッション由来の値だが、**`/token` は `sso_session_id` Cookie を読めない**
（ADR-0018 で api はブラウザ Cookie を読まないと決めた）。ID Token を発行するのは `/token` なので、
値の出所と使う場所が離れている。

**2. 通知が「一度送って終わり」だった。** RP が一時的に落ちている・ネットワークが詰まっている、
といった通常の障害で通知が失われる。ログアウトは**失われたことに誰も気づかない**種類の操作で、
RP 側にセッションが残り続ける。

## 決定

### 1. `sid` は SSO セッションのハッシュから導出し、発行経路を辿って運ぶ

`sid` は `sso_sessions.session_hash` から、ドメイン分離した SHA-256 で導出する
（`session_hash` そのものは出さない。RP へ渡す値から手元の認証情報を復元させないため）。

Cookie が読めない場所へ値を届けるために、**発行経路そのものを運搬路にする**:

```
sso_sessions          → auth_sessions.sso_sid
auth_sessions.sso_sid → authorization_codes.sid
authorization_codes   → refresh_tokens.sid  →  ID Token の sid クレーム
```

ログインを処理するのは web からの `/internal/authenticate`（そこでは SSO セッションが手元にある）
なので、その時点で `auth_sessions.sso_sid` へ書く。あとは code・refresh token へ引き継ぐだけで、
`/token` は自分が受け取った code / refresh token の行から `sid` を読める。

リフレッシュで再発行される ID Token も同じ `sid` を持つ（同じログインセッションの継続であるため）。

### 2. キューには署名済み `logout_token` を保存しない

`backchannel_logout_deliveries` が持つのは宛先・`sub`・`sid`・`jti`・試行回数・次回試行時刻・
最後のエラーだけで、**署名済みトークンは持たない**。再送のたびに発行し直す。

`logout_token` は署名済みの bearer credential で、これを DB に寝かせると
「保存された長命な資格情報」が 1 種類増える。行を読めた者がそのまま RP へ投げられる。
再署名のコストは無視できる（RSA 署名 1 回）。

`jti` は行の identity として先に決めておき、再送しても同じ値を使う。RP が `jti` で重複排除
できるようにするため（再送が二重ログアウトとして見えない）。

### 3. 再送は指数バックオフ・上限つき、取り出しは行単位の CAS

30 秒を基準に指数バックオフし、1 時間で頭打ち（`BACKCHANNEL_LOGOUT_MAX_ATTEMPTS`、既定 8 回で
打ち切り）。打ち切った行も**消さずに残す**（届かなかったという事実が運用情報として要る）。

送信ワーカーがキューから行を取り出すときは、`attempts` の**現在値を条件にした `UPDATE`**
（compare-and-swap）で確保する。`SELECT` してから `UPDATE` する形だと、ワーカーが 2 つ動いた
場合に同じ行を二重に送れてしまう。1 文で「試行回数が読んだ値のままなら次回試行時刻を進める」を
行い、更新できた行だけを送る。

決着済み（成功・打ち切り）の行は `BACKCHANNEL_LOGOUT_RETENTION_DAYS`（既定 7 日）で削除する。

## 影響

- ID Token に `sid` が入るため、RP はセッション単位でログアウトを扱える。既存の RP は
  未知のクレームを無視するだけで、破壊的変更にはならない。
- `sid` は SSO セッションに紐づく。ログインし直せば新しい `sid` になる
  （`sso_session_id` はログインのたびに再生成されるため）。
- 通知の到達性が「送った・送っていない」から「何回試して今どうなっているか」に変わり、
  届かない RP を運用で特定できる。
- ワーカーはプロセス内で回るが、取り出しが行単位の CAS なので api を複数プロセスにしても
  二重送信にはならない（G9 のシングルインスタンス前提の例外）。

## 却下した案

- **`sid` を `/token` のリクエストから受け取る。** RP が自称する値を信じることになり、
  他人のセッションを指す `sid` を送られると RP 側で誤ったログアウトを誘発できる。
- **`sid` に `sso_session_id`（Cookie 値）をそのまま使う。** RP へ渡す値から本人の
  セッション Cookie が復元できてしまう。導出には一方向関数を挟む。
- **送信を同期的に行い、失敗したらログアウト自体を失敗させる。** 落ちている RP が 1 つあると
  利用者がログアウトできなくなる。ログアウトは利用者側で必ず成立させ、通知は非同期で追う。
- **キューに署名済みトークンを保存して再送を軽くする。** 上記のとおり、保存された bearer
  credential を増やす代償に見合わない。
