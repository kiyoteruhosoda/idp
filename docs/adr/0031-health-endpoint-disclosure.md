# ADR-0031: ヘルスは公開面をサービス名までに留め、詳細は内部面に置く

- Status: Accepted
- Date: 2026-08-25
- 関連: `docs/adr/0007-api-web-service-split.md` §5（内部サービストークン）・§8（ヘルスチェック）、
  `docs/adr/0016-domain-split-as-default-topology.md`、
  `docs/adr/0019-sibling-api-hostname-and-web-origin-rp-id.md`（web=`idp.*` / api=`identity.*`）、
  `docs/adr/0030-machine-authentication-private-key-jwt.md`（時計ずれが認証失敗として現れる）

## 背景

`GET /healthz` は api と web の両方にあるが、**返すものが違っていた**。

| | 応答 |
|---|---|
| api | `{"status":"ok"}` |
| web | `200` のみ（**本文なし**） |

domain-split（ADR-0016・ADR-0019）で web（`idp.nolumia.com`）と api（`identity.nolumia.com`）は
別ホストになった。にもかかわらず応答に手がかりが無いため、`curl https://idp.nolumia.com/healthz`
が空の 200 を返したとき、**それが仕様なのか壊れているのか、そもそもどちらのサービスが答えたのかが
その場では分からない**。実際にこの取り違えが起きた。

ホスト名を見れば分かる、では足りない。前段プロキシの `location` の書き間違いや DNS の向き先違いは
「叩いたつもりと違うサービスが答える」形で現れるので、**取り違えを検出したい当のものをホスト名に
頼って判断することはできない**。

一方で「では色々返そう」と公開面を太らせるのは、既存の方針と衝突する。`router.rs` は Swagger UI を
既定で配信しない理由を「api 面は公開されるため、管理 API を含む全エンドポイントの仕様が無認証で
読めてしまう」と書いている。ヘルスも無認証・全世界公開の面である。

## 決定

### 1. 公開面（`/healthz`・`/readyz`）に載せるのは「どのサービスが答えたか」まで

`/healthz` の本文を api・web で同じ形にし、`service`（`"api"` / `"web"`）を含める。

```json
{ "status": "ok", "service": "web" }
```

`service` を公開してよいのは、**秘密ではなく（DNS を引けば分かる）、かつ攻撃者の役に立たない**
ためである。逆にこの 2 条件を満たさないもの——ビルド版数・コミットハッシュ・依存先の詳細・
稼働時間——は公開面へ足さない。

liveness をこれ以上太らせない理由はもう 1 つある。LB や監視が数秒おきに叩く経路であり、
**依存を見に行かない・安く返る**ことが liveness の定義そのものだからである。

### 2. 詳細は `/internal/health` に置く（内部トークンの内側）

版数・起動時刻・稼働時間・サーバー時刻・依存先の検査結果は `/internal/health` で返す。
`/internal/metrics`（G6）と同じ扱い——**プロキシ遮断（`docker/nginx.conf` の
`location /internal/ { return 404; }`）＋ サービストークン**の二重である。

api と web の**両方**に置く。web 自身の状態（版数・起動時刻・api への到達性）は api には分からず、
api の `/internal/health` を見ても「web が生きているか」には答えられないため。web は api を呼ぶ側と
して既に同じトークンを持っているので、新しい秘密は増えない。

応答の形は api・web で共有する（`assay_contracts::health::ServiceHealth`）。片方だけ形が違うと、
監視の設定と障害時の切り分け手順が service ごとに割れる。

### 3. サーバー時刻を返す

`server_time` を `/internal/health` に含める。HTTP の `Date` ヘッダでも秒精度の時刻は得られるが、
**時計ずれが認証失敗として現れる**経路があるため、状態レポートの中に明示的に置く価値がある——
`private_key_jwt` の client assertion は `exp` 5 分・時計ずれ許容 60 秒で判定するので（ADR-0030
決定 5）、ずれは「理由の分からない `invalid_client`」として現れ、原因に辿り着きにくい。

### 4. `status` は検査結果から導出する

`ServiceHealth::new` が `checks` を見て `"pass"` / `"fail"` を決める。監視側はこの 1 値だけを見れば
よく、検査項目が増えても監視設定を追随させずに済む。

`checks` の `detail` に**内部エラーの原文は入れない**。内部トークンの内側ではあるが、詳細は
運用ログ（`tracing::error!`）が持つ役割であり、二重に管理すると片方だけ古くなる。

## 影響

- `/healthz` の応答本文が変わる。**web は本文なし → JSON になる**ため、本文が空であることを
  前提にした監視があれば影響を受ける（ステータスコードだけを見る一般的な設定は影響なし）。
- `/internal/health` はプロキシ経由では 404 である（決定 2）。運用者が読むには
  Compose ネットワーク内（`docker compose exec`）か、サービスのポートへ直接到達する必要がある。
- 内部トークンのヘッダ名と定数時間照合を `assay_contracts::internal_auth` へ集約した。api と web に
  同じ定義が 2 つあり、web 側に 3 つ目を作るところだった。照合を各サービスで書き直すと
  **片方だけ定数時間でなくなる**危険がある。

## 積み残し（本 ADR では決めない）

**`/version` は `git_version`（コミットハッシュ）を無認証で公開している。** 決定 1 の基準に照らすと
公開面に置くべきものではなく、Swagger UI を既定で伏せている判断とも整合しない。動いているコミットが
分かることは、どの既知の不具合が塞がっているかを外から判断できることを意味する。

本 ADR ではヘルスの範囲だけを決め、`/version` の公開範囲は別途判断する（画面表示に使っている
経路があり、移動には web 側の取得経路の変更を伴うため）。

## 却下した案

- **公開 `/healthz` に版数・稼働時間まで載せる。** curl 一発で全部見えて運用は楽だが、無認証で
  全世界に指紋情報を配ることになる。監視 SaaS など認証を通せない相手から叩く必要があるなら
  再検討の余地はあるが、その要件は現時点で無い。
- **サービス名も載せない（現状維持）。** 取り違えの検出をホスト名に頼ることになり、まさに
  ホスト名の設定ミスを疑う場面で使えない。
- **`Date` ヘッダで足りるとしてサーバー時刻を返さない。** 秒精度は足りるが、ヘッダは
  「状態レポート」としてまとまっておらず、`/internal/health` 1 本で切り分けを終える形にならない。
- **web の詳細を api の `/internal/health` に含める。** api が web の状態を代弁することになり、
  web が落ちているときに何も答えられない（api から見た到達性しか分からない）。
