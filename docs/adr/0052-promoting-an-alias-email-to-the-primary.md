# ADR-0052: 別名のメールアドレスを主メールへ昇格させる

- Status: Accepted
- Date: 2026-09-14
- 関連: `docs/adr/0050-email-is-a-login-identifier.md`（主メール行。**本 ADR は決定 5 に例外を
  1 つ足す**）、`docs/adr/0025-login-identifier-registry.md`（登録簿）、
  migration 0052（`primary_email_of_user`）

## 背景

ADR-0050 で `users.email` は登録簿の**主メール行**になった。追加のメールアドレスは登録簿へ
足せる（画面も管理 API も既にある）が、**既に登録してある別名を「主」へ昇格させる操作が無い。**

いま付け替えるには、プロフィール編集でメールアドレスを書き換える。書き換えれば
`sync_primary_email_identifier` が主メール行を追随させ、通知の宛先も一緒に動くので、
**結果としては正しい**。足りないのは一覧から 1 手で選ぶ操作だけである。

とはいえ、その 1 手が無いことは見た目より悪い。管理者の画面には「この人が使えるアドレス」が
並んでいて、その中の 1 つが主メールだと分かる。にもかかわらず、隣の行を主にするには**別の画面へ
行き、並んでいる値を手で打ち直す**ことになる。打ち間違えれば、登録簿に無い 3 つ目のアドレスが
主メールとして作られる ——一覧に並んでいた値を選ぶだけの操作で、新しい値を作る余地は要らない。

## 決定

### 1. 昇格は登録簿の操作として置く

`POST /{tenant_id}/admin/users/{user_id}/login-identifiers/{identifier_id}/primary-email` を足す。
`idp.users:write` が要る（他の識別子操作と同じ）。

**`PATCH` の項目（`is_primary_email: true`）にしない。** 昇格は「この行の値を真にする」のでは
なく、**いまの主メール行の降格と選んだ行の昇格の入れ替え**である。項目として書けるように
すると `is_primary_email: false`（＝誰も主メールでない状態）も要求として書けてしまうが、
それは受け付けられない —— `users.email` は NOT NULL で、宛先の無い利用者は作れない。
**書けるのに必ず断る要求を型に残さない。**

### 2. 昇格できるのは、その利用者の `email` 種別の行だけ

電話番号や社員番号を主メールにできると、`users.email` にメールでない文字列が入り、
パスワードリセットとメール検証の宛先がそこになる。判定はアプリ層（種別を見て 400）と
SQL の `WHERE`（`identifier_type = 'email'`）の両方に置く —— 判定と書き込みの間に開く窓は、
条件を書き込みの側にも持たせないと閉じない。

主たるログイン識別子の行（`primary_of_user`）も除く。ユーザー名の行は常に `username` 種別
なので種別の判定で既に落ちるが、**条件を「メールであること」だけに寄せない**。主識別子は
プロフィール編集だけが動かす、という ADR-0025 の決めごとを SQL 側にも残す。

### 3. 3 つの書き込みを 1 つのトランザクションに置く

順に **降格 → 昇格 → `users.email` の差し替え**。`primary_email_of_user` は UNIQUE なので、
先に昇格させると一瞬でも 2 行が主メールになり、書き込みが落ちる。

途中で落ちたときに残ってはいけない状態は 2 つある。**主メール行が 0 本**（通知の宛先を
失う）と、**`users.email` と主メール行が別の値を指す**（入り口と宛先が割れる）である。
前者は「対象が在るか」を書く前に確かめることで、後者はトランザクションで防ぐ。

`users.email` に入れる値は**呼び出し側から渡させず**、同じトランザクションの中で対象行の
`display_value` を読む。渡させると、画面に出ていた値と実際に昇格した行が食い違ったとき、
`users.email` と登録簿が割れたまま成功する。

### 4. 昇格した行は必ず有効にする

主メール行は識別子単位で有効/無効を切り替えられない（ADR-0050 決定 5。`set_active` が
`primary_email_of_user IS NULL` で除外する）。無効なまま昇格させると、**二度と有効にできない行**
が通知の宛先になる。ADR-0050 決定 2 の「主メールは基本的に有効」と同じ理由である。

### 5. もとの主メール行は消さず、別名として残す

消すとその値は誰のものでもなくなり、他人が登録できてしまう（ADR-0025 の無効化と同じ話で、
「この値は使えない」と「この値は誰のものでもない」は別である）。降格した行は普通の別名なので、
不要なら管理者が明示的に削除できる。

### 6. `email_verified` は動かさない

昇格で `users.email` は変わるが、検証済みフラグは触らない。管理者によるメール変更（MT25）が
検証済みを維持するのと同じ扱いであり、ADR-0050 が「識別子としてのメールに所有確認を課さない」
と決めたのとも揃う。**ここだけ厳しくしても、隣の経路（プロフィール編集）が同じ状態を作れる。**

### 7. 監査は `user.primary_email_changed` として残す

識別子の追加・切替（`user.login_identifier_*`）とは別の種別にする。動くのは**通知の宛先**で
あり、識別子を 1 つ増やすのとは影響が違う。`reason` には昇格の出どころ
（`source=login_identifier`）だけを記録し、アドレスは記録しない（PII。`CLAUDE.md`「ログ」）。

## 影響

- スキーマは変わらない（`primary_email_of_user` は migration 0052 で入っている）。
- 管理コンソールのログイン識別子一覧に、`email` 種別の行だけボタンが 1 つ増える。
- 二度押しても壊れない。同じ行をもう一度昇格させると、降格と昇格が同じ行に当たって
  結果は変わらない ——画面を開いたままの二度押しはありふれた操作で、断る理由が無い。
