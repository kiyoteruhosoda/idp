# ADR-0041: パスキーを本人確認（step-up）の手段として受け付ける

- Status: Accepted
- Date: 2026-09-02
- 関連: `docs/adr/0040-passkey-on-logins-outside-the-authorization-flow.md`（同じ規則をログインへ適用済み）、
  `docs/adr/0020-authentication-policy.md` §3（パスキーは `require_mfa` を満たす）、
  ユーザー認証・認証ポリシー仕様書 §15（step-up）

## Context

重要操作（認証器の追加・削除、外部 IdP の紐付け、セッション失効、パスワード変更）の直前に求める
本人確認は、**パスワードしか受け付けなかった**。`StepUpService::verify` は必ずパスワードを検証し、
要件が多要素なら加えて TOTP を求める。本人確認の画面にもパスワードの欄しかない。

一方 ADR-0040 は「パスキーしか持たない利用者」を前提に置いた。パスキーで管理コンソール・ポータルへ
入れるようにし、強制パスワード変更はパスキー経路では見ないと決めている（決定 3）。

その結果、**パスキーで入った利用者はその先でパスキーを 1 本足すことも、失くした 1 本を消すことも
できない**。認証器の管理は step-up の対象で、その step-up がパスワードを要求するためである。
「パスキーを登録する画面自体がパスワードでしか入れなかった」という ADR-0040 の Context が、
1 段内側で残っていた。

全員が `users.password_hash` を持つので完全な締め出しではない（忘れていれば
`/forgot-password` から戻せる）。それでも、パスワードを一度も意識せずに運用できると謳いながら、
アカウントの要になる操作でだけパスワードを要求する形になっていた。

## Decision

### 1. パスキーはパスワードの代わりに step-up の起点になる

`step_up.rs` は「起点は常に本人しか知らないもの」と書いていた。理由は**端末を拾った攻撃者に本人確認を
通させない**ことで、TOTP だけで通せる作りを禁じるための規則である。

パスキーはこの要求を知識要素を経ずに満たす。所有要素と User Verification を 1 回のセレモニーで
満たし、かつフィッシング耐性がある。**ログインでは既にそう扱っている**（ADR-0020 §3 / ADR-0040
決定 2）ので、同じ規則を本人確認へ広げる。

`[WebAuthn]` は第二要素を含むため多要素として記録される（`AuthenticationStrength::from_methods`）。
したがって多要素を要求する操作（認証器の管理・外部 IdP の紐付け）も、この 1 回で満たす。
**TOTP を持たない利用者にとっては、これが唯一の導線になる。**

パスワード固有のゲート（アカウントロック `locked_until`）はパスキー経路では見ない ——
パスワードの総当たりへの対策で、署名鍵の総当たりには効かない（ADR-0040 決定 3 と同じ規則）。
IP レート制限は**掛ける**（ログイン・パスワード step-up と同じ枠を消費する。入口ごとに枠が違うと、
片方で締め出された攻撃者がもう片方で試行を続けられる）。

### 2. 本人確認のチャレンジは `challenge_type` で分ける

ADR-0040 決定 4 は「用途は `auth_session_id_hash` の有無で分ける」とし、`challenge_types` へ値を足す
案を採らなかった。**あの列が既に用途を表していた**からである。

本人確認のチャレンジは認可フローにも直接ログインにも結合しないため、`auth_session_id_hash` は
用途を表せない。ここでは種別を足すのが用途を表す唯一の場所になるので、`step_up` を追加する
（migration 0047）。あわせて、これまで誰も見ていなかった `challenge_type` を**登録・ログイン・
本人確認のすべての完了側で検証する**ようにした。

セッションを作る（ログイン）ことと、あるセッションを引き上げる（本人確認）ことは別の操作である。
分けないと、本人確認のために出したチャレンジでログインが成立し、その逆も通る。

### 3. セレモニーは足さない。持ち主の確認だけを足す

WebAuthn のセレモニーは `application::passkey_assertion` の 1 か所のままにする（ADR-0040 決定 1）。
本人確認が上に載せるのは 1 つだけ ——「**アサーションの持ち主がこのセッションの利用者か**」の照合で
ある。セレモニーは「誰のパスキーか」までしか答えないため、他人のパスキーで他人のセッションを
引き上げさせないのはこの層の責務になる。

`StepUpService` はセレモニーの実装全体ではなく、`PasskeyStepUpCeremony`（開始・検証の 2 つ）だけを
見る。本人確認の判定を試すのに、クレデンシャル・チャレンジ・登録簿・テナント所属の 4 リポジトリと
WebAuthn 実装を組ませないためである。実装は `PasskeyAssertionService` 1 つで変わらない。

### 4. 導線は「使えるパスキーを持っている利用者」にだけ出す

`step-up/check` が `passkey_available` を返し、画面はそれが真のときだけボタンを出す。持っていない
利用者に見せると、ブラウザのダイアログが出てから失敗する。判定は登録簿の `active` な WebAuthn 行の
有無で、**一時停止中（AP9）の本しか無い利用者には出さない**（押しても通らないため）。

## Consequences

- パスキーで入った利用者が、パスワードを打たずに認証器を足せる・消せるようになった。`require_mfa`
  下で TOTP を持たない管理者にとっては、これが唯一の導線になる。
- 「全利用者にパスワードを変えさせる」運用は、これまでどおりパスキー利用者には効かない
  （ADR-0040 決定 3 の帰結が 1 段広がっただけで、新しい抜け道は増えていない）。
- ブラウザ側のスクリプトは増えていない。`assets/passkey-login.js` を 4 画面目として共有し、
  開始・完了のパスと、完了 API へ添える値（どの操作か・終わったらどこへ戻すか）を data 属性で渡す。
- `passkey_challenges.challenge_type` の許可値が 3 つになった。`down` は残存する `step_up` 行を
  削除してから旧 CHECK へ戻す（チャレンジは 5 分で失効する一時データなので消してよい）。
