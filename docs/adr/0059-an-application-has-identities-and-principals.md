# ADR-0059: アプリには「名乗り」と「使う主体」の 2 つの関係がある

- Status: Accepted
- Date: 2026-09-16
- 置き換えるもの: ADR-0054 の決定 7（サービスアカウントはアプリではない、の扱い）、
  ADR-0057 の決定 2（宛先は `client_id`）・決定 7（権限は `idp.applications:read`）、
  ADR-0042 のうちクライアントへの宛名の貸し出し（`client_resources`）
- 関連: `docs/adr/0054-an-application-is-the-thing-a-relying-party-hangs-from.md`（アプリという段）、
  `docs/adr/0057-the-roster-answers-who-may-use-this-application.md`（名簿の口）、
  `docs/adr/0042-tokens-carry-an-audience-not-a-vocabulary.md`（宛名）、
  `docs/adr/0038-registration-splits-into-accounts-and-relying-parties.md`（サービスアカウント）、
  `docs/adr/0037-management-api-access-tokens-and-permission-set.md`（管理トークン）、
  `docs/adr/0032-client-usage-drives-the-registration-form.md`（ログイン用とサービスアカウントを 1 つの client に同居させない）

## 背景

ADR-0057 で入れた名簿の口は、RP が**自分のログイン用 `client_id` を経路に書いて**聞き、認可は
`idp.applications:read` で通していた。

```
GET {issuer}/admin/applications/oidc/{client_id}/users     （旧）
```

これは向きが逆だった。

- ⚠ **「呼んできたサービスアカウントはどのアプリのものか」を RP が申告している。** assay が
  持つべき事実を、呼ぶ側の設定に置いている
- ⚠ **`idp.applications:read` はテナントの全アプリの名簿を読める。** 名簿を読むためだけに、
  他のアプリの名簿まで読める権限を配ることになる（ADR-0057 の決定 7 が持ち越した穴）

穴の根は、**サービスアカウントとアプリの関係を assay が持っていない**ことにある。ADR-0054 の
移行はサービスアカウントにも「自分だけのアプリ」を作ったが、それは関係ではなく、サービスアカウントを
アプリと取り違えたものだった。

同じ根から、宛名（ADR-0042）にも歪みが出ている。宛名は「どの API の名前か」なのでアプリのものだが、
いまは**アプリを経由せずに**クライアントへ直接貸している（`client_resources`）。「wiki の API を
使ってよいサービスアカウントは誰か」を知るには、wiki の宛名を 1 つずつ辿るしかない。

## 決定

アプリと、アプリの外にあるものとの関係は **2 つだけ**である。

| 関係 | 問い | 相手 |
|---|---|---|
| **名乗り**（binding） | 「これはどのアプリか」 | ログイン用 client・SAML SP・サービスアカウント・宛名 |
| **使う主体**（assignment） | 「誰がこのアプリを使ってよいか」 | 人・サービスアカウント |

### 1. 名乗りは 4 種類。1 つの相手は 1 つのアプリにだけ属する

| `kind` | 相手 | 例 |
|---|---|---|
| `oidc` | ログイン用の client（`authorization_code`） | wiki のログイン |
| `saml` | SAML の SP | |
| `service_account` | アプリ自身が assay を呼ぶときの client（`client_credentials` だけ） | `nolumiawiki-prod-machine` は wiki の名乗り |
| `resource` | アプリの API の宛名（`aud`） | `api://nolumiawiki` |

- ⚠ **1 つの相手は 1 つのアプリにだけ属する**（DB の UNIQUE）。2 つに属せると、その相手から来た
  要求（ログイン・名簿・トークン）がどのアプリのものか決まらない
- ⚠ **種類と相手の性質を突き合わせる。** ログイン用として結び付けられるのは `authorization_code` の
  client、サービスアカウントとして結び付けられるのは `client_credentials` **だけ**の client。
  取り違えると、前者はログインの判定からアプリが外れ、後者は利用者のトークンで self の名簿が読める
- 列の名前は `protocol` から `kind` へ改める。サービスアカウントと宛名はプロトコルではない
- 相手は**人が知っている値**で指す（`client_id`・宛名の URI）。SAML の SP だけは内部 ID（ADR-0054 のまま）
- 既に別のアプリの名乗りなら 409 で、⚠ **そのアプリの名前を返す**（どこから外せばよいかを探させない）

### 2. 名簿の口は「呼んできたサービスアカウントのアプリ」を答える

```
GET {issuer}/admin/applications/self/users?limit=&offset=&subs=
Authorization: Bearer {client_credentials + resource={issuer}/admin で取った管理トークン}
```

- 宛先のアプリは、呼び出し元の `service_account` の名乗りから決める。**RP は経路に何も書かない**
- ⚠ **権限コードでは通さない。** 名乗りとして結び付いていることが、そのアプリの名簿を読んでよい
  理由である。テナント全体の `idp.applications:read` を持っていても、名乗りが無ければ通らない
- ⚠ **結び付いていない主体（利用者・名乗りの無いサービスアカウント）には 403**。空の名簿を返すと、
  RP は全員を止める
- ⚠ **ログイン用の名乗り（`oidc`）では通らない。** 同じ `client_id` 列を使うので、種類を見ないと取り違える
- 応答の形・状態の語彙（`allowed` / `blocked` / `unknown`）・ページング・`subs`（100 件まで）は
  ADR-0057 のまま
- 旧口 `/admin/applications/oidc/{client_id}/users` は消す（本番で使っている RP は無い）

### 3. 名乗りを持つサービスアカウントには、権限コードが無くても管理トークンを出す

`client_credentials` で `resource={issuer}/admin` を要求したとき、これまでは**権限コードを 1 つ
以上持つ client にしか**出していなかった（ADR-0037。出しても全部 403 になるトークンを作らないため）。

これに「**あるアプリの `service_account` の名乗りである client**」を足す。`perms` は空のままで、
通るのは名乗りで決まる口（self の名簿）だけである。テナント全体の権限は 1 つも増えない。

### 4. サービスアカウントはアプリではない。移行 0054 が作ったアプリは消す

ADR-0054 の決定 7 は「サービスアカウントにはアプリを作らない」としたが、移行 0054 は全 client を
アプリへ開いたので、既存のサービスアカウントには「自分だけのアプリ」が残っている。

**サービスアカウントはアプリではなく、アプリの名乗り（決定 1）か、アプリを使う主体（決定 5）である。**
残すと、同じ名前の「アプリ」が 2 つ並び、人はどちらに割り当てればよいのか迷う。移行 0058 で消す。

- ⚠ **消してよいのは、そのアプリが誰にも使われていないときだけ。** 割り当てがある・認証ポリシーから
  参照されている・他の名乗りも持っている、のどれかに当たれば**移行を失敗させる**（黙って残さない・
  黙って消さない）
- ⚠ **どのアプリの名乗りにするかは移行で推測しない。** `app_name` の似た client を探して結び付ける
  ような推測は、誤ると別のアプリの名簿を読ませる。人が画面・API で結び付ける

### 5. 使う主体は人とサービスアカウントの 2 種類（`USER` / `SERVICE_ACCOUNT`）

`application_assignments` を広げ、アプリを使ってよい主体として**人とサービスアカウントを同じ段に並べる**。

- **人の割り当て** = そのアプリへログインしてよい（ADR-0054 のまま）
- **サービスアカウントの割り当て** = **そのアプリの宛名（`resource` の名乗り）宛のトークンを取ってよい**

⚠ 次の 4 点は種類で振る舞いが違う。画面にも明記する。

1. **「全員（`EVERYONE`）」に含まれるのは人だけ。** サービスアカウントは必ず個別に割り当てる。
   「全員」は「テナントの利用者なら誰でも」であり、テナントのサービスアカウントまで含めると、
   宛名を持つアプリを「全員」にした瞬間にテナントの全サービスアカウントがその API を叩ける
2. **サービスアカウントの名乗り（決定 1）は 1 アプリだけだが、割り当ては何アプリにでもできる。**
   名乗りは「これは誰か」、割り当ては「何を使ってよいか」で、1 つのサービスアカウントが複数の API を
   使うのは普通である
3. **名簿（self）に載るのは人だけ。** 名簿は RP がローカル口座と突き合わせるためのもので、
   サービスアカウントの口座は RP に無い
4. **code の発行時の判定（`CodeIssuanceService`）は人だけを見る。** サービスアカウントはログインしない

### 6. 宛名のトークンは「宛名のアプリ」と「割り当て」で出す。`client_resources` は置き換える

`client_credentials` で `resource=X` を要求されたとき、次を**すべて**満たせば `aud=X` のトークンを出す。

1. X が登録済みで有効（ADR-0042 のまま）
2. X が、あるアプリ A の `resource` の名乗りである
3. A が有効
4. 要求元のサービスアカウントが A に割り当てられている

これで「wiki の API を使ってよいサービスアカウント」は、**wiki の詳細画面の「使う主体」に並ぶ**。
クライアントへ直接の貸し出し（`client_resources`）は、同じことを別の場所に持つだけになるので消す。

- ⚠ **既存の貸し出しは移行で写す。推測で写さない。** 貸し出し 1 行（client, X）について、X が
  あるアプリ A の `resource` の名乗りなら、（A, client）のサービスアカウントの割り当てへ写す。
  ⚠ **X がどのアプリの名乗りでもない貸し出しが 1 行でもあれば、移行を失敗させる。**
  「宛名 → アプリ」の対応は、移行の前に人が決定 1 の画面で結び付ける（＝対応表は DB の名乗りそのもの）
- 貸していた相手がサービスアカウントでない（`authorization_code` も持つ）行も、同じく移行を失敗させる

## 捨てた案

### A. 名簿の口を今のまま（`client_id` を経路に書く）にして、専用の権限コードを足す

⚠ **狭くならない**（ADR-0057 の捨てた案 E と同じ）。権限コードはテナント単位で、「自分のアプリだけ」を
表せない。

### B. サービスアカウント専用の表（`application_machine_clients`）を足す

名簿の口だけなら足りる。捨てたのは、**同じ形の関係が宛名にもあり、それが既に別の表
（`client_resources`）で持たれている**からである。「これはどのアプリか」を持つ場所は既に
`application_bindings` があり、そこへ種類を足すほうが、関係の置き場が増えない。

### C. 人の割り当てとサービスアカウントの割り当てを別の表にする

別の表にすれば決定 5 の 4 点は「その表を見ない」だけで成り立つ。捨てたのは、**画面と管理 API が
「このアプリを使う主体」を 1 つの問いとして扱う**ためである。表を分けると、一覧・追加・外すの
すべてが 2 本になり、「wiki を使っているのは誰か」に 2 回問い合わせることになる。4 点の違いは、
種類の列を見る場所（判定・名簿・件数）で明示的に書く。

### D. 移行で「宛名 → アプリ」「サービスアカウント → アプリ」を推測して写す

`app_name` や `client_id` の綴りから推せる組は多い。⚠ **誤ると、別のアプリの名簿を読める・
別のアプリの API を叩けるサービスアカウントが黙って生まれる。** 移行は失敗させて、人に結び付けさせる。

## 帰結

- RP の設定から「自分の `client_id` を経路に書く」が消える。名簿は `self` で引く
- サービスアカウントを使う RP は、**そのサービスアカウントをアプリの名乗りとして結び付ける**作業が
  1 回要る（結び付けるまで self は 403、権限コードを持たないなら管理トークンも出ない）
- `idp.applications:read` を名簿のために配る理由が無くなる
- 「このアプリの API を使ってよいサービスアカウント」がアプリの詳細画面に並ぶ（決定 6 の実装後）
- ⚠ 宛名の貸し出しを写す移行（決定 6）は、**すべての貸し出し先の宛名がアプリの名乗りになってから**
  でないと当たらない。順序は「決定 1〜4 を出す → 画面で宛名とサービスアカウントを結び付ける →
  決定 5・6 を出す」
- 移行 0054 がサービスアカウントに作ったアプリは消える。割り当て・ポリシー・他の名乗りのどれかが
  付いていれば移行が止まるので、黙って何かが外れることは無い
