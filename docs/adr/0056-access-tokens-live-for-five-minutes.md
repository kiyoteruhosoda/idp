# ADR-0056: アクセストークンの寿命は 5 分にする

- 日付: 2026-09-15
- 状態: 採用
- 関連: ADR-0037（管理トークンは通常のアクセストークンより短命）、ADR-0044（ログアウトで
  refresh token も失効させる）、ADR-0042（宛名 `resources`）、`docs/OPERATIONS.md` の設定表

## 背景

可用性と復旧の手当て（課題 #59）で RTO を測る過程で、⚠ **アクセストークンの寿命が
「決めた結果」ではなく、既定値のままだった**ことが分かった。`ACCESS_TOKEN_TTL_SECS` は
環境変数にも `system_settings` にも無く、組み込みの既定 900 秒（15 分）で動いていた。

寿命は本来、**2 つのものの間で決める**。

| 軸 | 長くすると | 短くすると |
|---|---|---|
| 可用性 | assay が落ちても、既に出ているトークンが長く使える | 落ちた時刻に近いところで止まる |
| 失効の速さ | 止めた利用者・止めたクライアントのトークンが残る | すぐ効く |

⚠ **この構成では、可用性の側がほとんど効かない。** RP は自前のセッションを発行し、
更新のたびに assay を引かない（`docs/RP_INTEGRATION.md`）。⇒ **アクセストークンを
延ばしても「assay が落ちている間に入れる人」は 1 人も増えない。**

実際に誰がアクセストークンを使い続けるのかを数えた（2026-09-15）。

- **利用者のトークン** —— RP が `userinfo` を引くのは**ログインの直後だけ**である
  （fastapitemplate 系 6 本と codelab-panel の実装を確認）。その後は RP 自身のセッション
- **機械のトークン**（`client_credentials`）—— ⚠ **同じ `ACCESS_TOKEN_TTL_SECS` が乗る**
  （管理 API の宛先を要求したときだけ `MANAGEMENT_TOKEN_TTL_SECS`。ADR-0037）。
  使い手（nolumiawiki / mp3play）は**期限の 60 秒手前で取り直す**作りで、
  取り直しの余裕は寿命に比例しない固定値である

⚠ **数える材料が 1 つ無いことも分かった。** `userinfo` の呼び出しは監査に記録されない
（`AuditEventType` に該当する種別が無い）ので、**「誰が引いているか」を監査ログからは
数えられない**。上の数えはログではなく RP の実装を読んで得たものである。

## 決定

- **`ACCESS_TOKEN_TTL_SECS` を 300 秒（5 分）にする。**
- ⚠ **組み込みの既定（900）は変えない。** 既定は一般の配布物のためのもので、
  この構成の判断ではない。決めたのは**この配備の値**である。
- **値は宣言に書く**（deploy-repo の `k8s/idp-prod/20-config.yaml`。stg も同値）。
  ⚠ **`system_settings`（DB）には置かない。** 設定の解決順は
  **既定 < 環境変数 < DB** なので、DB に置くと**宣言が黙って負ける**状態を作る
  ——画面から変えられることと、正本がどこかは別の話である。
- ⚠ **`restart_required` の設定なので、当てるには api の入れ替えが要る。**

## 理由

- **失効の速さだけが残った軸である。** 利用者を止めた・クライアントを止めた・鍵を
  入れ替えたとき、既に出ているアクセストークンは寿命の間だけ通り続ける。
  ⇒ **その上限を 15 分から 5 分へ縮める。**
- **機械のトークンが短くなる分の負荷は無視できる。** 取り直しは 14 分ごとから 4 分ごとへ
  増えるが、使い手は 2 本（nolumiawiki / mp3play）で、どちらもプロセスに 1 本を持ち回る。
- **管理トークン（300 秒）と同じ長さになる。** ⚠ ADR-0037 は「管理トークンは通常の
  アクセストークンより短く保つ」と書いている。この ADR で**両者は並んだ**
  ——管理トークンをさらに短くはしない。300 秒は「権限を剥奪してから効くまでの上限」として
  既に受け入れた長さであり、通常のトークンをそこへ揃えることは、その判断と矛盾しない。
  ⚠ **管理トークンを今後さらに縮めるなら、この並びを崩さないこと。**

## 捨てた案

- **900 秒のまま据え置く** —— 延ばす理由が無いのに、失効の効きだけが遅い。
  「決めていなかった値」を追認することにもなる。
- **60 秒にする** —— ⚠ **使い手の取り直しの余裕（60 秒）と衝突する。** 余裕を引くと
  寿命が 0 以下になり、`max(lifetime - margin, 1.0)` の下限へ落ちて**毎回取り直し**に
  なる。idp への往復が跳ね上がるうえ、⚠ **assay が落ちた瞬間に機械の処理も止まる。**
- **DB（`system_settings`）に置く** —— 画面から変えられるが、⚠ **宣言を読んでも本当の
  値が分からなくなる**（解決順で DB が勝つ）。運用中に試したい日が来たら、
  そのときだけ DB に置き、⚠ **戻すときは行ごと消す**こと。

## 影響

- 止めた利用者・クライアントのアクセストークンが通り続ける上限: **15 分 → 5 分**
- 機械トークンの取り直し: **14 分ごと → 4 分ごと**（使い手 2 本）
- ⚠ **`expires_in` を見ずに寿命を決め打ちしている実装があれば壊れる。**
  2026-09-15 時点では見当たらない（取り直しは全部 `expires_in` から計算している）。
