# ADR-0042: トークンには宛名だけを刻む（リソース指標）

- Status: Accepted
- Date: 2026-09-02
- 関連: `docs/adr/0033-resource-server-authorization-belongs-to-the-application.md`（業務権限は配らない）、
  `docs/adr/0037-management-api-access-tokens-and-permission-set.md`（管理 API のトークン）、
  `docs/adr/0030-machine-authentication-private-key-jwt.md`（システムの認証）、
  `docs/adr/0009-multi-tenant-architecture.md` §6（テナントごとの issuer）、
  RFC 8707（Resource Indicators for OAuth 2.0）

## 背景

`client_credentials` で出るトークンの `aud` は **`{issuer}/userinfo` 固定**だった。`resource` を
解釈するのは assay 自身の管理 API（`{issuer}/admin`）だけで、それ以外を指定すると
`invalid_target` で断っていた（ADR-0037）。

結果として、**このテナントで機械トークンを持つ相手は、どのリソースサーバにも同じトークンを
出せる**。受け取る側から見ると「自分宛か」が判定できない。実際に運用へ出たのは 2026-09-02 の
blobshare で、機械の口（`/api/machine/objects`）は `aud` の検証を**明示的に諦め**、
`sub_type == "client"` と `client_id` の照合だけで認可している。

```json
{ "iss": "…/01a00dfe-…", "sub": "0e26…", "client_id": "0e26…",
  "aud": "…/userinfo", "scope": "", "sub_type": "client" }
```

いま機械の口を持つアプリは 1 つしかないので事故になっていないが、2 つ目（nolumiawiki の
ページ API）を作った時点で、**1 本のトークンが両方の口に通る**。どちらかが `client_id` の
突き合わせを忘れれば、そこが素通しになる。

### 「では scope も載せるか」を検討して、載せないことにした

宛名を載せるなら、ついでに `page:write` のような業務権限も載せられる——という案は自然に出る。
標準的な認可サーバ（Entra ID・Auth0・Okta・Keycloak）はどれも、API を 1 つのオブジェクトとして
登録し、そこに公開する scope の語彙を宣言させる形を持っている。

採らなかった理由は 2 つある。

1. **変更の頻度が違う。** 宛名（`https://wiki.nolumia.com`）は一度決めればまず変わらないが、
   語彙はアプリの権限モデルを直すたびに変わる。語彙を assay に置くと、**アプリを直すたびに
   assay を触る**運用になる。ADR-0033 が「業務上の権限を scope として配ることはしない」と
   決めたのはこの点であり、その判断はここでも変えない。
2. **粒度が合わない。** 宛先のアプリ（例: nolumiawiki）の認可は「動詞」だけでは表せない
   ——「どのプロジェクトの」ページを書いてよいかはメンバーシップで決まる。語彙をトークンに
   載せても、対象を決める表はリソースサーバ側に残る。**表を 1 つ残すなら、2 か所に分けない。**

## 決定

**`aud` に入る名前だけを登録できるようにする。何をしてよいかは載せない。**

1. **`resources`（宛名の登録簿）を足す。** 1 行が「この認可サーバが `aud` に載せてよい名前」。
   テナント内で一意。`ACTIVE` / `DISABLED` を持ち、停止すると新しいトークンの宛先に使えなくなる。
2. **`client_resources`（クライアント × 宛名）を足す。** 「どのクライアントがどの宛先を要求して
   よいか」。**語彙の列は持たない。**
3. **`client_credentials` の `resource` を表引きにする。** 登録済みかつ当該クライアントへ
   許可済みなら `aud` はその名前、`perms` は載せず、寿命は通常のアクセストークンと同じ。
4. **未登録・停止中・未許可を応答で区別しない**（すべて `invalid_target`）。区別すると、
   総当たりで「どの宛名が登録されているか」を探れる。切り分けは監査ログの `reason`
   （`unknown_resource` / `resource_disabled` / `resource_not_granted`）で行う。
5. **assay 自身の名前空間（issuer 配下）は宛名として登録できない。** `{issuer}/admin` は
   `perms` と短い TTL を持つ別物であり（ADR-0037）、`resources` にも載せない。

   ⚠ **これは多層防御であって、脆弱性を塞ぐものではない。** 仮に `{issuer}/admin` を登録できた
   としても、(1) 発行の分岐は**管理 API の腕が表引きより先に当たる**のでその行は読まれず、
   (2) 仮に読まれても `perms` の付かないトークンでは管理 API の `RequirePerms` が 1 つも
   通らない（保有コードは DB ではなく `perms` クレームから読む。`management_token::held_codes`）。
   守っているのは**分岐の順序という暗黙の前提**で、並べ替えられた瞬間に崩れる種類のものなので、
   登録の側でも塞ぐ。`client_permissions` の包括権限を CHECK 制約とアプリ層で二重に防いでいるのと
   同じ扱いである。

   完全一致ではなく**接頭辞**で予約するのは、`{issuer}/admin/`（末尾スラッシュ）のような
   紛らわしい名前を残さないため。エンドポイントが増えるたびに「その名前は貸してよかったか」を
   考え直すことになる。
6. **`resource` は引き続き `client_credentials` 専用。** 利用者を認証した grant に付けると
   `invalid_target` のまま（RFC 8707 は禁じていないが、人の代理で他 API を叩く相手が現状居ない。
   開けるなら scope の議論とセットになる）。
7. **権限コードは `idp.resources:read` / `idp.resources:write`。** クライアント管理
   （`idp.clients:*`）と分けるのは、宛名がクライアントより長生きする独立した登録簿だから
   ——RP を 1 つ消しても、その RP が公開していた API の名前は他の呼び出し元にとって在り続ける。

## 帰結

- **リソースサーバは `aud` を検証できるようになる。** blobshare の `verify_aud: false` は、
  自分の宛名を登録して貸してもらった時点で `true` にできる。`client_id` の突き合わせは
  そのまま残す——`aud` は宛先、`client_id` は相手であって、片方が片方を置き換えない。
- **assay は「誰であるか」と「どこ宛か」までを保証し、「何をしてよいか」は保証しない。**
  受け側の allowlist は無くならない。無くしたいなら語彙の登録が要り、それは上記の理由で
  採らなかった。
- **宛名は叩かれない。** URI の形をしているのは名前が衝突しないためで、`api://blobshare` の
  ように解決できない値でよい。`redirect_uri`（ブラウザを実際に送り込む場所）と混同しないこと。
- **正規化しない。** 登録された文字列をそのまま保存し、照合は完全一致で行う。`url` の正規化
  （`https://x` → `https://x/`）を保存側に持ち込むと、リソースサーバが受け取った `aud` を
  文字列で比べたときに外れる。
- **停止・削除・取り消しは、発行済みのトークンには効かない。** 署名済みのクレームは取り消せない
  ので、効き始めるのは次の発行から（最大でアクセストークンの寿命ぶん遅れる）。急いで止めるなら
  受け側でその `client_id` を落とすほうが速い。
