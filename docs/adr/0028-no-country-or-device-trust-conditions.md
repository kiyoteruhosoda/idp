# ADR-0028: 認証ポリシーに「国」「端末信頼」の条件を置かない

- 日付: 2026-08-10
- 状態: 採用
- 関連: ADR-0020（認証ポリシー）、`docs/Progress.md` AP3 / AP14、
  ユーザー認証・認証ポリシー仕様書 §8（適用条件）

## 背景

ADR-0020 で認証ポリシー（`deny` / `require_mfa` / `allow`）を導入し、AP3 で適用条件に
ネットワークゾーン（CIDR）・時間帯・`requested_acr` を足した。仕様 §8 には、これに加えて
**接続元の国**と**端末の信頼状態**を条件に挙げてある。この 2 つは実装せずに `docs/Progress.md`
へ AP14 として残してあった。

条件式そのものは他の条件と変わらない（`PolicyConditions` に配列を 1 本足し、`matches` に
1 項足すだけ）。**足りないのは判定材料の方である。**

- **国**: 接続元 IP から国を出すには、GeoIP データベースを同梱して更新し続けるか、フロント
  プロキシが供給するヘッダを取り決めて信頼するかのどちらかが要る。前者はデータの取得・
  ライセンス・更新の運用が丸ごと増え、後者は「そのヘッダを付けるのは自分のプロキシだけ」を
  保証する経路の設計（クライアント供給値の剥ぎ取り）が前提になる。
- **端末信頼**: 「この端末は信頼済み」と言うには、端末を登録し、再訪時に同じ端末だと識別し、
  信頼状態を持つ登録簿が要る。識別子を配る以上、それ自体が追跡可能な値になるため、寿命・
  失効・利用者からの見え方まで決める必要がある。認証器の登録簿（ADR-0022）に相当する規模の
  サブシステムが 1 つ増える。

## 決定

**どちらも実装しない。** AP14 をバックログから落とし、判断をここに残す。

### 1. 材料の無い条件を先に置くと、設定できるのに決して成立しない条件になる

`PolicyConditions` は「**評価材料が無い条件は一致しない**に倒す」という規則で書いてある
（ADR-0020 / `authentication_policy.rs`）。国の条件を材料無しで足すと、管理画面には「国」欄が
並ぶのに、その条件を持つポリシーは**どのリクエストにも一致しない**。

これは単に無駄な欄が増えるのではない。「日本国外からのログインを拒否する」を設定した管理者は
**拒否されていると信じる**。実際には何も起きていない。設定できることが保護されていることの
証拠にならない状態は、条件が無いより悪い ——「まだ無い」なら他の手段を採るが、「あるように
見えて効かない」なら他の手段を採らない。

### 2. 現に必要な範囲は既存の条件で足りている

国の条件が実務で使われる形はたいてい「社外・海外からのアクセスを絞る」であり、本 IdP の
想定配置（Synology DSM 上の単一組織・ADR-0005）では**ネットワークゾーン（CIDR）条件**が
同じ役割を果たす。社内ネットワークを許可し、それ以外に `require_mfa` を掛ける形は AP3 で
既に書ける。国の粒度が要るのは、拠点が多国に散り、かつ拠点ごとの IP を列挙できない規模に
なってからである。

端末信頼も同様に、いま表現したい「いつもと違う入り方には第 2 要素を求める」は
`require_mfa` × ネットワークゾーン／時間帯で近似できる。端末の同一性まで持ち出す必要が
あるのは、持ち出し端末の管理台帳が別に存在し、それと突き合わせたい場合である。

### 3. 材料が揃ってから、条件はその回に足す

条件式を先に入れて材料を後から足す順序は採らない。**先に入れた条件が「効かない期間」を
持ってしまう**からで、これは決定 1 の状態そのものである。国も端末信頼も、材料
（GeoIP データベースの同梱またはヘッダの取り決め／デバイス登録簿）を入れる変更と同じ回に
条件を足す。

## 再検討の条件

次のいずれかが起きたら、この判断を見直す。

- **国**: 拠点が複数国に増え、拠点 IP の列挙が運用として維持できなくなったとき。または、
  フロントプロキシ（Cloudflare 等、国コードヘッダを供給する経路）が構成に入り、
  クライアント供給値の剥ぎ取りを含めて信頼できると決められたとき。
- **端末信頼**: デバイス登録簿を必要とする別の要件（管理対象端末の限定、端末単位の失効）が
  立ち上がったとき。そのとき登録簿はこの条件のためではなく、その要件のために作る。

## 影響

- `PolicyConditions` は現状の 5 条件（`client_ids` / `user_ids` / `ip_cidrs` / `time_windows` /
  `requested_acr`）のままとする。JSON カラムなので、将来足す際にマイグレーションは要らない。
- 仕様書 §8 に挙がっている「国」「端末信頼」は**未実装のまま据え置く**。仕様に書いてあるものを
  実装しない判断であるため、この ADR がその根拠になる。
- `docs/Progress.md` から AP14 を削除する。AP3 の残件は無くなり、認証ポリシーの実装は
  「材料のある条件はすべて実装済み」という状態になる。
