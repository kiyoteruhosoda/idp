# ADR-0060: アプリを止めると、その名乗りのサービスアカウントも止まる

- Status: Accepted
- Date: 2026-09-16
- 関連: `docs/adr/0059-an-application-has-identities-and-principals.md`（名乗りと使う主体。**本 ADR は
  そこで決めなかった「止めたとき」を決める**）、
  `docs/adr/0054-an-application-is-the-thing-a-relying-party-hangs-from.md`（アプリの `status`）、
  `docs/adr/0057-the-roster-answers-who-may-use-this-application.md`（名簿。止めたアプリは全員 `blocked`）、
  `docs/adr/0037-management-api-access-tokens-and-permission-set.md`（管理トークン）、
  `docs/adr/0056-access-tokens-live-for-five-minutes.md`（発行済みトークンの寿命）

## 背景

ADR-0059 でサービスアカウントはアプリの「名乗り」（`service_account`）として同じアプリに束ねられた。
しかし**アプリを `DISABLED` にしたとき、その名乗りのサービスアカウントがどうなるか**は決めていなかった。

いまの挙動は片側だけ止まる。

| | 止まるか |
|---|---|
| 人のログイン（code の発行） | 止まる（ADR-0054） |
| **そのアプリの宛名**宛てのトークン（呼ぶ側のサービスアカウント） | 止まる（ADR-0059 の決定 6 の条件 3） |
| **そのアプリの名乗り**のサービスアカウントが取るトークン | ⚠ **止まらない** |

たとえば mp3play を止めても、mp3play のサーバは `mp3play-prod-machine` の名前で blobshare 宛ての
トークンを取り続け、音声を読み書きできる。「アプリを止める」が、そのアプリの人の入口だけを閉じる
スイッチになっていた。

## 決定

### 1. 名乗りのアプリが止まっていたら、`client_credentials` のトークンを出さない

`client_credentials` の要求元が、ある `DISABLED` のアプリの `service_account` の名乗りであれば、

- 既定のトークン（`resource` 無し）を出さない
- **他のアプリの宛名**のトークンも出さない（割り当てがあっても）

応答は `unauthorized_client`、監査の `reason` は `own_application_disabled`。

⚠ 宛名の「登録が無い／止まっている／割り当てが無い」を応答で区別しない方針（ADR-0042）は、
**呼ばれる側の宛名を探らせない**ためのものである。ここで理由を返すのは要求元自身のアプリの状態で、
認証を通った本人に隠す理由は無い。

### 2. 管理トークンは出す。ただし権限コードを載せない

`resource={issuer}/admin` だけは出す。`perms` は**空**にする（権限コードを持っていても載せない）。
通るのは名乗りで決まる口 ——自分の名簿（`/admin/applications/self/users`）だけになる。

名簿は、止めたアプリに対して**全員 `blocked`** を返す（ADR-0057）。RP は定期照合でそれを読み、
ローカルのセッションと口座を止める。⚠ **ここで管理トークンまで塞ぐと、RP は 401 を「引けなかった」と
読んで何もしない**（ADR-0057・RP_INTEGRATION §5 の「引けなかったときは何もしない」）。止めたことが
定期照合で届かなくなる。

### 3. 名乗り・割り当て・権限コードは消さない

止めるのは発行の判定だけである。アプリを `ACTIVE` に戻せば、次のトークンからそのまま戻る。

### 4. 発行済みのトークンは寿命まで待つ

判定は発行時だけに置く。発行済みのアクセストークンは寿命（ADR-0056。本番 300 秒）で切れる。
宛名のアプリを止めたとき（ADR-0059 の決定 6）と同じ扱いである。

### 5. 名乗りにしないもの

この連動は**名乗り**にだけ効く。**使う主体**（割り当て）のサービスアカウントは、割り当て先のアプリを
止めてもそのアプリの宛名が取れなくなるだけで、自分自身は止まらない（決定 6 のまま）。

⇒ 名乗りにするのは「**そのアプリ自身のサーバが使う口**」だけにする。アプリを**呼ぶ側**（CI・ランナー・
運用の道具）を名乗りにすると、呼ばれる側を止めたときに無関係な仕事まで止まるうえ、そのアプリの名簿まで
読めてしまう。

## 捨てた案

### A. 止めない（アプリの停止は人の入口だけ。サービスアカウントはクライアントの `status` で止める）

スイッチが 2 つに分かれる。「アプリを止めた」のにサーバが他のアプリの API を叩き続け、画面では
それが見えない ——ADR-0059 が名乗りを束ねた理由（アプリの画面が実体を映す）と食い違う。
ログインだけ止めてサーバは動かしたいときは、停止ではなく**割り当て**で絞れる。

### B. 管理トークンも含めて全部止める

§2 のとおり、定期照合が止まったことを読めなくなる。停止の配信（back-channel logout）は取りこぼしが
あり得るので、二段目を塞がない。

### C. 発行済みのトークンも introspection・管理トークンの検証で即時に無効にする

寿命が 300 秒で、宛名側の停止（ADR-0059 の決定 6）も発行時だけで判定している。片方だけ即時にすると
挙動が割れ、`introspection` と管理トークンの検証にアプリの参照を足すことになる。必要になったら
両方まとめて入れる。

## 帰結

- アプリの停止が、そのアプリのサーバの外向きの仕事（他のアプリの API・assay の管理 API）まで止める
- ⚠ **名乗りを誤って付けると、停止の巻き添えが広がる。** 名乗りはアプリ自身のサーバの口だけにする
- 止めたアプリの RP は、名簿で全員 `blocked` を読める（定期照合は動き続ける）
