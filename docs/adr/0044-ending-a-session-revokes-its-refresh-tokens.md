# ADR-0044: セッションを終えたら、そのセッションの refresh token も失効させる

- Status: Accepted
- Date: 2026-09-08
- 関連: `docs/adr/0009-multi-tenancy.md`（テナント境界）、
  マイグレーション `0021_backchannel_logout_deliveries`（`sid` の導入）、
  `crates/core/src/application/account_security.rs`（G10 セルフサービス）、
  RFC 6819 §5.2.2.3、OpenID Connect RP-Initiated Logout 1.0 §2

## 背景

トークンの寿命は短命アクセストークン（既定 15 分・`ACCESS_TOKEN_TTL_SECS`）と、
失効可能な refresh token（既定 30 日・rotation あり・期限はスライドしない）で組んである。
**この組み立て自体は正しい。** 30 日という長さは「失効が効く」ことを前提にして初めて成り立つ。

ところが、その前提を支えるはずの失効が**セッションを終える 2 つの経路で呼ばれていなかった**。

1. **セルフサービスの「この端末をログアウト」**（`account_security::revoke_session`）——
   `sso_sessions` の行を消すだけ。画面は
   `user-security-session-revoke-confirm = この端末をアカウントからログアウトしますか？`
   と訊いているのに、その端末のアプリは更新が通り続ける。
2. **RP-initiated logout**（`logout::logout`）—— SSO セッションの削除と未消費の
   authorization code の失効のみ。back-channel logout で RP へ `sid` を添えて
   「このセッションは終わった」と通知しておきながら、**同じ `sid` のトークンは受け付け続ける**。

`exchange_refresh_token` が確かめるのは、クライアントの認証・トークンの所有クライアント・
再利用検知・失効/期限・**利用者が有効か**の 5 つで、**セッションが生きているかは見ていない**。
それどころか新しいアクセストークンへ `sid: stored.sid.clone()` を載せ直す
（`token.rs`「元の認可で確立したセッションを指し続ける」）——もう存在しないセッションを
指したまま発行し続けることになる。

結果として、ログアウトを押した端末は 15 分ごとに新しいアクセストークンを取り直せる。
rotation は期限を延ばさないので上限は最初の発行から 30 日だが、**ログアウトしたはずの端末が
30 日動く時点でログアウトになっていない。**

道具は揃っていた。`refresh_tokens.sid` は 0021 で足してあり、`sso_session::sid_of` が
`session_hash` から導出して発行時に持ち回り、rotation でも引き継いでいる。
**書き込むだけで、一度も引いていなかった。**

## 決定

**セッションを終える操作は、そのセッションから出た refresh token も失効させる。**

1. `RefreshTokenRepository::revoke_all_for_session(user_id, sid, revoked_at) -> u64` を足す。
   `sid` へ索引を張る（マイグレーション 0050）。
2. `account_security::revoke_session` と `logout::logout` の両方から呼ぶ。
3. **テナントで絞らない。** `SsoSession` はテナントを持たない（利用者単位）ので、1 つの
   セッションが複数テナントのクライアントを認可し得る。テナントを条件へ足すと取りこぼし、
   取りこぼしたトークンは切ったはずのセッションを指したまま更新が通る。`user_id` との組で絞る。
4. **失敗したときの扱いを 2 つの経路で変える**（下記）。

### 失敗したらどうするか

| 経路 | 扱い | 理由 |
|---|---|---|
| セルフサービスの失効 | **fail-closed**（`Internal` を返す） | ここで成功を返すと「切ったつもりで切れていない」を画面が肯定してしまう。利用者は押し直せる。 |
| RP-initiated logout | **fail-open**（警告ログのみ） | 既にリダイレクト先を組み立てる段まで来ており、途中で投げると **Cookie を消せないまま利用者が宙に浮く**。同じ関数内の「セッション削除」「code 失効」も既に fail-open で、揃える。 |

同じ操作に見えて非対称なのは、**失敗したときに利用者が取れる行動が違う**ため。前者は画面が
残っていて押し直せる。後者は既にブラウザが遷移していく途中で、止めると状態が壊れる。

## 選択肢と理由

- **案A（採用）: `sid` で失効させ、セッションを終える 2 経路から呼ぶ。**
  値も導出も既にあり、足りないのは「引く手段」だけだった。
- 案B: セッション終了時に `revoke_all_for_user` を呼ぶ。**不採用。** 他の端末まで巻き込む。
  「この端末をログアウト」が全端末のログアウトになるのは、画面の問いに対する答えとして誤り。
- 案C: refresh grant の中で「`sid` のセッションがまだ在るか」を毎回引く。**不採用。**
  トークン発行のたびに `sso_sessions` を 1 回引くことになるうえ、**セッションの
  idle 失効で refresh も道連れになる**。refresh token の寿命は SSO Cookie の寿命とは別物で、
  ネイティブアプリはブラウザのセッションが切れた後も使い続けられてよい。
  終わらせるのは「利用者がログアウトを指示したとき」であって「Cookie が古くなったとき」ではない。
- 案D: 失効ではなく `revoked_access_tokens` に載せる。**不採用。** それは発行済み
  アクセストークンを止める仕組みで、更新そのものは止まらない。

## 影響

良い点:

- 「ログアウト」「この端末を切る」が、画面の言うとおりの結果になる。
- 索引 1 本と UPDATE 1 文で済む。rotation でチェーンが伸びていても 1 回で落ちる
  （`sid` は家族全体が共有する）。
- 統合テストで「発行 → 更新 → セッション終了 → 更新が断られる」を実 DB で通している
  （`crates/api/tests/session_end_revokes_refresh_tokens.rs`）。**修正を外すと落ちることも
  確認した**（外すと更新が 200 で通る）。

トレードオフ:

- ログアウト経路は fail-open なので、**DB が落ちている最中のログアウトはトークンを残す**。
  警告ログには出るが、利用者には見えない。ここを fail-closed にすると Cookie を消せない方の
  事故になるため、承知のうえで選んでいる。
- `refresh_tokens` に索引が 1 本増える（書き込みのコストが少し上がる）。

やり残し:

- **自分でのパスワード変更は、いまも refresh token を失効させない**
  （`application/change_password.rs`）。メールのリンク経由のリセットは
  `revoke_all_for_user` を呼び、画面も「既存のセッションはすべてサインアウトされています」と
  明言しているのに、自分で変えたときだけ何も起きないという非対称が残っている。
  本 ADR の範囲外（機構が別で、**変更した本人のセッションを除外する**手当てが要る）。
- `/revoke`（RFC 7009）が、提示されたトークンが認証中のクライアントに発行されたものかを
  確かめていない（`revocation.rs` が認証済みクライアントを `_client` として捨てている）。
  §2.1 の要求を満たしていない。これも別件。
