# ADR-0038: 登録は「アカウント」と「連携先」の二軸に分ける

- Status: Accepted
- Date: 2026-08-27
- 関連: `docs/adr/0009-multi-tenant-architecture.md` §3（メンバーシップ）、
  `docs/adr/0027-saml-external-idp.md`（外部 IdP のプロトコル欄）、
  `docs/adr/0030-machine-authentication-private-key-jwt.md`（システムの認証）、
  `docs/adr/0032-client-usage-drives-the-registration-form.md`（用途と登録内容）、
  `docs/adr/0037-management-api-access-tokens-and-permission-set.md`（`AdminActor`・クライアント権限）

## 背景

管理コンソールの「クライアント（RP）」という 1 つの画面が、**性質の違う 2 つのものを兼ねている。**

ADR-0032 の「用途」select がその境界である。

| 用途 | 実体 | 何を登録しているのか |
|---|---|---|
| ブラウザで利用者をログインさせる | `authorization_code` + redirect_uri | **ID を渡す相手**（RP） |
| システムが API を呼ぶ（利用者不在） | `client_credentials` のみ | **名乗る主体**（機械） |

前者は「この IdP を信頼するアプリ」であり、後者は「この IdP に認証される当人」である。向きが逆で、
ライフサイクルも失効の導線も違う。それが同じ画面・同じ語彙に同居しているため、
**「クライアント登録とは何の登録なのか」を一文で言えない。**

同じ混線が語彙にも出ている。SAML の RP は別画面「SAML クライアント (SP)」にあり、外部 IdP は
さらに別の概念（こちらが RP に回る相手）なのに、どれも「クライアント」と呼ばれ得る。

一方で、**この二軸はコードの中では既に分かれている。**

- `AdminActor`（ADR-0037 決定 7）は主体を「利用者 or クライアント」の 1 つの型で表す
- `ExternalIdpProtocol`（ADR-0027）は 1 画面のプロトコル欄で OIDC / SAML を切り替える

画面と語彙だけが追いついていない。

## 決定

### 1. 登録は 3 系統しかない。軸は「向き」で決まる

| 系統 | 相手は何か | 実体 |
|---|---|---|
| **アカウント** | この IdP へ向かって名乗る主体 | `users` + `tenant_memberships` / `clients`（redirect_uri なし） |
| **連携先** | この IdP から ID を受け取る RP・SP | `clients`（redirect_uri あり）/ `saml_service_providers` |
| **外部 IdP** | この IdP が名乗る側に回る相手 | `external_idps` |

「主体」は概念の軸名として使い、画面名には使わない。

### 2. アカウント登録は「種別」で、連携先登録は「プロトコル」で切り替える

**この 2 つは別の軸であり、同じ選択肢に並べてはならない。** プロトコル（OIDC / SAML）は連携先の
性質であって、主体の性質ではない。

| | 選択肢 | 切り替わるもの |
|---|---|---|
| アカウント登録 | 人 / **サービスアカウント** | 識別子・本人確認の方式・権限テーブル・止め方 |
| 連携先登録 | OIDC / SAML | 相手の識別子・戻り先・渡すもの・相手の鍵 |

出し分けの実装はどちらも既にある。外部 IdP 画面のプロトコル欄と、クライアント画面の
`client-form.js` がそれである。新しい仕組みは要らない。

### 3. 「クライアント」は連携先だけの語にする

機械の主体は **サービスアカウント** と呼ぶ。「クライアント」を主体側にも使うと、OAuth 2.0 の
`client_id` を持つものすべてが同じ名前になり、画面の語彙が実体の区別を失う。

**「メンバー」は動かさない。** この語は `tenant_memberships` の HOME / GUEST に割り当て済みで、
i18n も「所属元がこのテナントの利用者」と書いている。ここへ機械を入れると
**ゲスト招待できないメンバー**という説明のつかないものができる。メンバーはアカウント（人）の
テナント参加を指したまま、アカウントの下に残す。

### 4. api のモデルは変えない

「種別」も「プロトコル」も **web 側の語彙**である。ADR-0032 が「用途は api のモデルには無い。
api は `redirect_uris` の有無と `client_credentials` の可否という 2 値を持ち、web がその 2 値へ
翻訳する」と決めたのと同じ位置づけで、導出できるものは持たない。

したがって変更は `crates/web` の router・templates・`i18n/*/main.ftl`・コンソールホームのナビに
閉じる。テーブルは 1 つも変わらない。

### 5. 行がどちらの画面に出るかは `redirect_uris` の有無で決まる

`clients` テーブルは再編後も 2 つの画面にまたがる。OAuth 2.0 では RP も機械も同じ `client_id` と
いう器を使うので、これは消せない。**消せるのは画面と語彙の混線だけである。**

判別は一意に決まる。ADR-0032（Revised）が「両方」の姿を登録・更新のどちらでも拒むため、
どの行も必ず片方だけに属する。両立を許していたら、この決定は成り立たない。

## 影響

- **「クライアント登録とは何か」が一文で言えるようになる。** 連携先の登録である。
- **サービスアカウントの登録が、人の登録の隣に並ぶ。** 権限の付与も同じ場所に来る
  （`user_permissions` と `client_permissions` はテーブルこそ別だが、権限コードの体系は共通。
  ADR-0037 決定 3）。ただし**包括権限はクライアントへ付与できない**（決定 5）ので、種別によって
  付与できるコードが違うことは画面で示す必要がある。
- **SAML SP の登録が「連携先」の下に入る。** テーブルは `saml_service_providers` のままで、
  一覧と導線だけを束ねる。プロトコルは登録後に変更できない（外部 IdP の既存の扱いに揃える）。
- **移行作業は無い。** 既存の行はそのまま、どちらの画面に出るかが決まる。

## 却下した案

- **主体側の器を「メンバー」と呼ぶ。** 既存の語と衝突する（決定 3）。
- **`clients` を主体用と連携先用の 2 テーブルへ割る。** `client_id` の一意性・クライアント認証・
  トークン発行はどちらも同じ経路を通る。テーブルを割ると、その経路が 2 本になる。
  混線しているのは画面と語彙であって、永続化ではない。
- **「種別」を api のモデルにも持たせる。** ADR-0032 が用途について却下したのと同じ理由。
  `redirect_uris` と `client_credentials` から導出できるものを二重管理すると、不整合を作れる余地が残る。
- **外部 IdP を「連携先」に含める。** 向きが逆である。同じ画面群に置くと、
  「この IdP が信頼する相手」と「この IdP を信頼する相手」が同じ語で並ぶ。
- **SAML SP を `clients` へ統合する。** 持つ属性（entityID・ACS URL・証明書）が
  `redirect_uris` / `grant_types` / `scopes` と 1 つも重ならない。1 テーブルにすると、
  片方では必ず NULL の列が並ぶ。
