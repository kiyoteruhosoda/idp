# ADR-0039: 署名鍵の入れ替えは、公開してから署名する

- Status: Accepted
- Date: 2026-08-27
- **Revised**: 2026-08-28 — 猶予の対象を SAML にも広げた。下記『SAML メタデータにも同じ窓を作る』。
- 関連: `docs/adr/0030-machine-authentication-private-key-jwt.md`（クライアント側の鍵の入れ替え）、
  `docs/adr/0031-health-endpoint-disclosure.md`（単一インスタンス前提）、K2（自動ローテーション）

## Context

署名鍵の入れ替えは実装されていた（`KeyService::rotate_if_needed`。`not_after` の
`KEY_ROTATION_LEAD_DAYS` 日前に新鍵を生成し、旧鍵を退役させる）。しかし**入れ替えが 1 段**で、
新鍵の生成と署名の切り替えが同時に起きていた。

`new_key_material` は `not_before = now` で鍵を作り、署名鍵の選択は
「使用可能なもののうち `not_before` が最も新しい 1 本」である。つまり**生成した瞬間から新鍵で
署名が始まる**。

これは RP 側から見ると次のようになる。

```
t=0   新鍵を生成・ACTIVE・JWKS に載る・同時に署名も新鍵へ
t=0   RP は古い JWKS をキャッシュしている（新しい kid を知らない）
t=0+  RP に届く ID Token の kid が JWKS に無い → 検証失敗
```

未知の `kid` を見たら JWKS を取り直す RP は自力で回復するが、**TTL で持つ RP は TTL が切れる
まで検証に失敗し続ける**。鍵の入れ替えは年 1 回の静かな出来事のはずが、連携先によっては
その瞬間にログインが落ちる。

同じ画面まわりに、放置すると効いてくる穴が 3 つあった。

1. **最後の ACTIVE 鍵を退役できた。** `retire_key` は「すでに RETIRED か」しか見ない。画面から
   最後の 1 本を退役させるとトークン発行が止まる。補充は `rotate_if_needed` の
   「ACTIVE 鍵が無い」経路が拾うが、走るのは 1 時間おきである。
2. **手動生成は ACTIVE を 2 本にした。** 旧鍵は ACTIVE のまま残り、署名するのは新しい方だが、
   画面は両方を同じバッジで出すだけで**どちらが署名しているか分からない**。ここで新しい方を
   退役させると、署名は黙って古い方へ戻る。旧鍵は最長 1 年 ACTIVE のまま残る。
3. **補充が RS256 決め打ちだった。** 画面では ES256 も選べるので、ES256 で運用していて 1 の
   状態に落ちると、黙って RS256 へ戻る。

## 決定

### 1. 入れ替えは 3 段にする

| 段 | すること | 誰がやるか |
|---|---|---|
| 1 | 後継鍵を生成し、**JWKS へ公開するだけ**にする（`not_before` を未来に置く） | `rotate_if_needed` |
| 2 | `not_before` が来ると署名が後継鍵へ移る | **誰もやらない**（選択規則が自然にそうなる） |
| 3 | 追い越された ACTIVE 鍵を退役させる | `rotate_if_needed`（次の呼び出し） |

猶予は `KEY_ROTATION_PUBLISH_LEAD_HOURS`（既定 24 時間）。

**新しい状態は足さない。** JWKS の公開条件（`list_published`）は `not_before` を見ておらず、
署名鍵の選択（`find_active`）は見ている。つまり `not_before` を未来に置くだけで
「JWKS には載るが署名には使われない」が既に表現できる。`PENDING` のような status を足すと、
DB の CHECK 制約・`SigningKeyStatus`・JWKS の条件・画面表示の 4 か所を増やすことになり、
**得られるものは同じ**である。

**退役を 3 段目に置く。** 公開と同時に旧鍵を退役させると、`not_before` が来るまで署名できる鍵が
1 本も無くなる。「新鍵生成後に退役させることで signing 空白期間を排除」という従来の順序は、
公開と署名開始が同時だった前提でのみ正しかった。

**猶予は現行鍵の `not_after` で頭打ちにする。** `publish_lead` が `lead_days` より長い設定でも、
引き継ぎは現行鍵が切れる前に起きなければならない。頭打ちは自動生成だけでなく**手動生成にも効かせる**
（`KeyService::generate_key`）—— 越えた `not_before` を持つ後継鍵を作ってしまうと、`rotate_if_needed`
はそれを「公開済みの後継鍵」と見て待つだけなので、空いた穴は次の確認では埋まらない。
いま署名できる鍵が 1 本も無いときは猶予を置かない（待つ相手が居らず、そのあいだ発行が止まるだけ）。

### 2. 最後の署名可能な鍵は退役させない

`retire_key` は、対象を除いても署名できる鍵が残ることを確かめる。**公開しただけの後継鍵は
数えない**（`not_before` が来ていなければ署名できない）。

1 クリックでトークン発行を止められる導線を残さない。`delete_key` が ACTIVE を断っているのと
同じ形である。

### 3. 「署名中」を画面に出す

`status` からは読めない（ACTIVE は複数あり得て、署名するのは 1 本）。判定規則
（`current_signer_at`）を domain に置き、`find_active` の SQL と同じ規則であることを明記する。
api が `is_current_signer` / `is_pending` として返し、web が表示する。

**規則を web 側に持たせない。** web は `crates/core` に依存しない（ADR-0007）ので、規則を写すと
2 か所に分かれる。ずれると、画面で「署名中」と見えている鍵を退役させたのに署名が止まらない、
という画面からは説明のつかない挙動になる。

### 4. 補充するときのアルゴリズムは直前の鍵から引き継ぐ

決め打ちをやめる。画面で ES256 を選べる以上、補充経路だけが RS256 へ戻すのは筋が通らない。
起動時のブートストラップ（`ensure_active_key`）も同じ規則にする。

あわせて、**ブートストラップが要るかの判定を「ACTIVE 行があるか」から「いま署名できる鍵があるか」へ
変える**（`current_signer_at` ／ `insert_if_no_active` の SQL）。公開しただけの後継鍵も期限切れのまま
ACTIVE で残った鍵も status は ACTIVE なので、行の有無で見ると「鍵はある」と読まれ、署名できない
まま起動してしまう（起動時の fail-fast が素通しになる）。

### 5. 手動生成も既定は 3 段にする

管理画面の生成も既定で猶予を置く（`activate_immediately` は既定 `false`）。**猶予を捨てるのは
明示的な選択**にし、鍵の危殆化のように待てないときだけに使う。追い越された旧鍵は
`rotate_if_needed` が退役させるので、手動生成も 3 段の入れ替えとして完結する。

## Consequences

- **手動生成の結果がすぐには見えなくなる。** 生成しても 24 時間は「公開のみ（署名待ち）」で、
  署名は旧鍵が続ける。画面に説明を出し、急ぐときの逃げ道（「すぐ署名に使い始める」）を残す。
- **`KEY_ROTATION_PUBLISH_LEAD_HOURS` は RP の JWKS キャッシュ TTL より長く取る必要がある。**
  既定 24 時間はよくある TTL（数分〜1 日）を包む値として選んだ。連携先が長い TTL を持つなら
  伸ばす。
- **入れ替えの完了までに最短でも 2 回の確認が要る**（公開 → 引き継ぎ後の退役）。確認は 1 時間
  おきなので、`lead_days` は猶予より十分長く取る。既定は 30 日と 24 時間で、余裕は十分ある。
- **単一インスタンス前提は変わらない。** `rotate_if_needed` に排他制御は無い（K2 からの前提）。
  複数インスタンスで同時に走ると後継鍵が重複生成されうる。重複しても署名するのは 1 本で、
  余った方は次の確認で退役するため壊れはしないが、設計としては単一インスタンスのままである。

## SAML メタデータにも同じ窓を作る（2026-08-28 / T33）

本 ADR を入れた時点で、**窓ができたのは JWKS だけ**だった。SAML の IdP メタデータは
`active_signing_key()` から `KeyDescriptor` を 1 本しか出しておらず、**SAML SP からは署名が
切り替わる瞬間に証明書が入れ替わって見える**。OIDC RP のために無くした断絶が、そのまま
SAML 側に残っていた（`docs/OPERATIONS.md` は「連携先」に窓を約束する書き方なので、記述と実態も
ずれていた）。

### 決定

**`jwks()` と同じ集合を `KeyDescriptor` として並べる。** SAML 2.0 のメタデータは `use="signing"` の
`KeyDescriptor` を複数持てるので、仕様上の障害は無い。片方だけ古くならないよう、出所も
`jwks()` に揃える。

**署名中の鍵を先頭に置く。** `list_published()` の並びは公開順（`created_at DESC`）なので、
本 ADR の下では**まだ署名していない後継鍵が先頭に来る**。SP の実装には先頭の `KeyDescriptor` だけを
読むものがあり、そのままだと使われていない鍵を掴ませることになる。並べ替えは api 側の責務とし、
`build_idp_metadata_xml` は渡された順をそのまま出す（domain は「どれが署名中か」を知らない）。

署名中の鍵が引けないときは**並べ替えないだけで公開は続ける**。検証に使える鍵がメタデータから
消えるほうが困る。

### アサーションに `KeyInfo` を載せる

**どの鍵で署名したかを、アサーション自身が名乗る。** SAML には JWT の `kid` にあたる標準の印が
無いため、複数の `KeyDescriptor` を並べた瞬間に「SP はどれで検証すべきか」が曖昧になる。
`KeyInfo/KeyValue` がその役目を果たす。

従来は「`KeyInfo` は含めない（SP は取り込んだ IdP メタデータの鍵で検証する）」としていたが、
その前提は**鍵が 1 本しか載っていないとき**にしか成り立たない。複数並べる以上、名乗るのが筋である。
Entra ID など、複数の署名証明書を公開する IdP も同じ形を採る。

`KeyInfo` は `SignedInfo` の外（署名対象ではない）なので、載せても署名計算は変わらない。値の描画は
メタデータと同じ `IdpSigningKey::to_key_value` を使う —— **別々に書くと、SP が「メタデータで受け
取った鍵」と「アサーションが名乗る鍵」を突き合わせられない形にいつでもずれ得る**。

### SP 側の互換性

**複数の `KeyDescriptor` を並べること自体は標準的である。** Entra ID の公開メタデータは
`use="signing"` を 5 本並べている（2026-08-28 に実測）。特殊なことはしていない。

順序を「署名中が先頭」にするのは、`KeyInfo` を読まない SP への保険である。読む SP には順序は
関係しない。**本決定の時点で登録済みの SAML SP は 0 件**（prod で確認）。
