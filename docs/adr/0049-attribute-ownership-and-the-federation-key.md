# ADR-0049: IdP とアプリの境界 —— 属性の持ち主・結び付けの鍵・秘密の置き場所

- Status: Accepted
- Date: 2026-09-13
- 関連: `docs/adr/0009-multi-tenant-architecture.md` §2（所属元テナントは変更不可）、
  `docs/adr/0024-backchannel-logout-sid-and-delivery-queue.md`（停止の伝播）、
  `docs/adr/0025-login-identifier-registry.md`（ログイン識別子の登録簿。AP8）、
  `docs/adr/0033-resource-server-authorization-belongs-to-the-application.md`（業務権限は配らない）、
  `docs/adr/0042-tokens-carry-an-audience-not-a-vocabulary.md`（宛名だけを刻む）、
  `docs/adr/0043-authentication-strength-is-two-reserved-words.md`（`acr` / `amr`）、
  `docs/adr/0040-passkey-on-logins-outside-the-authorization-flow.md`（直接ログインのパスキー）

## 背景

RP を 1 つ足すたびに、同じところで手が止まる。

> ユーザー ID・ユーザー名・表示名・ユニーク ID・パスワード。このうち IdP が持つのはどれで、
> アプリが持つのはどれで、連携で渡すのはどれなのか。

この 5 つを**並列に並べているかぎり決まらない**。並んでいるように見えて、変わる速さも、
秘密かどうかも、誰の持ち物かも違うからである。`users.preferred_username`（人が打つ値）と
`users.sub`（機械が使う値）はどちらも「ユーザーを指す 1 つの文字列」に見えるが、前者は改名で
変わる前提の値で、後者は一生変わらない値である。取り違えると、**改名した利用者が RP 側で
別人になる**。

決まっていないので、RP は各自で決めてきた。その結果が**同じ IdP に繋がる 9 つのアプリが、
少しずつ違う作りになっている**という現状である。本 ADR は先に**理想像**を書き、
そのあとに**実測したギャップ**を置く。理想像は現状に引きずられずに書く。

## 決定（理想像）

### 原則

1. **1 つの事実に持ち主は 1 人。** 同じ属性を 2 か所で編集できる形を作らない。
2. **鍵は変わらないものだけ。** 人が打つ値・人が読む値を鍵にしない。
3. **秘密は 1 か所。** 認証の証拠が 2 か所にあるなら、それは 2 つの認証系である。
4. **正本の変化は届く。** 写しを持つなら、更新される経路と一緒に持つ。
5. **止めたら届く。** 止めたことが伝わらない連携は、止められていない。

### I1. 属性は 5 つの役割に分け、役割ごとに正本を 1 つへ決める

| 役割 | 実体 | 変わるか | 正本 | RP の持ち方 |
|---|---|---|---|---|
| 不変の識別子 | `sub`（UUID） | **変わらない** | IdP | `iss` と対で保存する |
| ログイン識別子 | ユーザー名・メール・電話・社員番号 | 変わる | IdP | **持たない** |
| 認証の証拠 | パスワード / パスキー / TOTP | — | **IdP のみ** | **持たない** |
| プロフィール | 表示名・メール・言語・配色 | 変わる | IdP | 表示用の**写し**（読むだけ） |
| 認可 | ロール・権限 | 変わる | **RP** | RP が持つ（ADR-0033） |

迷ったときは「人が打つ値か、機械が使う値か」で切る。人が打つ値は変わるので鍵にできず、
機械が使う値は変わらないので表示に使えない。

### I2. 結び付けの鍵は `(iss, sub)` の対。RP の内部 id は自前に採番する

`sub` 単独では足りない。issuer はテナントごとに `<基底>/<tenant_id>` へ分かれるので、
`sub` だけを鍵にすると別テナントの利用者と同じ空間に載る。

```
issuer   PK
subject  PK
user_id  FK   -- RP の内部 id。★ 一意制約を置かない（1 人が複数の IdP 口座を持てる）
linked_at, last_login_at
```

`sub` を RP の主キーに流用しない。流用すると、外部 IdP の追加や IdP の載せ替えのたびに
全テーブルの外部キーが動く。

### I3. 認証の証拠は IdP に一元化する。RP は 1 本も持たない

パスワードも、TOTP も、パスキーも、RP 側に置かない。**RP が第二要素を持つと、それは
IdP の認証ポリシーと無関係に効く別の認証系になる** —— IdP 側で MFA を必須にしても
RP 側の口が素通しなら意味が無く、解除も棚卸しも 2 系統になる。

例外は **IdP が落ちたときの緊急口座（break-glass）だけ**で、次を満たす場合に限る。

- アプリごとに 1 口座
- 使用が監査に残り、通知が飛ぶ
- 通常のログイン画面からは見えない

### I4. 「ローカル認証が無い」をデータで表現できる形にする

RP がローカル口座を持たないなら、次のどちらかにする。

- `password_hash` を NULL 許容にし、**NULL = ローカル認証不可**とする
- パスワードを `users` の列として持たず、`credentials`（種別 + 値）として外に出す

**ランダム値で埋めない。** 動きはするが、「パスワードが無い」と「誰も知らないパスワードが
ある」が区別できず、設定画面に変更の導線が出る・リセットを通すと実質ローカル認証が生える・
監査で入れる手段が読めない、という歪みが出る。

### I5. プロフィールの写しはログインのたびに上書きし、RP では編集させない

更新は ID トークンの内容で上書きするだけでよく、`/userinfo` を都度叩く必要はない。
RP の画面で写しを編集させないこと —— 編集させると、どちらが正本か分からなくなる。

### I6. 権限は RP が持つ。IdP は配らない

ADR-0033 のとおり。IdP 由来のグループでロールを決める形を取るなら、**IdP がその
クレームを実際に発行していること**が前提である。発行していない値の対応表は、
設定として存在するのに一度も効かない。

### I7. 利用者を止めたら RP に届く

3 つで塞ぐ。どれか 1 つでは足りない。

- **back-channel logout の受け口**（`sid` でセッションを落とす。ADR-0024）
- **アクセストークンを短命にする**（受け口が落ちていたときの上限時間になる）
- **定期照合**（RP の `last_login_at` と IdP の利用者一覧を突き合わせる）

### I8. RP は認証の強度を要求し、戻りを確かめる

`acr_values` を送り、返ってきた `acr` が要求を満たしているか RP 側で照合する。
**要求したら確かめる。確かめないなら要求しない。** `amr` は監査と表示だけに使う
（ADR-0043）。

### I9. 結び付けは本人の操作。自動リンクは意味が両側で一致しているときだけ

`(iss, sub)` が未登録で同じメールアドレスのローカル口座があるとき、黙って結び付けない。
結び付けは「本人がログイン済みの状態で、設定画面から連携する」経路に限る。

自動リンクを選ぶなら、条件に使う属性の意味が**IdP 側と RP 側で一致していること**を
確かめる。`email_verified` を条件にするなら、その値が IdP でどう立つのかまで見る。

### I10. 識別子は再利用しない

無効化した識別子の行は残す。削除すると同じ値を別人が登録でき、**無効化した識別子の宛先が
黙って変わる**。

## 現状とのギャップ（2026-09-13 実測）

対象は `git.nolumia.com` に在る RP 9 本と assay 本体。**この節は時点の記録であり、
古くなる前提である**（理想像のほうは古くならない）。

### 全体像

| | I3 認証は IdP だけ | I4 パスワード無しを表現 | I5 写しの更新 | I7 停止が届く | I8 acr の照合 |
|---|---|---|---|---|---|
| fastapitemplate | ✗ | ✗ | ✗ | ✗ | ✓ |
| mp3play | ✗ | ✗ | ✗ | ✗ | ✓ |
| nolumiadeck | ✗ | ✗ | ✗ | ✗ | ✓ |
| nolumiawiki | ✗ | ✗ | ✗ | ✗ | ✗ |
| rewardpointsweb | ✗ | ✗ | ✗ | ✗ | ✗ |
| blobshare | ✗ | ✗ | ✗ | ✗ | ✗ |
| photonest | ✗ | ✗ | ✗ | ✗ | ✗ |
| codelab-panel | — | — | — | ✗ | ✗ |
| vikunja-fork | ✗ | — | — | ✗ | ✗ |

I1・I2・I10 は**おおむね満たしている**。federation を持つ 8 本はすべて
`(issuer, subject)` を鍵にしており、`sub` を RP の主キーへ流用したものは無い。

ただし `vikunja-fork` だけは鍵を**独立した表ではなく `users` 行の列**として持つ
（`Issuer` / `Subject`）。1 利用者に 1 つの発行元しか結び付かないので、
ローカル口座と SSO の併存も、IdP の載せ替えも表現できない。上流の実装なので
本 ADR の対象外とするが、**写してよい形ではない。**

### G1. RP が独自の認証スタックを丸ごと持っている（I3。最大のギャップ）

`blobshare` / `fastapitemplate` / `mp3play` / `nolumiadeck` / `nolumiawiki` /
`rewardpointsweb` に `account_security` コンテキスト（パスワード + TOTP + パスキー +
第二要素の検証）があり、`photonest` には `totp` がある。**assay の認証系と並列に、
アプリごとの認証系が 7 つ動いている。**

影響は「二重持ち」で済まない。assay の認証ポリシーで `require_mfa` を掛けても、
RP 側のローカルログインには一切掛からない。パスキーの解除（MT21）も assay の分しか
効かない。**利用者が「入れる手段」の一覧が、どこにも無い。**

直し方は RP ごとに 2 通りある。SSO 専用にするなら `account_security` を落とす
（break-glass は I3 の条件で 1 口座だけ残す）。ローカル口座を意図して持つなら、
その旨を ADR に書いて、認証系が 2 つあることを前提にした運用（棚卸し・MFA 強制）を
RP 側でも用意する。**いまはどちらとも決めていない状態が既定になっている。**

### G2. `password_hash` が全アプリで NOT NULL（I4）

7 本すべてで `nullable=False`。nolumiawiki は SSO 利用者に
`secrets.token_urlsafe(48)` のハッシュを入れている。

nullable へ移すときは、**既存のランダム値を NULL へ落とす**こと。残したまま列だけ
緩めると、パスワードリセットを通した利用者にローカル認証が生える。

### G3. 停止が届かない（I7）。送り手はあるが受け手が 0

assay は `BackchannelLogoutDeliveryService`（配信キュー付き。ADR-0024）を持っている。
一方、**受け口を実装した RP は 1 本も無い**。9 本を走査して、`backchannel` に
当たったのは fastapitemplate の設定コメント 1 行だけだった。

いま利用者を止めても、RP のセッションはそれぞれの寿命が尽きるまで生きている。
**3 つのうち 1 つも塞がっていない**（定期照合も未実装）。

### G4. プロフィールの写しが初回以降更新されない（I5）

`FederatedUserDirectory` の口は `find_by_id` / `find_by_email` / `provision` /
`apply_roles` の 4 つで、**プロフィールを更新する口が存在しない**。写しは `provision`
した一度だけ書かれる。assay で改名・メール変更をしても RP の表示は永久に古いままになる。

`ResolveFederatedAccount._known_account` がログインのたびに行うのは
`identities.touch()` とロール同期だけである。ここに写しの上書きを足すのが最短である。

### G5. email が無いと SSO が成立しない（I1 の副作用）

`ClaimsMapping.apply` は `email` が空なら `SsoEmailMissingError` で落ちる。理想では
email は鍵ではないので**任意**でよいはずだが、実装は必須にしている。結び付けの初回に
email を使う設計（G6）の帰結であり、G6 を直すとここも緩められる。

### G6. email の自動リンクが既定で有効、かつ前提が IdP 側と食い違っている（I9）

`ProvisioningPolicy.link_by_email` の既定は `True`。条件は `user.email_verified` で、
コメントには「IdP が検証していないアドレスで寄せると、相手のアドレスを名乗るだけで
他人のアカウントを乗っ取れる」と正しく書いてある。

**問題は、assay の `email_verified` が RP の期待する意味ではないことである。**
この値が `true` になる経路は自己登録の確認メールだけで、**管理者によるメール変更
（MT25）はこの値を維持する**（`update_profile` は `email_verified` を触らない）。
管理者がログイン識別子としてメールを足すときも所有確認は行わない（ADR-0025）。

つまり assay の `email_verified` は「本人が所有を証明した」ではなく
**「テナント管理者がそう主張している」**である。これは assay 側の決定として筋が通って
いるが、RP 側は前者の意味で読んでいる。**どちらかを直さないと揃わない。** 選択肢は 3 つ。

1. RP 側の `link_by_email` の既定を `False` にする（I9 の本筋。推奨）
2. assay がメール変更時に `email_verified` を落とす（MT25 の運用が変わる）
3. 主張の出どころを分けて載せる（クレームを増やす。いちばん大きい）

### G7. グループによるロール同期が動かない（I6）

`ClaimsMapping.groups_claim`（既定 `groups`）と `roles_for(user.groups)` が在るが、
**assay は `groups` クレームを発行しない**（ADR-0043 が挙げる ID トークンのクレーム一覧に
無い）。`sync_on_login` を真にしても、渡る集合は常に空である。

`apply_roles` は「1 つも当たらないときは触らない」と防いであるため事故にはならないが、
**設定として存在するのに一度も効かない**。RP 側で落とすか、assay 側で発行するかを決める。

### G8. `acr` の照合が 3 本だけ（I8）

`fastapitemplate` / `mp3play` / `nolumiadeck` は `acr_values` を送って戻りを照合する
（`authentication_context.py`）。残りは送っても確かめてもいない。
ADR-0043 で予約語（`urn:assay:ac:mfa` / `urn:assay:ac:single`）を用意した目的が
効いているのは 3 本である。

### G9. codelab-panel が email で認可している（I2）

`auth.py` はセッションに `sub` を持つが、入れるかどうかの判定は
`email.lower() not in ALLOWED_EMAILS` で行っている。**認可の鍵が email になっている。**
このアプリは利用者表を持たない小さな操作盤なので影響範囲は限られるが、
assay 側で管理者がメールを変更すると**黙って締め出される / 黙って入れる**。

### G10. assay 側 —— RP 向けの統合ガイドが無い

`docs/OIDC_INPUT.md` は MVP の設計書で、RP をどう作るかは書いていない。9 本が少しずつ
違う作りになっている原因はここにある。本 ADR の「決定（理想像）」がその出発点になる。

### G11. assay 側 —— 本人がログイン識別子を管理できない（I1 の範囲の話）

追加・無効化はテナント管理者の操作で、本人の導線は用意していない（ADR-0025 の決定）。
組織で配る番号を扱う前提では正しいが、個人が自分でメールや電話を足したい形には
届かない。理想像に反するとまでは言えないので、**現時点では課題として置くだけにする。**

## 付録: assay の現在の仕様（2026-09-13 実測）

理想像との差を読むための下敷きとして、いま assay が何でログインさせ、何を編集させるのかを
書き出しておく。

### ログインに使える値

入力欄は 1 つで、入力の形から候補の種別を組み立てて登録簿を 1 クエリで引く
（`lookup_candidates` → `resolve_login_identifier`）。`users.preferred_username` への
フォールバックは無い（AP15b）—— 残っていると、登録簿で無効化した識別子でも認証が通る。

| 種別 | 既定で使えるか | 正規化 |
|---|---|---|
| ユーザー名（主識別子） | **使える** | 前後の空白を落とし、小文字化 |
| メールアドレス | 管理者が足したときだけ | 小文字化 |
| 電話番号 | 管理者が足したときだけ | 区切りを落とし、先頭の `+` だけ残す |
| 社員番号 | 管理者が足したときだけ | 空白を落とし、大小を無視 |

**1 人に決まらなければ認証しない**（`LoginIdentifierMatch::ambiguous`）。

第一要素はパスワードまたはパスキー（パスキーは認可フロー外の直接ログインでも使える。
ADR-0040）。第二要素は TOTP で、パスキーは単独で `require_mfa` を満たす。外部 IdP 経由の
認証は第二要素として数えない。結果は `acr` として RP へ渡る（ADR-0043）。

### 編集できる範囲

| 属性 | 本人 | テナント管理者 |
|---|---|---|
| `sub` | — | **—（更新経路が無い。不変）** |
| 所属元テナント | — | **—（ADR-0009 §2）** |
| ユーザー名（主識別子） | — | 変更できる（改名。識別子単位の削除は不可） |
| 追加のログイン識別子 | **—（導線を用意しない）** | 追加・無効化できる |
| `email` | — | 変更できる（`email_verified` は維持される。G6） |
| 表示名 `name` | **変更できる**（空で解除） | 変更できる |
| `language` / `theme` | **変更できる** | — |
| パスワード | 変更できる | 再発行のみ（平文は一度だけ返る） |
| TOTP / パスキー | 登録・削除できる | **解除のみ**（MT21） |
| `status` | — | 変更できる |

本人のセルフサービスは**表示名・言語・配色・パスワード・認証器**に閉じている
（`account_profile.rs` が返すのはこの範囲）。

### assay が RP へ渡すもの

| クレーム | 用途 |
|---|---|
| `iss` + `sub` | **結び付けの鍵**。これだけが不変 |
| `preferred_username` / `name` / `email` / `email_verified` | 表示用の写し。scope で制御 |
| `acr` / `amr` | 認証の強度（ADR-0043）。強度の判断は `acr` だけで行う |
| `sid` / `auth_time` | セッションの同一性と鮮度。back-channel logout が使う |

業務上の権限は載らない（ADR-0033）。`groups` も載らない（G7）。

## 直す順序

| 順 | ギャップ | 理由 | 規模 |
|---|---|---|---|
| 1 | G3（停止が届かない） | 止めたはずの利用者が入れる。送り手は既にある | 中（RP ごとに受け口 1 本） |
| 2 | G6（自動リンクの前提のずれ） | 乗っ取りの経路になり得る。既定を倒すだけで塞がる | 小 |
| 3 | G2（パスワード列） | G1 の前提。ここが直らないと SSO 専用を表現できない | 小〜中（移行が要る） |
| 4 | G1（認証スタックの二重化） | 最大だが、アプリごとの方針決めが先に要る | 大 |
| 5 | G4（写しの更新） | 実害は表示だけ。口を 1 つ足すだけで済む | 小 |
| 6 | G7 / G8 / G9 / G5 | いずれも局所的 | 小 |

## 影響

- 新しい RP を足すときの型が決まる。既存で最も理想に近いのは
  `bounded_contexts/identity_federation`（fastapitemplate 系）だが、I3・I4・I5・I7 は
  どの実装も満たしていないので、**既存をそのまま写さないこと。**
- assay 側の実装変更は本 ADR では行わない。G6 の選択肢 2 を選ぶ場合だけ assay が動く。
