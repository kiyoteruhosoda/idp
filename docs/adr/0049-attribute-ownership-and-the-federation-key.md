# ADR-0049: 属性の持ち主は役割で決め、アプリとの結び付けは `(iss, sub)` で行う

- Status: Accepted
- Date: 2026-09-13
- 関連: `docs/adr/0009-multi-tenant-architecture.md` §2（所属元テナントは変更不可）、
  `docs/adr/0025-login-identifier-registry.md`（ログイン識別子の登録簿。AP8）、
  `docs/adr/0033-resource-server-authorization-belongs-to-the-application.md`（業務権限は配らない）、
  `docs/adr/0042-tokens-carry-an-audience-not-a-vocabulary.md`（宛名だけを刻む）、
  `docs/adr/0043-authentication-strength-is-two-reserved-words.md`（`acr` / `amr`）、
  `docs/adr/0040-passkey-on-logins-outside-the-authorization-flow.md`（直接ログインのパスキー）

## 背景

RP を 1 つ足すたびに、同じところで手が止まる。

> ユーザー ID・ユーザー名・表示名・ユニーク ID・パスワード。このうち IdP が持つのはどれで、
> アプリが持つのはどれで、連携で渡すのはどれなのか。

この 5 つを**並列に並べているかぎり決まらない**。並んでいるように見えて、変わる速さも、
秘密かどうかも、誰の持ち物かも違うからである。実際、`users.preferred_username`（人が打つ値）と
`users.sub`（機械が使う値）はどちらも「ユーザーを指す 1 つの文字列」に見えるが、前者は改名で
変わる前提の値で、後者は一生変わらない値である。ここを取り違えると、**改名した利用者が
アプリ側で別人になる**。

もう 1 つ、RP 側で必ず出てくるのがパスワードの二重持ちである。nolumiawiki は
`users.password_hash` が NOT NULL なので、SSO で作られた利用者には
**誰も知らないランダム値のハッシュ**を入れている（`sql_federated_user_directory.py`）。

```python
# パスワード認証の口からは入れない状態にする（``password_hash`` は NOT NULL）。
password_hash=generate_password_hash(secrets.token_urlsafe(48)),
```

意図どおり動いてはいる。しかし**「パスワードが無い」と「誰も知らないパスワードがある」を
データから区別できない。** その結果、設定画面に変更の導線が出る・パスワードリセットを通すと
SSO 専用のはずの口座に実質ローカル認証が生える・監査で「この人はどの手段で入れるのか」を
読めない、という歪みが出る。

これらは個々のアプリの実装判断に見えて、実際には**assay と RP のあいだの契約**が
書かれていないことから来ている。ADR-0033（業務権限は配らない）と ADR-0042（宛名だけを刻む）は
「何を**渡さない**か」を決めたが、「何を**誰が持つ**か」は決めていない。

## 決定

### 1. 属性は 5 つの役割に分け、役割ごとに持ち主を 1 つに決める

| 役割 | 実体 | 変わるか | 正本 | RP の持ち方 |
|---|---|---|---|---|
| 不変の識別子 | `users.sub`（UUID） | **変わらない** | assay | `iss` と対で保存する |
| ログイン識別子 | 登録簿（`user_login_identifiers`） | 変わる | assay | **持たない** |
| 認証の証拠 | `password_hash` / パスキー / TOTP | — | **assay のみ** | **持たない** |
| プロフィール | `name` / `email` / `language` / `theme` | 変わる | assay | 表示用の**写し** |
| 認可 | ロール・権限 | 変わる | **RP** | RP が持つ（ADR-0033） |

役割が決まれば持ち主も決まる。迷ったときは「これは人が打つ値か、機械が使う値か」で切る。
人が打つ値は変わるので鍵にできず、機械が使う値は変わらないので表示に使えない。

### 2. 結び付けの鍵は `(iss, sub)` の対とする

`sub` 単独では足りない。issuer はテナントごとに `<基底>/<tenant_id>` へ分かれるので
（ADR-0009 §6）、`sub` だけを鍵にすると別テナントの利用者と同じ空間に載る。

RP 側の形は次になる（nolumiawiki の `federated_identities` が既にこの形である）。

```
issuer   PK
subject  PK
user_id  FK   -- RP の内部 id。★ 一意制約を置かない（1 人が複数の IdP 口座を持てる）
last_login_at
```

RP の内部 id は RP が自分で採番する。`sub` を主キーに流用しない —— 流用すると、
外部 IdP の追加や IdP の載せ替えのたびに全テーブルの外部キーが動く。

### 3. email を鍵にしない。`email_verified` は本人の証明ではない

email を鍵にできない理由は 3 つある。変わる。使い回される。そして**大小の揺れがある** ——
`users.email` の一意制約は大小を区別するので、`Alice@example.com` と `alice@example.com` は
両方作れる。RP 側で正規化して引くと 1 行に決まらないことがあり、そこで「最初の 1 行」を
返すと、結び付ける相手が実行計画しだいで変わる。

さらに `email_verified` の意味に注意が要る。assay でこの値が `true` になる経路は
**自己登録の確認メール**だけであり、**管理者によるメール変更（MT25）はこの値を維持する**
（`update_profile` は `email_verified` を触らない）。ログイン識別子として管理者が
メールアドレスを足すときも所有確認は行わない（ADR-0025）。これは欠落ではなく決定である
——管理者の割り当てを本人確認の代わりとして受け入れる、という運用を選んでいる。

したがって RP から見た `email_verified` は、**「本人が所有を証明した」ではなく
「assay のテナント管理者がそう主張している」**である。テナントの管理者を信頼するなら
十分だが、**鍵として使ってよいという意味にはならない。**

### 4. RP は認証の証拠を持たない。ローカル認証の有無は明示的に表現する

RP がパスワードのハッシュを持ってよいのは、**その RP が独自のローカル口座を持つと
決めたときだけ**である。持たないなら、次のどちらかで「パスワードが無い」を表現する。

- `password_hash` を NULL 許容にし、**NULL = ローカル認証不可**とする
- パスワードを `users` の列として持たず、`credentials`（種別 + 値）として外に出す。
  SSO も password も「ぶら下がる認証手段の 1 つ」になり、二重持ちではなく併存になる

**ランダム値で埋める形を既定にしない。** 動きはするが、意図が列に残らない。

### 5. RP 側の利用者の行は初回ログインで作る（JIT）

assay で利用者を作った時点で RP 側に行を先回りして作らない。作ると、一度もログインしない
孤児が溜まり、RP が `sub` を先に知る必要も出る。**行は初回ログインで生える**のが正しい向きで、
これは ADR-0038 の「向きで分ける」と同じ話である——assay は ID を**渡す**側であって、
RP のデータを**作る**側ではない。

自動作成するかどうかは RP 側の独立したつまみにする。以前ドメイン制限で持ち主を締め出した
ときも、実際に効いていた関門は許可リストではなく自動作成のフラグだった。

### 6. 既存のローカル口座への自動結び付けはしない

`(iss, sub)` が未登録で、同じメールアドレスのローカル口座が既にあるとき、**黙って結び付けない。**
結び付けは「本人がログイン済みの状態で、設定画面から連携する」経路だけに限る。
自動で結び付ける運用を選ぶなら、`email_verified == true` かつ信頼する issuer に限る、という
条件を RP 側に明示的に書く（決定 3 のとおり、この条件は管理者の主張を信じるという意味になる）。

## この決定から出る帰結

### assay が RP へ渡すもの

| クレーム | 用途 |
|---|---|
| `iss` + `sub` | **結び付けの鍵**。これだけが不変 |
| `preferred_username` / `name` / `email` / `email_verified` | 表示用の写し。scope で制御 |
| `acr` / `amr` | 認証の強度（ADR-0043）。強度の判断は `acr` だけで行う |
| `sid` / `auth_time` | セッションの同一性と鮮度。back-channel logout が使う |

業務上の権限は載らない（ADR-0033）。写しの更新は**ログインのたびに ID トークンの内容で
上書きする**だけでよく、`/userinfo` を都度叩く必要はない。RP の画面でこの写しを
**編集させない**こと——編集させると、どちらが正本か分からなくなる。

### ログインに使える値（何で入るか）

入力欄は 1 つで、入力の形から候補の種別を組み立てて登録簿を 1 クエリで引く
（`lookup_candidates` → `resolve_login_identifier`）。`users` 側へのフォールバックは無い
（AP15b）——残っていると、登録簿で無効化した識別子でも認証が通ってしまう。

| 種別 | 既定で使えるか | 正規化 |
|---|---|---|
| ユーザー名（主識別子） | **使える** | 前後の空白を落とし、小文字化 |
| メールアドレス | 管理者が足したときだけ | 小文字化 |
| 電話番号 | 管理者が足したときだけ | 区切りを落とし、先頭の `+` だけ残す |
| 社員番号 | 管理者が足したときだけ | 空白を落とし、大小を無視 |

**1 つに決まらなければ認証しない**（`LoginIdentifierMatch::ambiguous`）。

第一要素はパスワードまたはパスキー。パスキーは認可フロー外の直接ログイン
（ポータル・管理コンソール）でも使える（ADR-0040）。第二要素は TOTP で、パスキーは
単独で `require_mfa` を満たす。外部 IdP 経由の認証は**第二要素として数えない**。

### 編集できる範囲（誰が何を変えられるか）

| 属性 | 本人 | テナント管理者 |
|---|---|---|
| `sub` | — | **—（経路が無い。不変）** |
| 所属元テナント | — | **—（ADR-0009 §2）** |
| ユーザー名（主識別子） | — | 変更できる（改名。識別子単位の削除は不可） |
| 追加のログイン識別子 | **—（導線を用意しない）** | 追加・無効化できる |
| `email` | — | 変更できる（`email_verified` は維持される） |
| 表示名 `name` | **変更できる**（空で解除） | 変更できる |
| `language` / `theme` | **変更できる** | — |
| パスワード | 変更できる | 再発行のみ（平文は一度だけ返る） |
| TOTP / パスキー | 登録・削除できる | **解除のみ**（MT21） |
| `status` | — | 変更できる |

本人のセルフサービスは**表示名・言語・配色・パスワード・認証器**に閉じている。
本人が自分のログイン識別子を増やせないのは決定であって未実装ではない（ADR-0025）——
ログイン欄に一致する値を増やす操作は、他人に解決される値を作り得るため管理者の操作とする。

## 影響

- 新しい RP を足すときの型が決まる。実装済みの参照は nolumiawiki の
  `bounded_contexts/identity_federation`（`federated_identities` + JIT プロビジョニング）。
- assay 側の変更は無い。本 ADR は既にある実装を契約として書き起こしたものである。

## 残る課題

1. **nolumiawiki の `users.password_hash` が NOT NULL**（決定 4 に反する）。
   nullable へ移し、NULL をローカル認証不可として扱う。移行中は既存のランダム値を
   NULL へ落とす必要がある——**ランダム値のまま残すと、パスワードリセットを通した利用者に
   ローカル認証が生える。**
2. **停止の伝播。** assay で `status` を止めても RP のセッションは生き残る。
   back-channel logout（ADR-0024）・アクセストークンの寿命・RP 側の `last_login_at` による
   棚卸しの 3 つで塞ぐ。現状どの RP がどこまで塞げているかは未確認。
