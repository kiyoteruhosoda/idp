# ADR-0058: 設定はテナントが決める。全体は既定を配る

- Status: Accepted
- Date: 2026-09-16
- Revised: 2026-09-16 — §13 を追加（消費側を作り替えたときに決めた「**どのテナントの値で動くか**」）。

  `docs/adr/0056-access-tokens-live-for-five-minutes.md`（アクセストークンの寿命）、

## 背景

assay の設定は、いま **IdP 全体で 1 枚しか無い**。`system_settings` の主キーは `setting_key` だけで、
⚠ **テナント列を持たない**（migration 0003 の冒頭に「テナント列は持たない。システム設定は IdP 全体に
一律適用する」と明記されている）。結果、パスワードの最小長もロックアウトの回数もセッションの寿命も、
**全テナントで同じ値**になる。

これは ADR-0009 の建て付けと食い違っている。ADR-0009 は「**各テナントは独立した管理境界**で、root は
テナントを作れるが**中は操作できない**」と決めた（Entra ID 型）。ところが**設定だけは root が全テナントへ
一方的に効かせている**。⚠ **テナント管理者は、自分のテナントのパスワードポリシーもロックアウトも
決められない。**

受け皿の形には前例がある。認証ポリシー（`authentication_policies(tenant_id, policy_code)`）も外部 IdP も
アプリも、すでにテナント単位で持っている。**新しい概念を持ち込む話ではなく、全体にしか無い設定を
その形へ降ろす話である。**

いま入れるのが安い。本番のテナントは **ROOT と kyon の 2 つだけ**で（2026-09-15 実測）、どちらも既定に
従っている。⚠ **降ろしても挙動が 1 つも変わらない。** テナントが増えてからだと、テナントごとに違う値を
抱えたまま作り替えることになる。

## 決定

### 1. 原則 —— 全体に 1 つ無いと壊れるもの以外は、テナントが決める

判定は 1 つだけである。⚠ **「IdP 全体に 1 つ無いと壊れるか」。** 壊れないなら降ろす。

⚠ **「root が握っていたいか」で分けない。** それは ADR-0009 が否定した形であり、この判定を持ち込むと
「全体で持つ理由」が毎回作れてしまう。

### 2. 解決順は「テナント ＞ 全体 ＞ 組み込み既定」

- **テナントの値**（`tenant_settings`）——そのテナントにだけ効く
- **全体の値**（`system_settings` / 環境変数）——テナントに行が無いときの既定
- **組み込み既定**（`RUNTIME_SETTING_DEFINITIONS` の `default_value`）

⚠ **テナントに行が無いことが「全体に従う」である。既定値の写しをテナントへ配らない。** 写すと、全体の値を
変えてもそのテナントだけ追随しなくなり、しかも**画面上は同じ値に見える**（差が見えるのは全体を変えた
あとだけで、そのときにはもう原因を思い出せない）。

### 3. 単位はキー定義が持つ

`RUNTIME_SETTING_DEFINITIONS`（`crates/core/src/domain/system_setting.rs`）に **単位（scope）** を足す
——「全体のみ」か「テナントで上書きできる」か。ADR-0010 の 3 状態（`BUILTIN` / `ENV_LOCKED` /
`DB_MANAGED`）は**出所**の軸で、単位はそれと直交する 4 つ目の軸である。状態の 3 区分は動かさない。

⚠ **定義に無いキーはテナントの表に書けない。** 書けると、綴り違いが「黙って無視される行」として残る
——保存はできるのに一生効かない設定が画面に並ぶ。

### 4. 降ろすキー（テナントが決める）

| まとまり | キー |
|---|---|
| パスワードポリシー | `PASSWORD_MIN_LENGTH` / `PASSWORD_HISTORY_COUNT` / `PASSWORD_MAX_AGE_DAYS` / `PASSWORD_BREACH_CHECK_ENABLED` |
| ロックアウト | `LOGIN_MAX_FAILED_ATTEMPTS` / `LOGIN_LOCK_DURATION_SECS` / `LOGIN_MAX_LOCK_DURATION_SECS` |
| セッション | `SSO_IDLE_TTL_SECS` / `SSO_ABSOLUTE_TTL_SECS` / `STEP_UP_MAX_AGE_SECS` |
| リンクの有効期間 | `INVITATION_TTL_SECS` / `PASSWORD_RESET_TTL_SECS` / `EMAIL_VERIFICATION_TTL_SECS` / `PASSWORD_RESET_CONSOLE_LINK_ENABLED` |
| ポリシーの既定 | `AUTH_POLICY_DEFAULT_EFFECT` |
| アプリ割り当ての強制 | `APPLICATION_ASSIGNMENT_ENFORCEMENT` |
| 既定言語 | （新設。いまはキーですら無く `Ja` がコードに直書き） |
| メールの経路 | SMTP 一式（§8） |

`APPLICATION_ASSIGNMENT_ENFORCEMENT` が**いちばん効く**。名簿が整ったテナントから `enforce` へ倒せる
——全体 1 枚だと「**全テナントの名簿が揃うまで倒せない**」。

### 5. 全体のまま（降ろすと壊れる）

| キー | 壊れ方 |
|---|---|
| `ISSUER` / 署名鍵（`signing_keys`）/ `KEY_ROTATION_*` | 発行者と鍵は**テナント軸を持たない**（`signing_keys` の主キーは `kid` だけ）。テナント別にすると JWKS・ディスカバリ・`iss` 検証・鍵の入れ替えが全部テナント軸を要求する |
| `COOKIE_SECURE` / `COOKIE_DOMAIN` / `HSTS_MAX_AGE` | ⚠ **発行と失効で同じ値であることが安全の根拠**（ADR-0014 §1）。テナント別にすると**消せない Cookie** が生まれる |
| `PUBLIC_WEB_BASE_URL` | **WebAuthn の RP ID の導出元**（ADR-0019）。テナント別にするとパスキーが別物になる |
| `AUTH_SESSION_TTL_SECS` | DB のレコードの寿命（api）と Cookie の `Max-Age`（web）が同じでないとログインが静かに進まなくなる（ADR-0013） |
| トークンの寿命（§7） | 失効の効きの上限。§7 で改めて決める |
| `BIND_ADDR` / `DATABASE_URL` / `KEY_ENCRYPTION_KEY` / `CSRF_SECRET` / `INTERNAL_SERVICE_TOKEN` / `LOG_FORMAT` | プロセスと DB の配置。**テナントを解決する前に要る** |
| レート制限 / CORS / 各キャッシュ TTL / ログ保持日数 / GC 間隔 / `CLOCK_SKEW_SECS` / バックチャネル配送の再試行 | プロセス 1 つの振る舞いであって、テナントの判断ではない |

### 6. 床を持たない（テナントは自由に決める）

全体の値は**既定であって下限ではない**。テナントは自分の値を緩くも厳しくもできる。

ADR-0009 の独立モデルに忠実であることを採る ——root がテナントの中の値に口を出さない。

⚠ **ただし、見えなくはしない。** 全体の設定画面から、そのキーについて「**いま既定から外れている
テナント**」と「**この値に従っているテナントの件数**」を読めるようにする。干渉はしないが、**変更の影響
範囲が読めないまま全体の値を動かす**状態も作らない。

### 7. トークンの寿命はテナントが変えられない

`ACCESS_TOKEN_TTL_SECS` / `ID_TOKEN_TTL_SECS` / `REFRESH_TOKEN_TTL_SECS` /
`MANAGEMENT_TOKEN_TTL_SECS` / `AUTHORIZATION_CODE_TTL_SECS` は**全体のまま**にする。

- ADR-0056 は 300 秒という短さ自体を「**権限を剥奪してから効くまでの上限**」の根拠にした。テナントが
  緩められると、その上限が**テナントの数だけ**できる
- ⚠ **アクセストークンの寿命は機械のトークンにも乗る**（`client_credentials`。ADR-0056）。緩める口を
  作ると、人ではなく機械のトークンが長生きする
- 緩める必要が**いま無い**。要求が出てから、そのとき何を守るのかと一緒に決める

### 8. SMTP はテナントごとに持てるようにする（ADR-0051 §3 を覆す）

ADR-0051 §3 は「この 2 つ（`idp.smtp:read` / `idp.smtp:write`）は root scope でしか持てない」と決めた。
理由は 1 つで、**`system_settings` がテナント列を持たない全体の表だから**である ——テナントの中で
配れるようにすると、あるテナントの管理者が**全テナントのメール経路**を変えられてしまう。

⚠ **本 ADR でその理由自体が消える。** テナント別の受け皿ができれば、テナントの管理者が触れるのは
**自分のテナントの経路だけ**になる。したがって §3 を覆す。

- **テナントの SMTP** —— `tenant_settings` に持つ。口は自テナント宛て（`/{tenant_id}/admin/settings/smtp`）
- **全体の SMTP** —— `system_settings` のまま。口も今までどおり（`/{tenant_id}/admin/system-settings/smtp`）で、
  ⚠ **要求テナントが root でなければ 403 のまま**（ADR-0051 §3 の二重防御のうち、使う側は残す）
- `idp.smtp:read` / `:write` を `ROOT_SCOPED_CODES` から外す（テナントの中でも付与できる）
- ⚠ **`TENANT_MANAGEMENT_CODES` には入れない。** `idp.tenant.admin` が SMTP を含意すると、**root の
  テナント管理者が全体のメール経路へ届く**。ADR-0051 が明示的に断った形なので、付与は引き続き
  明示的な 1 枚とする

覆さないもの: ADR-0051 §1（SMTP だけを細粒度コードで開ける）・§2（口と応答の型を分ける）・
パスワードの平文を返さないこと。

#### ⚠ メールの経路は「塊」で解決する。キー単位で全体へ落とさない

テナントに 1 つでも SMTP の行があれば、**そのテナントの塊だけ**を使う（欠けている項目は空として扱い、
全体の値で埋めない）。テナントに行が無ければ、全体の塊をそのまま使う。

⚠ **キー単位で落とすと、全体の SMTP パスワードを盗める。** テナントが `smtp.host` と `smtp.username` だけを
自分のサーバに設定し、`smtp.password` を未設定のまま全体から借りると、**全体の資格情報がそのテナントの
サーバへ送られる**。秘密の落とし先を作らないことが、この作りの要である。

「設定済みか」の判定は全体と同じ規則にする（`smtp.host` が空でなければ設定済み）。

### 9. 反映は「参照のたびに引く」。`Config` 全体のリロードへは進まない

ADR-0014 は**ホットリロードを入れない**と決め、同時に「ホットにしたい設定が出たら、まず**そのキーだけ**
`restart_required = false` にできるか（毎回 DB を読める設計か）を**キー単位で**検討する。`Config` 全体の
リロードへは進まない」という線を残した。

降ろすキーは**この線に乗せる**。テナントごとに違う値は、そもそも起動時に 1 つ解決して配る形では
表せない ——「テナントを解決してから引く」以外に道が無い。SMTP が既にこの形である。

⚠ **`Config` 全体のリロードへは進まない。** 全体のまま残すキー（§5）は今までどおり
`restart_required = true` で、反映は api → web の順の再起動が担う。

### 10. web へは値ではなく「解決済みの結果」を渡す

ADR-0013 は「web は DB を持てないので、api の**起動時スナップショット**を 1 本だけ受け取る」と決めた。
テナントごとに違う値は、1 本のスナップショットでは表せない。

⚠ **降ろすキーを `shared_with_web` に載せない。** 2026-09-16 に `origin/main` を実測したところ、
web は次のようになっていた。

| キー | web での実態 | どうするか |
|---|---|---|
| `AUTH_POLICY_DEFAULT_EFFECT` | **表示にしか使っていない**（判定は api が行う。`admin_authentication_policies_console.rs` の 2 か所） | `shared_with_web` を外し、**api の応答**（認証ポリシー一覧）に載せて描く |
| `APPLICATION_ASSIGNMENT_ENFORCEMENT` | ⚠ **web のコードから一度も参照されていない**（`shared_with_web: true` だけが立っている） | `shared_with_web` を **false** にする |
| 既定言語（新設） | 言語の決定は web の責務（`CLAUDE.md`「国際化」） | 画面を描くときに**既に引いているテナントの応答**へ載せる。⚠ 起動時スナップショットには載せない |

結果として、**ADR-0013 のスナップショットの不変条件はそのまま保たれる** ——共有されるキーは全部
「全体で 1 つ」のままである。

### 11. 権限

- テナントの設定 —— `idp.tenant-settings:read` / `idp.tenant-settings:write`（既存。`idp.tenant.admin` が含意する）
- テナントの SMTP —— `idp.smtp:read` / `:write`（§8）
- 全体の設定 —— ⚠ **`idp.system.admin` の完全一致のまま**（ADR-0037 §4 は動かさない）

⚠ **テナントの権限で全体のキーが開かないこと。** 付与の側と使う側の二重で止める（ADR-0051 と同じ作り）。

### 12. 移行は「行を 1 つも作らない」

`tenant_settings` は**空**で入る。全テナントが全体の既定に従う状態であり、⚠ **挙動は 1 つも変わらない。**
変わったなら、それは受け皿ではなく**既定値がずれている**ということで、そのときは受け皿ではなく既定値を
疑う。

### 13. どのテナントの値で動くか —— 状態を持つ行の持ち主で決める

「テナントの値」と言っても、1 つの要求には**テナントが 2 つ**現れうる。URL のテナント（ゲストなら
参加先）と、利用者の所属元である。判定は 1 つで、⚠ **その値で動く状態がどの行にあるか**で決める。

| まとまり | 引くテナント | 状態の在りか |
|---|---|---|
| パスワードポリシー・ロックアウト | 利用者の**所属元** | パスワードと失敗回数は `users` の行にあり、所属元だけが管理する（ADR-0009 §2） |
| SSO セッションの寿命・step-up の間隔 | 利用者の**所属元** | `sso_sessions` はテナント列を持たず、ホスト単位で全テナントに共有される |
| パスワード再設定・メール検証のリンク | 利用者の**所属元** | リンクは所属元を指し、消費も所属元でしか通らない（MT26） |
| 招待のリンク | 招待した**参加先** | 招待は参加先の `tenant_memberships` の行である |

- ⚠ **URL のテナントで決めない。** ゲストが参加先の画面から入るたびに閾値や寿命が変わり、同じ
  失敗回数・同じ SSO セッションが入口によって別の規則で数えられる。とくに SSO セッションは、
  確立したテナントと延長したテナントで寿命が食い違う
- ⚠ **発行と検証で同じテナントを引く。** リンクの期限は発行時に `expires_at` として保存するので、
  検証側は値を引き直さない。SSO セッションの idle 延長は、確立と同じく所属元の値で延ばす
- web が SSO Cookie の `Max-Age` に使う秒数は、⚠ **確立したセッションそのもの**（絶対期限 − 確立時刻）
  から採る。応答を組み立てる側で設定を引き直すと、値を変えた瞬間に Cookie とセッションがずれる
- 再設定リンクのコンソール出力（`PASSWORD_RESET_CONSOLE_LINK_ENABLED`）だけは、利用者を解決する
  **前**に可否を決める必要がある（アカウントに依らない `Unavailable` を返すため）。要求テナントで
  可否を見たうえで、解決した利用者の所属元でも許されていなければ出さない（どちらかが塞げば塞ぐ）

#### テナントが決まらない場面は無い

§4 の 14 キーの消費側を洗い出した結果、⚠ **テナントを持たずに値を引く経路は 1 つも無かった**
（どの経路も利用者か招待の行に辿り着いてから値を使う）。そのため解決器は `TenantId` を**必須の引数**に
して、「テナント無しで全体へ落とす」入口をそもそも作っていない。黙って全体へ落ちる経路は、型の上で
書けない。テナントを持たない経路でこれらの値が要る日が来たら、そのときに落とす口とログを足す。

## 既存の ADR の再判断

⚠ **黙って上書きしない。** 本 ADR が触る決定を明記する。

| ADR | 何と食い違うか | どう扱うか |
|---|---|---|
| ADR-0009 | 各テナントは独立した管理境界。root は中を操作できない | ✅ **本 ADR はこれに寄せる側。** §6 で床を持たないことも、この独立性に従った結果である |
| ADR-0010 | 設定の出所を `BUILTIN` / `ENV_LOCKED` / `DB_MANAGED` の 3 状態で持つ | **4 つ目の軸（単位）を足す。** 状態の 3 区分はそのまま |
| ADR-0013 | web は api の起動時スナップショットを 1 本もらうだけ | ✅ **覆さない。** §10 のとおり、降ろすキーはそもそも共有しない |
| ADR-0014 | ホットリロードは入れない | ✅ **覆さない。** §9 のとおり「キー単位で `restart_required = false` にできるか検討する」に乗る |
| ADR-0037 §4 | システム管理操作は細粒度へ分割しない | ✅ 変えない。全体の設定は `idp.system.admin` の完全一致のまま |
| ADR-0051 §3 | `idp.smtp:*` は root scope でしか持てない | ⚠ **覆す**（§8）。根拠だった「テナント列が無い」が本 ADR で消えるため。§1・§2 は維持 |
| ADR-0056 | アクセストークンは 300 秒 | ✅ 覆さない。§7 でテナントは変えられないと決めた |

## 影響

- **テナント管理者**は、自分のテナントのパスワードポリシー・ロックアウト・セッションの寿命・招待や
  再設定のリンクの有効期間・ポリシーの既定・アプリ割り当ての強制・既定言語・メールの経路を決められる
- **降ろしたキーは再起動なしで効く。** 逆に、⚠ **再起動しないと効かないなら、その口はまだ `Config` を
  読んでいる**（切り分けの目印になる）
- **秘密の保管場所がテナントの数だけ増える**（SMTP）。暗号化は `system_settings` と同じ
  AES-256-GCM で、参照 API は平文を返さない
- ⚠ **ロックアウトのカウンタはプロセス内のメモリのままである**（`InMemoryLoginRateLimiter`）。閾値は
  テナント別になるが、カウンタ自体は単一インスタンス前提という制約は変わらない

## 代替案

- **`tenants` に列を足す（採らない）** —— 型は堅いが、降ろすキーは 20 以上あり **20 回以上 `ALTER TABLE`**
  することになる。型が緩む分はキー定義（§3）で縛れる
- **全体の値を床にする（採らない）** —— 緩められない安心と引き換えに、root がテナントの中へ口を出す形に
  なる。ADR-0009 の再判断が要るうえ、「厳しくだけできる」の向き（大きいほど厳しい設定と、小さいほど
  厳しい設定が混在する）をキーごとに定義して回ることになる
- **テナントごとに `Config` を作って持つ（採らない）** —— 起動時解決の形を保ったままテナント別にする案。
  テナントが増えるたびにプロセスの持ち物が増え、設定の変更が**どのテナントで**反映済みかを持ち回る
  ことになる。参照のたびに引く（§9）ほうが状態が少ない
