# ADR-0026: パスワードポリシーの拡張（漏えい検出・再利用禁止・有効期限）

- 日付: 2026-08-10
- 状態: 採用
- 関連: ユーザー認証・認証ポリシー仕様書 §11.2、ADR-0009 §5（強制パスワード変更）、
  ADR-0020（認証ポリシー）、`docs/Progress.md` AP7

## 背景

パスワードの受け入れ条件は最小・最大文字数だけだった。長さは**入力そのものの形**しか見ておらず、
形が正しくても危険なパスワードを 3 通り取りこぼす。

- **漏えい済みの値。** 公開された資格情報リストに載っている値は、文字数を満たしていても
  クレデンシャルスタッフィングで即座に破られる。長さでは区別できない。
- **元に戻された値。** 侵害を疑って変更を強制しても、直前と同じ値へ戻せるなら要求が意味を持たない。
  「戻された」ことは過去のパスワードを覚えていないと分からない。
- **何年も同じままの値。** いつ設定されたかを持っていないため、経過での交換を促せない。

3 つとも「そのパスワードの**来歴**を見る」要件であり、判定には長さと違って**材料**が要る。

## 決定

### 1. 判定と記録を 1 つのサービスへ集約する

パスワードを設定する経路は 7 つある —— 自己登録、OIDC ログイン中の強制変更、管理コンソールの
強制変更、ポータルの強制変更、セルフサービス変更、パスワードリセット、管理者による再発行。
条件を各経路に書くと、**書き忘れた経路がそのまま抜け穴**になる（しかも抜けているのは
「その経路だけ」なので気付きにくい）。

`application::password_policy::PasswordPolicyService` を唯一の入口とし、各経路は
`validate` → 保存 → `record_change` を呼ぶだけにする。判定そのもの（長さ・期限の算術）は
`domain::password_policy` に置き、材料の取得（DB・外部 API）はサービスが担う。

判定は安い順に見る（長さ → 漏えい → 再利用）。再利用の照合は履歴の件数だけ argon2 を回すため、
長さ不足のような明らかな入力でメモリハード関数を走らせない。

### 2. 有効期限は「ログイン拒否」ではなく「強制変更」として扱う

期限切れでログインを拒否すると、利用者は自力で復旧できない。管理者によるパスワード再発行
（＝ 別経路での配布）を毎回挟むことになり、期限を短くするほど運用が破綻する。

代わりに `must_change_password` と同じ「パスワード変更画面へ誘導する状態」として扱う。判定は
`password_change_required(user, policy, now)` の 1 本にまとめ、**ログイン経路と変更経路が同じ規則を
見る**。片方だけが期限を見ると「変更画面へ送られたのに、その画面が変更を受け付けない」という
出口の無い状態になる。

**期限切れをフラグとして DB に書かない。** 期限は設定値（`PASSWORD_MAX_AGE_DAYS`）で決まり、
設定変更で**過去にさかのぼって変わる**。書き込み時点の判定を保存すると、設定を戻しても
フラグが残る・伸ばしても消えないという食い違いが生じる。設定と現在時刻から毎回導出する。

起点は `users.password_changed_at`。列は **NULL 許容**とする。NOT NULL にすると、ローリング
デプロイ中に列を知らない旧プロセスが `users` へ INSERT した瞬間に失敗し、利用者を作れなくなる。
NULL は「未記録」を意味し、アプリ層は `created_at`（＝そのパスワードが存在し得た最古の時刻）へ
落とす。未記録を「無期限」に丸めると、**最も古いパスワードを持つ利用者だけが期限の外に出る**。

### 3. 履歴には退役したハッシュだけを積む

`user_password_history` に置くのは**置き換えられた**ハッシュだけで、現行の写しは持たない。
同じ値が 2 か所にあると更新漏れで「履歴上は現行だが実際は違う」状態が生まれ、そのずれは
パスワードを設定する 7 経路すべてに散る。再利用の判定は `users.password_hash` と履歴の
新しい順 N-1 件を見る。

`PASSWORD_HISTORY_COUNT` は**現行を含む**件数と定義する（`1` = 現行と同じ値だけを拒否）。
保持件数も判定件数と一致させ、使わないハッシュを持ち続けない。

保存するのは現行パスワードと同じ argon2 の PHC 文字列で、平文も可逆な値も持たない
（照合は候補を各行へ verify する）。履歴が新しい攻撃面を作らないようにするためで、
不可逆でない要約（生ハッシュ・トランケート値）は使わない。

**書き込みは現行ハッシュを条件にした compare-and-swap にする。** 履歴は「実際に置き換えた」
ハッシュでなければ意味を持たない。無条件の UPDATE だと、同時に届いた 2 つの変更要求が同じ現行
ハッシュを読み、後勝ちで上書きしたうえで**両方が同じ古いハッシュを積む** —— 先に書かれた
パスワードは現行にも履歴にも残らず、直後に再利用できてしまう（同じフォームの二重送信でも、
古いハッシュの重複で本当に古い行が剪定で押し出される）。`UPDATE ... WHERE password_hash = ?`
の影響行数で判定し、負けた要求は書き込まずにやり直させる。管理者によるパスワード再発行でも
同じにする —— 負けたのに成功を返すと、管理者へ渡した生成パスワードが実際には設定されていない
（本人へ伝える値が嘘になる）。

### 4. 漏えい照合は k-匿名性で行い、到達できないときは通す（fail-open）

パスワードの SHA-1 の**先頭 5 桁だけ**を照合サービスへ送り、返ってきた数百件の接尾辞との一致は
プロセス内で見る（Pwned Passwords のレンジ API と同じ契約）。外へ出るのは「同じ 5 桁で始まる
どれか」だけで、パスワードも利用者も渡らない。ここでの SHA-1 は**照合プロトコルの定義**であって、
保存・認証には使わない（保存は argon2 のまま）。

既定は**無効**とする。外向き通信を前提にしない配置（ADR-0010 のゼロタッチ配置、閉じた社内網）で
「設定していないのに外部へ出る」ことを避けるためで、閉域では互換のミラーを立てて
`PASSWORD_BREACH_API_BASE_URL` を向ける。

**照合できなかったときは拒否せず通す。** 外部サービスの不調でパスワード変更・リセットが一切
できなくなると、資格情報が漏れた**まさにその状況**で交換ができない。「漏えい済みの値をたまに
取りこぼす」ことより「変更を止める」ことの方が危険だ、という判断である。

一方で**履歴の読み取り失敗は fail-open にしない**。履歴は自前の DB にあり、読めない状態は外部の
不調と違って IdP 自身の異常である。黙って再利用を通すより、変更を失敗させて異常を見せる。

### 5. 拒否理由を利用者へ返す

「弱い」の一語にまとめると、再利用を拒否された利用者は同じ値を何度も試すことになる。利用者が
次に取るべき行動は理由ごとに違う（長さ不足は伸ばせばよいが、漏えい・再利用は別の値を考えるしかない）。

api は理由コード（`policy` / `breached` / `reused`）を返し、訳出は web が行う（`CLAUDE.md` の i18n
責務分離。api は言語を決めない）。理由コードは既定値を持つ enum とし、理由を持たない応答を
読んでも従来と同じ表示になるようにする。

## 影響

- migration 0031 で `user_password_history` と `users.password_changed_at` を追加する。
  down は両方を落とす（パスワード認証自体は `users.password_hash` だけで成立するため、
  戻してもログインは通る。失われるのは再利用禁止と有効期限の判定材料）。
- 既定値の変更は `PASSWORD_HISTORY_COUNT = 5`（＝現行と直近 4 件を拒否）のみ。**現行と同じ値への
  「変更」がこれまで通っていたが、以後は拒否される**（強制変更をその場で無効化できる状態を塞ぐ）。
  有効期限と漏えい照合は既定で無効のため、設定しない限り挙動は変わらない。
- 管理者によるパスワード再発行でも退役ハッシュを積む。積まないと「再発行 → 本人が変更」の直後に
  再発行前のパスワードへ戻せてしまう。
- 残件: パスワードポリシーの管理画面は未実装（ランタイム設定として編集する）。`PASSWORD_MIN_LENGTH`
  は web と共有していないため、フォームのブラウザ側チェック（`minlength`）は既定値の 8 のままで、
  超過分はサーバが拒否する。
