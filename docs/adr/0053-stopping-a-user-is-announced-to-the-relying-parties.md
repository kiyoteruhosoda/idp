# ADR-0053: 利用者を止めたことは RP へ伝える

- Status: Accepted
- Date: 2026-09-15
- 関連: `docs/adr/0024-backchannel-logout-sid-and-delivery-queue.md`（配送キュー）、
  `docs/adr/0049-attribute-ownership-and-the-federation-key.md`（I7・G3）

## 背景

assay は OpenID Connect Back-Channel Logout 1.0 の送り手を持っている（ADR-0024）。
ところが、その `enqueue` を呼ぶ場所は**ログアウトのハンドラ 1 か所だけ**だった。

つまり、**利用者本人がログアウトしたときにしか通知が飛ばない**。管理者が

- 利用者を無効化した
- パスワードを再発行した
- MFA を解除した

いずれの場合も、assay は SSO セッション・リフレッシュトークン・認可コードを消す
（`UserLifecycleService::revoke_credentials`）が、**RP には何も言わない**。RP は自分が
発行したトークンで動いているので、こちらが黙って消しても気付けない。

⚠ **これらの操作をする理由の多くは「乗っ取られたかもしれない」である。** その状況で
assay の中だけ閉じても、利用者は RP 側では入ったままになる。ADR-0049 は I7 として
「利用者を止めたら RP に届く」を掲げ、G3 で**受け口を持つ RP が 0 本**であることを
指摘したが、そもそも**送り手も出していなかった**。受け口を 7 本に入れた今、ここが
残っていると経路全体がつながらない。

## 決定

### 1. 失効させたら知らせる —— 起点は「セッションを消した場所」に置く

条件を「無効化のとき」にしない。**`revoke_credentials` / `revoke_credentials_strict`
そのものが通知を積む。** この 2 つは「この利用者の既存セッションはもう使えない」を
意味する唯一の場所で、無効化・パスワード再発行・MFA 解除はすべてここを通る。

呼び出し側に条件を書くと、次に失効を伴う操作が増えたときに**足し忘れても何も壊れない**
（テストも通り、気付けるのは RP に古いセッションが残っているときだけになる）。

### 2. `sid` は付けない

ログアウトは「この 1 セッションを閉じる」なので `sid` を載せる。管理操作が失効させるのは
**その利用者の全セッション**なので、`sid` は `None` にする。付けると RP は名指しされた
1 つしか閉じず、別の端末のセッションが残る。

### 3. 出口はトレイトで挟む（`SessionStopAnnouncer`）

具象 `StopAnnouncementService` は「RP の一覧」と「配送キュー」の両方を握る。
`UserLifecycleService` がこれを直に持つと、管理操作のユニットテストが署名鍵・HTTP 送信・
キューの DB まで組み立てることになる。トレイト越しに受け、テストは呼ばれた事実だけを見る。

### 4. 積めなかったときの扱いは、呼び出し元の性格に合わせる

- `revoke_credentials`（fail-open。無効化・パスワード再発行）—— 通知が積めなくても
  操作は成功のまま。assay 側では既に止まっており、ここで巻き戻すと
  「止めたのに止まっていない」というより悪い状態になる。積めなかったことは ERROR で残す。
- `revoke_credentials_strict`（fail-closed。MFA 解除）—— **失効しきったときだけ**知らせる。
  失効に失敗した状態で「止まった」と伝えると、RP は閉じたのに assay にはセッションが残り、
  食い違いが後から追えなくなる。

## 理由

**「送り手はある」と「送っている」は別である。** ADR-0024 で配送キューを作った時点で
I7 の送り側は済んだつもりになっていたが、実際に呼ばれる経路は 1 本しか無かった。
機能の有無ではなく**呼ばれる場所の数**で見る必要がある。

条件を呼び出し側に書かない（決定 1）のは、この失敗を繰り返さないためでもある。
「失効させる」と「知らせる」を同じ関数に閉じておけば、片方だけ足すことができない。

## 影響

- 管理者が利用者を止める・パスワードを再発行する・MFA を解除すると、
  `backchannel_logout_uri` を登録している全クライアントへ通知が積まれる。
  送信はこれまでどおりワーカーが再試行付きで行う（ADR-0024）。
- ⚠ **RP 側の受け口が要る。** 受け口を持たない RP には通知が届かない（登録もされない）。
  受け口の実装は RP ごと（ADR-0049 G3 の対応）。
- 通知の件数は「テナントに登録されたクライアントのうち `backchannel_logout_uri` を
  持つもの」の数だけ増える。1 回の管理操作あたりで、ログアウト 1 回と同じ規模。
