# ADR-0022: 認証器レジストリは状態だけ先に集約し、秘密は後から動かす

- 日付: 2026-08-08
- 状態: 採用
- 関連: ADR-0004（schema-version 同期・expand/contract）、ADR-0020（認証ポリシー）、
  `docs/Progress.md` AP11（contract フェーズ）、`migrations/0023_user_authenticators.up.sql`

## 背景

第 2 要素の実装が種別ごとにばらばらの表を持っていた。TOTP は `user_totp_secrets`、
パスキーは `user_webauthn_credentials` で、どちらも「その方式の秘密」と「その方式の状態」を
同じ行に混ぜている。この形には次の問題がある。

- **利用者が自分の認証器を一覧できない。** 「今どの手段でログインできるのか」を出すには
  種別の数だけ表を舐める必要があり、種別を足すたびに画面と API が増える。
- **状態の語彙が種別ごとに違う。** TOTP には `confirmed_at`、パスキーには実質的に
  「行が在るか」しかなく、「一時停止」に相当する状態がどちらにも無い。端末を無くしたが
  まだ捨てたくない、という運用（AP9 の要件）を表現できない。
- **リカバリーコード・メール OTP・SMS OTP を足す先が無い。** 素直にやると表がもう 3 つ増える。

一方で、既存の秘密を新しい表へ移すのは危険度が高い。TOTP の共有鍵とパスキーの公開鍵は
**それが唯一のログイン手段である利用者がいる**値で、移送に失敗すると本人は自力で復旧できない
（管理者の MFA 解除に頼るしかなくなる）。

## 決定

`user_authenticators` を **認証器レジストリ**として追加するが、**expand フェーズでは秘密を移さない**。

### 1. レジストリが持つのは「種別・状態・ラベル・時刻」だけ

`authenticator_type`（`totp` / `webauthn` / `recovery_code` / `email_otp` / `sms_otp`）と
`status`、表示用の `label`、`confirmed_at` / `last_used_at` / `expires_at` / `revoked_at` を持つ。
TOTP の共有鍵とパスキーの公開鍵は元の表に残したまま、`credential_ref` で元の行を指す。
検証経路（TOTP 照合・WebAuthn assertion）は従来どおり元の表を読む。

**この時点でレジストリは秘密の所在ではなく目録である。** 目録だけでも、一覧・一時停止・
失効・「残り n 本」の表示という AP9 の要件は満たせる。

例外はレジストリで新設した種別（リカバリーコード・メール OTP）で、これらは移送すべき既存データが
無いため最初から `secret_encrypted`（値はハッシュ）をレジストリ側に持つ。

### 2. 状態遷移は 4 状態・失効は終端

`pending` →（確認）→ `active` ⇄ `suspended` →（失効）→ `revoked`。`revoked` からはどこへも戻れない。

戻れることにすると「失効させた認証器が復活しうる」ことになり、紛失・盗難への対応として
成立しない。復活が要るなら新規に登録し直す。同じ状態への遷移は冪等な成功として扱う
（二重クリック・再送で 500 を返さないため）。

### 3. 一時停止・失効は、秘密が元の表にあっても認証時に効かせる

状態を登録簿にしか書かないなら、**認証経路も登録簿を見なければならない**。見なければ「画面では
停止中と出ているのに、その認証器で入れる」ことになり、機能として成立しない。TOTP 照合と
WebAuthn assertion の直前に登録簿を引き、`suspended` / `revoked` の行があれば通さない。

判定は「止められた行があるか」に限る。行が無い・`pending` の場合は既存経路の判断
（`confirmed_at` の有無など）に委ねる。**登録簿はこの段階では「確認済みかどうか」の出所ではない**
ため、そこまで登録簿で決めると、秘密は書けたが登録簿の更新だけが落ちた利用者を締め出しかねない。
契約フェーズで秘密ごと移したら、登録簿が唯一の出所になり、この二段構えは消える。

パスキーは 1 利用者に複数あるので `credential_ref` で 1 行に絞る（1 本止めても他の本は使える）。
TOTP は 1 利用者 1 件なので種別で引く。

### 4. 秘密の集約（contract フェーズ）は独立した後続タスクにする

`docs/Progress.md` AP11 として切り出し、(1) 読み出し経路の切り替え → (2) 秘密の移送 →
(3) 旧表の削除、を別々のマイグレーションで段階的に行う。1 と 2 の間には**両方を読める期間**を置く
（ローリングデプロイ中は新旧のプロセスが同時に動くため）。

## 影響

- 一覧・状態変更は `user_authenticators` を、検証は元の表を見る**二重の読み先**が当面残る。
  どちらを見るかは「目録か秘密か」で決まり、判断が要る箇所はレジストリ側の
  `credential_ref` に集約されている。認証経路は両方を読む（登録簿で止められていないかを見てから、
  元の表の秘密で照合する）。
- 既存の TOTP・パスキーはマイグレーション内の冪等な `INSERT ... SELECT` で backfill する。
  再実行しても二重登録にならない（`credential_ref` の有無で判定する）。
- 認証器の種別を足すコストが「表を 1 つ足す」から「enum に 1 値足す」へ下がった。
  SMS OTP は語彙としては入っているが送信経路が無く、実際には使えない（AP13）。

## 却下した案

- **最初から秘密ごと移す（ビッグバン移行）。** 一度で済むが、失敗したときの影響が
  「MFA を設定した全利用者がログインできない」で、しかも本人には復旧手段が無い。
  段階を刻めば、各段で戻せる。
- **表はそのままに、一覧をアプリ層の UNION で組み立てる。** マイグレーション不要だが、
  「一時停止」の状態を置く場所が無く、種別を足すたびに UNION の枝が増える。
  問題の本体は表の数ではなく**状態の語彙が種別ごとに違うこと**なので、これでは解けない。
