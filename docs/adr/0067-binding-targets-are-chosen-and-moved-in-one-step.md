# ADR-0067: 名乗りの相手は一覧から選び、別のアプリからは 1 回で移す。アプリは画面から消せる

- Status: Accepted
- Date: 2026-10-01
- 関連: `docs/adr/0054-an-application-is-the-thing-a-relying-party-hangs-from.md`（アプリという段。決定 7
  「登録した RP はその場でアプリとして開く」、帰結「binding を外すと判定の外へ出る」）、
  `docs/adr/0059-an-application-has-identities-and-principals.md`（名乗りの 4 種類。決定 1「相手は人が
  知っている値で指す」「既に別のアプリの名乗りなら 409 でそのアプリ名を返す」）、
  `docs/adr/0060-a-stopped-application-stops-its-service-accounts.md`

## 背景

持ち主の指摘（2026-10-01）:「空になったアプリを消す方法？UI 足りてる？」「（名乗りを結ぶのに）ID 指定は酷では」。

ADR-0054 の決定 7 で、ログイン用のクライアントを登録すると**アプリが 1 件自動で開く**。それを本来の
アプリ（たとえば同じサービスの別のログイン口や宛名を既に持つアプリ）へ結び直すには、画面では次の手順が
要った。

1. 自動で開いたアプリの詳細を開き、名乗りを「外す」
2. 本来のアプリの詳細を開き、種類を選び、**クライアント ID を手で写して**「結び付ける」
3. 空になった自動のアプリが一覧に残る。**画面に消す口が無い**（API の `DELETE` はある）

困りごとは 3 つある。

- **ID の写し**: クライアント ID は乱数の 32 桁で、SAML は SP の内部 ID（UUID）。人が写す値ではない。
  相手はどれもテナントに登録済みの行なので、assay は候補を全部知っている
- **2 段の間に穴が開く**: 1 と 2 の間、ログイン用の相手はどのアプリにも属さない。判定はアプリを持たない
  client を素通しする（ADR-0054 の帰結）ので、その間は**テナントの誰でもログインできる**。画面の操作は
  数十秒でも、途中で手が止まれば開いたままになる
- **消せない**: 空のアプリは名簿も名乗りも持たないが、一覧で本物のアプリと並ぶ

## 決定

### 1. 名乗りの相手は、種類ごとの候補の一覧から選ぶ。手入力の欄は画面から消す

`GET /{tenant_id}/admin/applications/{application_id}/binding-candidates` を足す。テナントに登録済みの
ものを、種類の性質に合うものだけ並べ、**いまどのアプリの名乗りか**を添える。

| 種類 | 候補 | 表示 |
|---|---|---|
| ログイン（OIDC） | `authorization_code` を持つ client（論理削除済みを除く） | 登録名 — `client_id` |
| ログイン（SAML） | SP | 表示名 — `entity_id` |
| サービスアカウント | `client_credentials` だけの client（論理削除済みを除く） | 登録名 — `client_id` |
| API の宛名 | 宛名 | 表示名 — URI |

- ⚠ **種類の突き合わせは結び付け（`bind`）と同じ述語で行う。** 候補に出たのに結べない、を作らない
- このアプリの名乗りになっているものは出さない（もう結んである）
- 権限はアプリの詳細と同じ `idp.applications:read`。出すのは相手の識別子と登録名だけで、クライアントの
  設定（リダイレクト URI・認証方式・秘密）は出さない。アプリの詳細も名乗りの `client_id` と登録名を
  既に出しており、結び付けの口（`idp.applications:write`）は `client_id` を受けて 404 / 409 で答えるので、
  この一覧で新しく見えるようになる事実は無い

**手入力の欄は残さない。** 逃げ道として残す理由が無い ——結べる相手は定義からテナントに登録済みの行で、
その全部が候補に出る。候補に無いのは「まだ登録していない」か「種類が合わない」かのどちらかで、前者は
登録の画面へ、後者は手で入れても API が 400 で断る。欄を残すと「一覧に無いから ID を探して入れる」という
誤った道を示すことになる。

API は今までどおり値（`client_id`・SP の内部 ID・宛名の URI）で受ける（機械のクライアントと手順書が使う。
ADR-0059 の決定 1 のまま）。

### 2. 別のアプリの名乗りは、外す＋結ぶを 1 回で移す。移す元は名指しする

`POST …/bindings` に `move_from_application_id` を足す。相手が既に別のアプリ A の名乗りで、
`move_from_application_id` が A なら、A から外してこのアプリへ結ぶ。

- ⚠ **1 文で付け替える**（`UPDATE application_bindings SET application_id = …`）。外す＋足すの 2 回に
  分けると、間で落ちたときに相手がどこにも属さなくなり、ログイン用なら判定の外に出る（背景の穴）
- ⚠ **移す元を名指しにする。** 「移してよい」の真偽値だけを受けると、画面で確かめた時点と送った時点の
  間に持ち主が A から B へ替わったとき、確かめていない B から黙って奪う。名指しが今の持ち主と違えば、
  今の持ち主の名前で 409 を返す（ADR-0059 の決定 1 の 409 と同じ形）
- 名指しが無ければ今までどおり 409（黙って奪わない）
- 相手がどこにも属していなければ、名指しがあってもただ結ぶ
- 監査は `application_binding.moved` の **1 行**で残す。`reason` に移した先（`application=`）と
  移した元（`from_application=`）、種類と相手を載せる。外す・足すの 2 行にすると、「外したまま」と
  「移した」が監査ログで見分けられない

画面は、持ち主の居る相手を選んだら**すぐには送らない**。「『A』から移しますか？」と、移すと何が変わるか
（A から外れる。ログインの判定・名簿・宛名のトークンはこのアプリの設定で決まる）を出し、「『A』から移す」で
名指しを付けて送り直す。確認はブラウザのダイアログではなく画面で出す（JavaScript に頼らない。持ち主は
送った時点で引き直す）。

### 3. アプリは詳細の画面から消せる。何が外れるかは押す前に言う

詳細の画面の下に「このアプリを消す」を置く。API の削除（`DELETE …/applications/{id}`）は**断らない**
——名乗りと使う主体を外して消す（相手の登録は消えない）。画面はこれに合わせ、押す前に次を出す。

- 「名乗り N 件と、使う主体 M 件を外して、このアプリを消します。」（どちらも 0 なら「名乗りも使う主体も
  ありません」）
- 名乗りだった連携先・サービスアカウント・宛名の登録は消えず、どのアプリにも属さない状態に戻ること
- ⚠ **ログイン（OIDC・SAML）の名乗りがあれば**、消すとその連携先は判定の外に出て、テナントの誰でも
  ログインできるようになること。使い続けるなら先に別のアプリへ移すこと

押したらブラウザの確認（`data-confirm`）を挟み、消したら一覧へ戻す。

## 捨てた案

### A. 手入力を「候補に無いもの用」に残す

上のとおり、候補に無いものは結べないか、まだ登録されていない。残すと誤った道を示すだけになる。

### B. 削除を「名乗りが残っていれば断る」にする

空のアプリを消したいという要求には足りる。採らないのは、API の振る舞いを変えると機械のクライアントの
前提が変わるうえ、「名乗りを全部外してから消す」が画面で何手にもなるからである。名乗りが残っていても、
外れるものと、ログインの名乗りなら判定の外に出ることを押す前に言えば足りる。

### C. 移すときは確認をブラウザのダイアログ（`data-confirm`）で出す

選択肢に持ち主を `data-*` で持たせれば 1 往復減る。採らないのは、JavaScript が動かないと確認なしで
送ってしまう（実際には 409 で止まるが、そのときの文言は「外してから」で、移す道を示さない）ことと、
画面を出した時点の持ち主で確かめることになる（送る時点で引き直せない）からである。

### D. クライアントの登録画面で、作るアプリを選べるようにする

自動のアプリが生まれること自体を避けられる。今回は入れない（登録の要求と、アプリを開く処理の両方に
手が入る）。課題として task に残す。

## 帰結

- 自動で開いたアプリを本来のアプリへ寄せる操作は、「本来のアプリで相手を選ぶ → 移す」と「空のアプリを
  消す」の 2 つになり、ID を写す手順が無くなる
- 移す操作の間に、ログイン用の相手が判定の外に出る瞬間が無くなる
- 監査ログに `application_binding.moved` が増える（`event_type` は文字列の列で、表の変更は要らない）
- 使う主体（人・サービスアカウント）の追加は、まだ ID の手入力のまま（本 ADR の範囲外）
