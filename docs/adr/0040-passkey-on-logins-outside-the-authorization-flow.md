# ADR-0040: 認可フロー外のログインでもパスキーを受け付ける

- Status: Accepted
- Date: 2026-08-29
- 関連: `docs/adr/0006-admin-permission-model.md`（管理コンソール）、`docs/adr/0009-multi-tenant-architecture.md` §5・§8、
  `docs/adr/0019-sibling-api-hostname-and-web-origin-rp-id.md`（RP ID は web のホスト）、
  `docs/adr/0020-authentication-policy.md`（認証ポリシー。パスキーは `require_mfa` を満たす）

## Context

パスキー（WebAuthn）のログインは **OIDC 認可フローの中でしか成立しない**作りだった。
`PasskeyAuthenticationService::complete()` はチャレンジに結合した `auth_session_id` が無いと
内部エラーで落ち、成功時は必ず authorization code を発行して RP の `redirect_uri` へ戻す。

一方、assay には認可フロー外の直接ログインが 2 つある。**管理コンソール**
（`/{tenant_id}/admin/login`）と**ポータル**（`/{tenant_id}/login`）で、どちらも RP を介さずに
SSO セッションを直接発行する（ADR-0006 §6）。この 2 画面にはパスキーのボタンが無く、
利用者は「自分のアカウントにパスキーを登録したのに、IdP 自身の画面ではパスワードを打つ」
という状態に置かれていた。**パスキーを登録する画面自体が、パスワードでしか入れなかった。**

さらに副作用として、認証ポリシーで `require_mfa` が掛かった管理者は管理コンソールへ入る手段が
実質無かった。管理コンソールのログインは第二要素の入力ステップを持たないため
`AdminLoginOutcome::MfaRequired` を返してポータルへ案内するが、ポータルの第二要素も
パスワード + TOTP であり、TOTP を持たない管理者はどこからも入れない。

## Decision

### 1. セレモニーは 1 か所に置き、その上に経路ごとの続きを載せる

WebAuthn のセレモニー（チャレンジの発行・消費、アサーション検証、認証器登録簿の一時停止判定
（AP9）、署名カウンタの更新、テナント境界の確認）を `application::passkey_assertion` へ切り出す。
3 つのログイン経路はこれを共有し、その上に自分の続きだけを持つ。

| 経路 | セレモニーの後にやること |
|---|---|
| `passkey_authentication`（認可フロー） | `auth_session` の継続 → 同意 → authorization code 発行 |
| `admin_login` | admin 権限の確認 → 認証ポリシー → SSO 発行 |
| `portal_login` | メール検証ゲート → 認証ポリシー → SSO 発行 |

**3 か所へ写さない。** 一時停止した認証器の判定や署名カウンタの更新は、経路ごとにずれても
テストが落ちずに気づけない種類の手順である。

### 2. パスキーは `require_mfa` を満たす（ADR-0020 §3 の適用範囲を直接ログインへ広げる）

パスキーは所有要素と User Verification を 1 回のセレモニーで満たすフィッシング耐性認証であり、
認可フローのログインでは既にそう扱っていた。**同じ規則を管理コンソール・ポータルにも適用する。**

結果として、`require_mfa` 下の管理者はパスキーでのみ管理コンソールへ入れる。パスワード経路の
`MfaRequired` / `MfaEnrollmentRequired` は従来どおり残す（単一要素で入れてしまわないため）。

`require_specific_method`（AP3）は使った方式の集合（`[WebAuthn]`・UV 済み）で判定する。
満たせない指定に当たった場合、パスキー経路はこの先に足せる要素が無いので拒否する。

### 3. パスワード固有のゲートはパスキー経路では見ない

**強制パスワード変更（`must_change_password`）**と**アカウントロック（`locked_until`）**は
パスキー経路では判定しない。前者はパスワードを使わない経路で変更を強制する意味が無く（現行
パスワードを要求する変更フォームは、パスキーしか持たない利用者には通せない）、後者は
パスワードの総当たりへの対策で、署名鍵の総当たりには効かない。認可フローのパスキーログインも
以前からこの規則で動いている。

**メール検証ゲート（SEC6b）はポータル経路で残す。** これは資格情報の強さではなく
「このアカウントでポータルへ入れるか」の判定であり、認証方式を変えても外す理由が無い。

### 4. チャレンジの用途は `auth_session_id_hash` の有無で分ける

api の開始（`POST /internal/passkey/login/begin`）は 3 経路で共通とし、`auth_session_id` を
渡すかどうかがそのままチャレンジの用途になる。完了エンドポイントは自分の用途と違うチャレンジを
`WrongFlow` で拒否し、**用途違いでもチャレンジは使い切る**（同じチャレンジで別の経路を
試させない）。

**web の開始ルートだけは経路ごとに分ける**（`/passkey/login/begin` と
`/passkey/login/direct/begin`）。Cookie を読むのは web だけで、共通にすると別タブで始めて
放置した認可フローの `auth_session_id` Cookie を直接ログインの画面が拾ってしまい、
Cookie が切れるまで管理コンソールへ入れなくなる。

`passkey_challenges.challenge_type` に値を足す案は採らなかった。CHECK 制約のマイグレーションを
足しても得られるのは同じ判定で、`auth_session_id_hash` は既に「認可フローに結合しているか」を
表す列だからである。

**管理コンソールとポータルは互いに区別しない。** どちらも同じ利用者の同じ SSO Cookie を
発行する経路で、権限差は完了側の判定（admin 権限の有無）で付く。ホスト共有の SSO は
そもそもテナント切り替えで行き来する（ADR-0009 §8）。

## Consequences

- パスキーを持つ管理者は、管理コンソールにパスワードを打たずに入れる。`require_mfa` 下の
  管理者にとっては、これが唯一の導線になる。
- 管理コンソールとポータルのログイン画面は、RP ID の都合で **web と同一オリジン**にある必要が
  ある（ADR-0019 決定 2）。既にそうなっており、登録済みのパスキーがそのまま使える。
- パスキーしか持たない管理者に強制パスワード変更を掛けても、パスキーで素通りする。
  「全員にパスワードを変えさせる」運用を組む場合、パスキー利用者には効かない。
- ブラウザ JS 経路が 1 本増えたわけではない。`assets/passkey-login.js` を 3 画面で共有し、
  完了先だけを `data-complete-path` で受け取る。
