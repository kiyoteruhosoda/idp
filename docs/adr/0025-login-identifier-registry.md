# ADR-0025: ログイン識別子の登録簿（expand フェーズ）

- 日付: 2026-08-09
- 状態: 採用
- 改訂: 2026-08-23（MT25。migration 0041）— 一意制約を `(tenant_id, identifier_type,
  normalized_value)` から **`(tenant_id, normalized_value)`（種別非依存）**へ変更した。以下 §2・§7 の
  「1 種別の中では 1 人に決まる」という記述はこの改訂で置き換わっている（詳細は ADR-0009 §8）。
- 関連: ユーザー認証・認証ポリシー仕様書 §4、ADR-0009 §8（認証はテナント境界内・ログイン識別子は
  `preferred_username`）、ADR-0004 §6（expand/contract）、ADR-0022（認証器登録簿の expand フェーズ）

## 背景

ログイン欄に入力できる値は `users.preferred_username` の 1 本だけだった。1 利用者 1 列である以上、
次のことが構造的にできない。

- **組織がすでに配っている識別子でログインさせる。** 電話番号・社員番号は多くの組織で「その人を
  指す値」として既に流通しているのに、本 IdP にログインするときだけ別の名前を覚えさせている。
- **入り口を複数用意する。** 改姓でユーザー名を変えると、旧い名前は即座に使えなくなる。周知が
  行き渡るまでの猶予を作れない。
- **識別子を 1 本だけ止める。** 列が 1 つしか無いので、止める手段はアカウントごと無効化するか、
  値を書き換えて（＝別の識別子に変えて）しまうかのどちらかしかない。

## 決定

### 1. 識別子は種別付きの登録簿（`user_login_identifiers`）として持つ

1 行が「この利用者は、この種別のこの値でもログインできる」を表す。種別は
`username` / `email` / `phone_number` / `employee_number` の 4 値（DB ネイティブ ENUM を使わず
`VARCHAR` + `CHECK`。許可値の単一の出所は Rust の `LoginIdentifierType`）。

**種別は「正規化のしかた」を決めるためにある。** 同じ文字列でも、ユーザー名としてなら大小を
無視し、電話番号としてなら区切り記号を無視する。この違いを列やフラグではなく型で表す。

### 2. 表示値と正規化値を分けて持つ

照合は `normalized_value` だけで行い、画面に出すのは登録したままの `display_value` にする。
`090-1234-5678` と `+81 90 1234 5678` は同じ番号を指すが、利用者が自分の登録内容だと分かるのは
前者である。正規化した値を表示にも使うと「登録した覚えのない値が管理画面に並ぶ」ことになり、
同一性の確認ができなくなる。

一意制約は `(tenant_id, identifier_type, normalized_value)` に張る。「同じ値で 2 人が解決される」
ことを DB の側で禁じるためで、アプリ側の事前チェックだけに頼らない。

> **改訂（2026-08-23 / migration 0041）**: 一意キーから `identifier_type` を外し
> `(tenant_id, normalized_value)` にした。種別は正規化のしかたを決めるためのもので、値の持ち主を
> 決めるものではない。引き方（種別との対で引く）に合わせた非ユニーク索引
> `user_login_identifiers_lookup_idx` を別に持つ。

### 3. 無効化は行を消さずに行う

`is_active = 0` の行はログイン欄で一致しないが、行は残る。一意制約は `is_active` を見ないため、
**止めた値は他の利用者が登録できない**。削除にすると同じ値を別人が登録でき、止めた識別子の
宛先が黙って変わる。「この値は使えない」と「この値は誰のものでもない」は別の状態である。

### 4. 解決は「登録簿 → `users.preferred_username`」の順。既存の値は**写さない**（expand フェーズ）

`users.preferred_username` は**主たるログイン識別子のまま**にし、登録簿には**追加の識別子だけ**を
置く。migration 0029 は backfill を行わない。ログイン時の解決は
`UserRepository::find_by_login_identifier` の 1 本に閉じ、登録簿を先に引いて、無ければ
`preferred_username` へ落とす。

写しを取らないのは、同じ値が 2 か所にあると**二重書きの同期**が必要になるためである。同期が
漏れた瞬間に次が起きる。

- プロフィール編集で `users` 側だけが変わると、**変更前のユーザー名でログインできる**
  （登録簿が先に引かれるため）。
- 写しの行を無効化しても、`preferred_username` へのフォールバックで**認証は通ってしまう**。
  管理者が「侵害された識別子を止めた」と思った操作が効いていない。
- `users` の更新と登録簿の更新は別トランザクションになるため、片方だけ成功した状態を
  「エラーを返したのに変更は起きている」形で外へ見せてしまう。

これらはどれも**同じ値を 2 か所に持ったこと**が原因で、経路ごとに同期を足していく形では塞ぎ
きれない。主識別子を登録簿へ移すのは contract フェーズ（Progress AP15）でまとめて行う。移送に
失敗すると**誰もログインできなくなる**変更であり、登録簿の導入と同じ回に載せない（ADR-0022 と
同じ分け方）。

管理画面が「その利用者が実際にログインに使える値」を一覧できないと困るため、一覧 API は
`users.preferred_username` から**読み出し時に合成した行**を先頭に足す（`id` が `null`・
`is_primary` が `true`）。保存はしないので、同期の問題は生まれない。

### 5. `users.email` も取り込まない

取り込むとマイグレーションを当てた瞬間から**メールでログインできる**ようになる。今日まで
できなかったことが黙って可能になるのは、認証の入り口が広がる変更であって、マイグレーションが
勝手に決めてよいことではない。メールでのログインを許すかはテナントの判断とし、管理 API から
`email` 種別の識別子を明示的に足したときだけ有効になる。

### 6. 追加できる値かは「実際の解決経路で引いてみる」で判定する

登録簿の一意制約だけでは足りない。主たる識別子は expand フェーズの間 `users` 側にあるため、
そちらと衝突した識別子は「登録はできたが、ログインすると別人が返る」という壊れ方をする。
そこで追加前に `find_by_login_identifier`（＝本番の解決と同じ引き方）を通し、**すでにログインに
使える値を拒否する**。判定と本番が同じ経路である限り、両者がずれることはない。

拒むのは他人に解決される値だけではない。**自分の主識別子と同じ値も拒む。** 登録できてしまうと、
その行を無効化しても `preferred_username` へのフォールバックで認証が通る ——「止めたのに使える」
識別子ができる。重複させないことが、その状態を作らせない一番簡単な方法である。

メールアドレス種別だけは追加で `users.email` も見る。メールは現状ログインの入り口ではないため
解決経路には当たらないが、他人のメールアドレスを自分のログイン識別子にできると、その人の
連絡先で本人になりすませる（本人自身のアドレスは正当な用途なので通す）。

### 7. 候補生成と登録時検証は同じ「読めるか」判定を使う

入力には種別が書かれていないため、解決は「この入力が各種別だったら何になるか」を作って引く。
このとき**種別ごとの正規化を無条件に掛けてはいけない**。電話番号の正規化は数字以外を落とすので、
ユーザー名 `alice123456` から `123456` が生まれ、**他人の電話番号**に一致し得る。

そこで `LoginIdentifierType::accepts`（その種別として読めるか）を 1 つ置き、登録時の検証と
候補生成の両方がそれを使う。これで「登録できる値は必ずその種別の候補になる」「登録できない
読み方では引かない」が同時に成り立つ。社員番号が空白を含めないのもこの整合のためで、
正規化で空白を落とす以上、含む値を許すと登録した書き方では引けなくなる。

それでも種別をまたいだ曖昧さは原理的に残る（ある入力がユーザー名としては A、社員番号としては
B に当たる）。**複数の利用者に当たったら誰も返さない**（fail-closed）。
`LIMIT 1` で選ぶと、どちらが返るかが索引の都合で決まってしまう。

> **改訂（2026-08-23 / migration 0041）**: 一意制約が `(tenant_id, normalized_value)` になったため、
> 同じ**正規化値**で 2 人に当たることは無くなった。残る曖昧さは、種別ごとに正規化が違うために
> 1 つの入力が複数の正規化値へ広がる場合（`090-123-4567` はユーザー名なら素のまま、電話番号なら
> `0901234567`）と、参加先テナントのゲスト解決が所属元テナントをまたぐ場合の 2 つである。
> fail-closed はそのために引き続き要る（ADR-0009 §8。「不在」と「曖昧」は型で区別する）。

### 8. 管理は API（CRUD）から始める

`/{tenant_id}/admin/users/{user_id}/login-identifiers`（GET/POST/PATCH/DELETE、`idp.tenant.admin`
必須）。変更は `user.login_identifier_added` / `.updated` / `.removed` として監査記録し、**種別のみ**を
`reason` に残す（電話番号・メールアドレスは PII のため値は残さない）。web 管理コンソールの画面は
後続タスク（Progress AP1 と同じ扱い）。

主たるログイン識別子は登録簿に無いため、識別子単位の操作（有効/無効・削除）の対象にならない。
一覧では `id` が `null` の合成行として出るので、宛先そのものが作れない。変えるならプロフィール
編集（MT25）、止めるならアカウントの無効化を使う。

## 影響

- マイグレーション 0029 で `user_login_identifiers` を追加（reversible）。**既存データは移さない**。
- ログイン 4 経路（OIDC・ポータル・管理コンソール・管理コンソールのパスワード変更）が
  `find_by_username` から `find_by_login_identifier` へ移った。**既定の挙動は変わらない**
  （登録簿が空なら `preferred_username` へのフォールバックだけが働く）。
- 利用者作成・プロフィール編集の一意性チェックが `find_by_username` から
  `find_by_login_identifier` へ移った（`users` だけを見ると、別名として登録済みの値を
  素通しにしてしまう）。
- 監査イベント種別が 3 つ増えた。

## 残る限界（承知のうえで受け入れる）

- 追加する識別子と `users.preferred_username` の衝突は**アプリ層の事前チェック**でしか防げない
  （主識別子が登録簿に無いため DB 制約が張れない）。同時実行の窓は残る。管理者操作に限られ、
  結果は「同じ値が 2 か所から解決され得る」だが、解決側は fail-closed（決定 7）なので認証は
  通らない。contract フェーズで DB 制約へ寄せる。
- 電話番号の国際表記（`+81 90…`）と国内表記（`090…`）は別のキーになる。国番号と国内
  プレフィクスの対応は国ごとに違い、ここで推測すると別人の番号に当たり得る。両方でログイン
  させたいなら両方を識別子として登録する。

## 非対象（フォローアップ）

- **contract フェーズ**: `users.preferred_username` を登録簿へ移し、列を撤去する。解決経路の
  切り替え → 移送 → 列の撤去を独立したマイグレーションに分け、間に「両方を読める期間」を挟む
  （ローリングデプロイ中に古いプロセスが残るため）。Progress AP15。
- **web 管理コンソールの画面**（Progress AP1 と同じ扱い）。
- **利用者本人による追加**。電話番号の所有確認（SMS OTP）が無い以上、本人が自由に足せる導線は
  作らない（Progress AP13）。
