# ADR-0025: ログイン識別子の登録簿（expand フェーズ）

- 日付: 2026-08-09
- 状態: 採用
- 関連: ユーザー認証・認証ポリシー仕様書 §4、ADR-0009 §8（認証はテナント境界内・ログイン識別子は
  `preferred_username`）、ADR-0004 §6（expand/contract）、ADR-0022（認証器登録簿の expand フェーズ）

## 背景

ログイン欄に入力できる値は `users.preferred_username` の 1 本だけだった。1 利用者 1 列である以上、
次のことが構造的にできない。

- **組織がすでに配っている識別子でログインさせる。** 電話番号・社員番号は多くの組織で「その人を
  指す値」として既に流通しているのに、本 IdP にログインするときだけ別の名前を覚えさせている。
- **入り口を複数用意する。** 改姓でユーザー名を変えると、旧い名前は即座に使えなくなる。周知が
  行き渡るまでの猶予を作れない。
- **識別子を 1 本だけ止める。** 列が 1 つしか無いので、止める手段はアカウントごと無効化するか、
  値を書き換えて（＝別の識別子に変えて）しまうかのどちらかしかない。

## 決定

### 1. 識別子は種別付きの登録簿（`user_login_identifiers`）として持つ

1 行が「この利用者は、この種別のこの値でもログインできる」を表す。種別は
`username` / `email` / `phone_number` / `employee_number` の 4 値（DB ネイティブ ENUM を使わず
`VARCHAR` + `CHECK`。許可値の単一の出所は Rust の `LoginIdentifierType`）。

**種別は「正規化のしかた」を決めるためにある。** 同じ文字列でも、ユーザー名としてなら大小を
無視し、電話番号としてなら区切り記号を無視する。この違いを列やフラグではなく型で表す。

### 2. 表示値と正規化値を分けて持つ

照合は `normalized_value` だけで行い、画面に出すのは登録したままの `display_value` にする。
`090-1234-5678` と `+81 90 1234 5678` は同じ番号を指すが、利用者が自分の登録内容だと分かるのは
前者である。正規化した値を表示にも使うと「登録した覚えのない値が管理画面に並ぶ」ことになり、
同一性の確認ができなくなる。

一意制約は `(tenant_id, identifier_type, normalized_value)` に張る。「同じ値で 2 人が解決される」
ことを DB の側で禁じるためで、アプリ側の事前チェックだけに頼らない。

### 3. 無効化は行を消さずに行う

`is_active = 0` の行はログイン欄で一致しないが、行は残る。一意制約は `is_active` を見ないため、
**止めた値は他の利用者が登録できない**。削除にすると同じ値を別人が登録でき、止めた識別子の
宛先が黙って変わる。「この値は使えない」と「この値は誰のものでもない」は別の状態である。

### 4. 解決は「登録簿 → `users.preferred_username`」の順（expand フェーズ）

`users.preferred_username` は**主たるログイン識別子のまま**にし、登録簿へは `username` 種別として
写しを取り込む（migration 0029 の backfill）。ログイン時の解決は
`UserRepository::find_by_login_identifier` の 1 本に閉じ、登録簿を先に引いて、無ければ
`preferred_username` へ落とす。

列そのものの撤去（contract フェーズ）は本 ADR の範囲外とする。移送に失敗すると**誰もログインでき
なくなる**変更であり、登録簿の導入と主識別子の移送を同じ変更に載せない（ADR-0022 と同じ分け方）。

写しが古くなるのは危険で、`users` 側だけを変えると**変更前のユーザー名でログインできてしまう**
（登録簿を先に引くため）。同期は `PrimaryLoginIdentifierSync` の 1 メソッドに閉じ、利用者作成
（管理者作成・自己登録）とプロフィール編集の両方をそこへ通す。

### 5. `users.email` は取り込まない

backfill するとマイグレーションを当てた瞬間から**メールでログインできる**ようになる。今日まで
できなかったことが黙って可能になるのは、認証の入り口が広がる変更であって、マイグレーションが
勝手に決めてよいことではない。メールでのログインを許すかはテナントの判断とし、管理 API から
`email` 種別の識別子を明示的に足したときだけ有効になる。

### 6. 追加できる値かは「実際の解決経路で引いてみる」で判定する

登録簿の一意制約だけでは足りない。主たる識別子は expand フェーズの間 `users` 側にもあるため、
そちらと衝突した識別子は「登録はできたが、ログインすると別人が返る」という壊れ方をする。
そこで追加前に `find_by_login_identifier`（＝本番の解決と同じ引き方）を通し、他人に解決される値を
拒否する。判定と本番が同じ経路である限り、両者がずれることはない。

メールアドレス種別だけは追加で `users.email` も見る。メールは現状ログインの入り口ではないため
解決経路には当たらないが、他人のメールアドレスを自分のログイン識別子にできると、その人の
連絡先で本人になりすませる。

### 7. 管理は API（CRUD）から始める

`/{tenant_id}/admin/users/{user_id}/login-identifiers`（GET/POST/PATCH/DELETE、`idp.tenant.admin`
必須）。変更は `user.login_identifier_added` / `.updated` / `.removed` として監査記録し、**種別のみ**を
`reason` に残す（電話番号・メールアドレスは PII のため値は残さない）。web 管理コンソールの画面は
後続タスク（Progress AP1 と同じ扱い）。

`username` 種別のうち `users.preferred_username` の写しに当たる行は削除させない。消しても `users`
側が残っているためログインは通り続け、「消したのに使える」という食い違いだけが残る。

## 影響

- マイグレーション 0029 で `user_login_identifiers` を追加（reversible）。既存の
  `preferred_username` を `username` 種別として取り込む。
- ログイン 4 経路（OIDC・ポータル・管理コンソール・管理コンソールのパスワード変更）が
  `find_by_username` から `find_by_login_identifier` へ移った。**既定の挙動は変わらない**
  （登録簿には backfill された `username` 行しか無いため）。
- `RegisterService` / `UserManagementService` / `UserLifecycleService` のコンストラクタ引数が
  1 つ増えた（`PrimaryLoginIdentifierSync`）。
- 監査イベント種別が 3 つ増えた。

## 非対象（フォローアップ）

- **contract フェーズ**: `users.preferred_username` を登録簿へ移し、列を撤去する。解決経路の
  切り替え → 移送 → 列の撤去を独立したマイグレーションに分け、間に「両方を読める期間」を挟む
  （ローリングデプロイ中に古いプロセスが残るため）。Progress に別項目として残す。
- **web 管理コンソールの画面**（Progress AP1 と同じ扱い）。
- **利用者本人による追加**。電話番号の所有確認（SMS OTP）が無い以上、本人が自由に足せる導線は
  作らない（Progress AP13）。
