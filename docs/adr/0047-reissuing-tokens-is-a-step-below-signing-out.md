# ADR-0047: トークンの再発行は、サインアウトの 1 段手前に置く

- Status: Accepted
- Date: 2026-09-09
- 関連: `docs/adr/0044-ending-a-session-revokes-its-refresh-tokens.md`（セッション側の失効）、
  `docs/adr/0045-changing-your-password-signs-out-the-other-devices.md`（パスワード変更の後始末）、
  `docs/adr/0046-revocation-is-bound-to-the-owning-client.md`（`/revoke` の持ち主確認）、
  `docs/adr/0009-multi-tenancy.md`（テナント境界）、RFC 6819 §5.2.2.3

## 背景

refresh token を落とす経路は ADR-0044 〜 0046 で一通り塞いだ。だが**落とすことそのものを
目的にした操作**は、どこにも無い。いま失効が起きるのは、他の何かの副作用としてだけである。

| 経路 | 一緒に起きること |
|---|---|
| 端末のログアウト（G10・RP-initiated） | その端末のログイン状態が切れる |
| 連携アプリの解除 | 同意が消え、次回に同意画面が出る |
| パスワード変更・リセット | パスワードが変わる |
| 無効化・削除・MFA 解除（管理者） | 業務が止まる／認証器が外れる |

「アプリに渡した鍵が漏れたかもしれない」だけの人が、この表から選べるものは無い。
一番近いのはパスワード変更（ADR-0045）だが、**パスワードは漏れていない**のに変えることになる。
管理者側はもっと極端で、ヘルプデスクに渡してある道具は無効化・パスワード再発行・MFA 解除の
3 つしかなく、どれも利用者の作業を止める。

結果として起きるのは「様子を見る」である。**30 日の refresh token を、心当たりを抱えたまま
放置する**。失効が効くこと（ADR-0044）は、それを呼ぶ手段が要ることとセットでしか意味を持たない。

## 決定

**発行済みの refresh token をまとめて失効させるだけの操作を、本人と管理者の両方へ用意する。**
利用者から見た名前は「トークンの再発行」——アプリは次のアクセスで取り直すので、体験としては
失効ではなく入れ替えである。

| | 経路 | 対象 |
|---|---|---|
| 本人 | `POST /{tenant_id}/settings/security/reissue-tokens`（セキュリティ画面） | 自分の全 refresh token |
| 管理者 | `POST /{tenant_id}/admin/users/{user_id}/token-reissue`（`idp.users:write`） | 対象利用者の全 refresh token |

**触るのはトークンだけ**とする。SSO セッションも同意も未消費の authorization code も残す。

- **セッションを残す**のは、切ると押した本人がその場で締め出されるため。手元のログインが
  生きているので、アプリの取り直しは SSO で素通りする（多くの利用者には何も起きない）。
  端末を切りたい人にはセッションの失効（ADR-0044）が既にある。
- **同意を残す**のは、消すと次回に同意画面が出るため。「鍵を替えたい」に対して同意のやり直しは
  余計で、それを望む人には連携解除がある。
- **authorization code を残す**のは、落としても守るものが無いため。code は数十秒で切れる一方、
  別タブで進行中のログインを巻き添えにする。そして生きたセッションを持つ相手は、押した直後に
  新しい code を取れる——そこを止めるのはセッションの失効の役目である。

### テナントで絞らない

refresh token は利用者の資格情報で、`sso_sessions` と同じく 1 人が複数テナントのアプリを
認可し得る（ADR-0044 決定 3）。画面の「連携済みアプリ」が現在のテナントぶんしか出ないことに
揃えると、**見えていないテナントの鍵だけが生き残る**。取りこぼした鍵は「入れ替えたつもり」を
裏切るが、余分に落とした鍵は黙って取り直されるだけで済む。

管理者側も同じ関数を呼ぶが、対象は**所属元（HOME）が要求テナントの利用者**に限られる
（`find_home_user`。他のライフサイクル操作と同じ）。他テナントの管理者が横から他人の
利用者を指せる経路にはならない。

### 自分自身にも実行できる（管理者経路）

無効化・削除・MFA 解除の自己禁止は誤操作によるロックアウトの防止が目的である。この操作は
ログイン状態を切らないので、ロックアウトが起きない。ロック解除（AP6）と同じ扱いにする。

### step-up は要求しない

セッションの失効に本人確認を挟むのは、セッションを盗んだ側が**本人の端末を先に切って
締め出せる**ためだった。この操作は誰も締め出さない（アプリが黙って取り直すだけ）。
安全側へ倒すための操作に本人確認の壁を置くと、心当たりがある利用者ほど押せなくなる。

### 失敗したらどうするか

**両方とも fail-closed。** 失効そのものが操作の目的で、他に守るものが無い。ここで成功を
返すと「入れ替えたつもりで古い鍵が生きている」を画面が肯定してしまう。ADR-0045 の
パスワード変更を fail-open にしたのと基準は同じ（失敗したときに利用者が取れる行動で決める）
——あちらは既にパスワードが変わっていて押し直しても同じ結果にならないが、こちらは画面が
残っていて押し直せる。

### 0 件を成功として、そう伝える

生きているトークンが 1 本も無くても成功とし、**落とした本数を返して画面が出し分ける**
（「無効にするトークンはありませんでした」）。同じ「完了しました」だけを返すと、効いて
いないのか元から無いのかが分からない。管理コンソールの MFA 解除・ロック解除と揃えた。
そのために `RefreshTokenRepository::revoke_all_for_user` の戻り値を `()` から行数へ変えた。

## 選択肢と理由

- **案A（採用）: 失効だけを行う操作を新設し、本人と管理者の両方に置く。**
- 案B: 本人（セルフサービス）だけに置く。管理者は既存の無効化・パスワード再発行で代用する。
  **ヘルプデスクに届く相談は「本人が操作できない」ときが多い**（端末が手元にない・本人が
  手順を追えない）。代用は必ず利用者の作業を止めるので、相談のたびに天秤に掛けることになる。
  不採用。
- 案C: 連携済みアプリの行ごとに「再発行」を置く（クライアント単位）。粒度は細かいが、
  **どのアプリの鍵が漏れたか分かっている人にしか使えない**。この操作の想定は「どれか
  分からないが心当たりがある」で、そこには一括しか効かない。1 つのアプリだけを外したい人には
  連携解除がある。不採用。
- 案D: セッションも一緒に落とす（＝実質「全端末サインアウト」）。押した本人が締め出される。
  それが欲しい人にはセッションの失効が既にあり、名前も結果も違う操作を同じボタンに
  まとめない。不採用。

## 影響

良い点:

- 「鍵だけ替える」が 1 手で済む。パスワードを変えずに、業務も止めずに、心当たりへ応えられる。
- 監査に `refresh_token.revoked` が残る（本人経路は `self_service_reissue`、管理者経路は
  対象と本数）。トークンの値もハッシュも記録しない。
- 統合テスト（`crates/api/tests/token_reissue.rs`）で実 DB を通し、**更新が断られること**と
  **セッションが残ること**を同じテストで確かめている。片方だけでは、この操作が
  「効いていない」のか「切りすぎ」なのかを区別できない。

トレードオフ:

- アクセストークンは**その寿命（既定 15 分）まで有効なまま**である。自己完結型 JWT なので
  失効が即時に効かないのは設計上の受容点で、即時性が要るなら `revoked_access_tokens`（F5）を
  使う。画面の文言では「次のアクセスで取り直す」とだけ言い、即時に切れると読める表現は避けた。
- ネイティブアプリのように、ブラウザの SSO セッションを共有しない実装では**再ログインを
  求められる**ことがある。確認ダイアログでその可能性に触れている。

やり残し:

- 管理者は「対象利用者が何本のトークンを持っているか」を事前に見られない（押した結果の
  本数で分かるだけ）。一覧に出すには管理 API 側に列挙が要る。この ADR の範囲外とした。
