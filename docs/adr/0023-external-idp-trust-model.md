# ADR-0023: 外部 IdP の同一性は `iss` + `sub` だけで決め、自動連携はオプトインにする

- 日付: 2026-08-08
- 状態: 採用
- 関連: ADR-0009（テナント独立）、ADR-0018（Cookie 非依存のハンドオフ）、
  `migrations/0024_external_identity_providers.up.sql`、`docs/Progress.md` AP12（SAML）

## 背景

テナントが自社の既存 IdP（Entra ID・Google Workspace 等）を認証元として使えるようにする（AP10）。
外部 IdP を受け入れるということは、**本 IdP の利用者アカウントを外部の主張に紐づける**ことなので、
「何をもって同じ人と見なすか」を決めないと、外部 IdP を 1 つ登録した時点でアカウント乗っ取りの
経路になりうる。

具体的な危険は 2 つある。

- **メールアドレスを同一性の根拠にすると乗っ取れる。** 攻撃者が自分の管理する外部 IdP、あるいは
  外部 IdP 内で自由に変更できるメール属性に被害者のアドレスを設定すれば、被害者のアカウントで
  ログインできてしまう。メールは「連絡先」であって識別子ではない。
- **管理者が入れた URL をサーバが叩く。** 外部 IdP のエンドポイントは管理者入力で、本 IdP の
  サーバがそこへ HTTP 要求を出す。素通しなら SSRF の踏み台になる。

## 決定

### 1. 同一性は `iss` + `sub` のペアのみ

`user_external_identities` は連携時の `iss` を `external_issuer` として保存し、**引くときも
`iss` + `sub` の両方で絞る**。`(provider_id, external_subject)` を UNIQUE とし、
`(user_id, provider_id)` も UNIQUE にして、1 人が同じプロバイダに複数の外部 ID を持てない
ようにする（どちらが正か決められなくなるため）。

`iss` を条件から外して `provider_id` + `sub` だけで引くと、**管理者がプロバイダの `issuer` を
別の IdP へ張り替えたとき、新しい IdP にある同じ `sub` のアカウントが以前の利用者に化ける**。
`iss` が変われば既存の連携は引けない（＝未連携として拒否する）のが正しい振る舞いで、
連携し直しを求める。

**メールアドレスは同一性の根拠にしない。** プロフィールの更新にも使わない。

### 2. 既定は「事前に連携済みの利用者しかログインできない」

未連携の外部 ID でログインしてきたら拒否する（利用者の自動作成もしない）。テナントの利用者を
増やす経路は招待・自己登録に限り、外部 IdP を登録しただけでは増えない。

### 3. 自動連携はプロバイダ単位のオプトイン + `email_verified` 必須

`allow_auto_link` を有効にしたプロバイダに限り、外部 IdP が **`email_verified: true` を返した場合**
だけ、同じメールアドレスの既存利用者へ連携する。どちらか一方でも欠ければ連携しない。

「外部 IdP のメール検証を信用する」という判断は本 IdP には下せない（外部 IdP の運用次第）ため、
テナント管理者に明示的に選ばせる。既定は無効。

### 4. ID Token の検証はポートの実装内で完結させ、検証済みクレームだけを外へ出す

`ExternalOidcClient` トレイトの契約を「**返るのは検証済みのクレームだけ**」とする。
JWKS による署名検証・`iss` 一致・`aud` 一致・`exp`・`nonce` 一致は実装（infrastructure）の中で行い、
未検証のトークンや生の JWT を application 層へ渡さない。

検証を呼び出し側の責務にすると、経路が増えたときに「どこかで検証を忘れる」余地が残る。
型として「検証済みしか出てこない」ようにすれば忘れようがない。

### 5. エンドポイント URL は https のみ・内部宛先を拒否する

`issuer` / `authorization_endpoint` / `token_endpoint` / `jwks_uri` は登録時**と更新時の両方**で、
https であることとループバック・プライベート・リンクローカルでないことを検査する。
登録時だけ見ても、更新で差し替えられれば意味がない。

### 6. 認可フローの続きは api が進める

外部 IdP から戻った時点で OIDC 認可フローの途中だった場合、**その続き（認証済みの記録・同意確認・
authorization code の発行）も api が行い**、web には戻り先の URL を返すだけにする。認可要求の
パラメータ（`client_id`・`redirect_uri`・PKCE・`nonce`）は api 側の `auth_sessions` にしか無く、
web には組み立てようがない。他のログイン経路（パスワード・MFA・パスキー）と同じ責務分担で、
共通部分は `CodeIssuanceService` に寄せてある。

auth_session が既に期限切れなら、外部 IdP での認証自体は成立しているので SSO は発行したまま
アカウント画面へ戻す（RP へは戻れないが、ログインし直しは要らない）。

### 7. `state` はブラウザ Cookie に置かず、DB の進行状態で照合する

`external_login_requests` に `state` のハッシュ・`nonce`・PKCE の `code_verifier`（暗号化）を持ち、
外部 IdP から戻ってきた `state` を鍵として引く。ADR-0018 と同じ理由で、api はブラウザ Cookie を
読まない。`state` はワンタイムで、期限切れは再開できない。

## 影響

- 外部 IdP を登録しても、利用者ごとに一度は連携操作（またはオプトインした自動連携）が要る。
  「登録すれば全社員が即ログインできる」ではない。運用の手順は `docs/OPERATIONS.md` に置いた。
- クライアントシークレットは暗号化して保存し、**読み出す API を持たない**。管理 API の応答は
  `has_client_secret` の真偽だけを返す。
- 対応プロトコルは OIDC のみ。`external_identity_providers` の列が OIDC 前提
  （`jwks_uri` / `token_endpoint` 等）のため、SAML を足すなら `protocol` 列とプロトコル固有設定の
  置き場所を決める設計判断が別途要る（AP12）。
  なお本 IdP を **SAML の IdP として**振る舞わせる側は既に別に存在しており、向きが逆である。

## 却下した案

- **メール一致で常に自動連携する。** 導入は楽だが、外部 IdP のメール属性を信用することと同義で、
  上記の乗っ取り経路をそのまま開ける。
- **未連携の外部 ID で利用者を自動作成する（JIT プロビジョニング）。** テナントの利用者を外部の
  主張だけで増やせることになり、ADR-0009 のテナント独立（誰がテナントに属するかはテナントが決める）
  と衝突する。要望が出たらプロバイダ単位のオプトインとして別途設計する。
- **`state` を Cookie に置く。** 一般的な実装だが、api がブラウザ Cookie を読むことになり
  ADR-0018 を崩す。DB に進行状態を持つのは `auth_sessions`・`saml_sso_requests` と同じ形なので、
  この方が既存と揃う。
