# ADR-0029: テナントにドメインを紐づけ、ゲストの所属元を識別子から決める

- 日付: 2026-08-24
- 状態: 採用
- 関連: ADR-0009 §8（認証の対象テナント・ログイン識別子の解決）、ADR-0025（ログイン識別子の登録簿）、
  `docs/Progress.md` MT25、`docs/CHANGELOG.md` 2026-08-23（2）

## 背景

参加先テナントのログイン画面からゲストが入れるようにした（ADR-0009 §8 改訂、2026-08-23）。
解決は **所属元 → 参加先のゲスト** の順で、後者は「要求テナントに ACTIVE な GUEST メンバーシップを
持つ利用者を、**その利用者の所属元テナントの**登録簿で引く」という横断走査である。

ここで**一意性の範囲と解決の範囲がずれている**。

| | 範囲 |
|---|---|
| ログイン識別子の一意性 | 1 テナントの中（`user_login_identifiers` の一意キーは `(tenant_id, normalized_value)`） |
| 参加先テナントのログイン画面が解決する範囲 | そのテナントの HOME 利用者 **∪** 参加中のゲスト（各自の所属元の登録簿） |

ゲストは所属元をまたいで集まるので、同じユーザー名のゲストが 2 人参加した時点で、その入力は
2 人に当たる。解決は fail-closed（曖昧なら誰も返さない。MT25 で「不在」と型で区別した）なので、
**その 2 人とも参加先の画面から入れなくなる**。なりすましではなく締め出しで、しかも当人からは
「正しいパスワードなのに入れない」としか見えない。ゲストが増えるほど当たりやすい。

一意性を種別非依存にする処置（migration 0041）はテナント**内**の話で、ここには効かない。

## 検討して採らなかった案: 一意性をクロステナントへ広げる

識別子をシステム全体で一意にすれば解決の範囲と一致する。**採らない。** ADR-0009 §1 の
テナント独立が壊れる —— あるテナントが `admin` を取ると、他のどのテナントでも `admin` が使えなく
なる。テナントは互いに独立した管理境界であって、名前の在庫を共有する関係ではない。

Entra ID もこれはしていない。UPN がグローバル一意なのは**ドメイン接尾辞を 1 つのテナントが
所有している**からで、`alice@contoso.com` と `alice@fabrikam.com` は別物として共存する。
一意なのは全体空間ではなく「ドメイン × その中のローカル部」である。

## 決定

### 1. ドメインをテナントへ排他的に割り当てる（`tenant_domains`）

`domain` を**グローバルに一意**な列として持ち、1 つのテナントへ紐づける。テナント同士が
名前を取り合うことはない —— 取り合いの対象はドメインだけで、それは所有関係で決まる。

```sql
CREATE TABLE tenant_domains (
    id         CHAR(36)     NOT NULL,
    tenant_id  CHAR(36)     NOT NULL,
    domain     VARCHAR(253) NOT NULL,  -- 正規化済み（小文字・末尾ドットなし）
    created_at DATETIME(6)  NOT NULL,
    updated_at DATETIME(6)  NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY tenant_domains_domain_uk (domain),
    KEY tenant_domains_tenant_idx (tenant_id),
    CONSTRAINT tenant_domains_tenant_fk FOREIGN KEY (tenant_id)
        REFERENCES tenants (id) ON DELETE CASCADE
);
```

- 1 テナントは複数のドメインを持てる（合併・旧ドメインの併存）。1 ドメインは 1 テナントだけ。
- テナント削除で紐づけも消える（`ON DELETE CASCADE`）。ドメインは再び割り当て可能に戻るべきで、
  消えたテナントの名で押さえ続ける理由がない。

### 2. 割り当ては root の system 管理者だけが行う（所有の検証は後続）

`idp.system.admin`（root scope にしか存在しない。ADR-0009 §4）を要求する。**テナント管理者が
自分でドメインを主張できるようにはしない** —— グローバルに一意な資源なので、早い者勝ちにすると
他人のドメインを先に押さえられる。

DNS TXT レコード等による**所有の検証は本 ADR の対象外**とする。今の一意性の担保は
「グローバル一意 ＋ root が割り当てる」であり、これは運用者が確認したうえで登録する前提に立つ。
検証を足すときも、この表に `verified_at` を足して未検証の行を解決対象から外すだけで済む
（解決経路の形は変わらない）。

### 3. 解決に「ドメインで所属元を決める」段を挟む（home realm discovery）

ログイン欄の入力の解決を次の 3 段にする（先勝ち。ADR-0009 §8 の 2 段を 3 段へ）。

1. **要求テナントの登録簿。** 従来どおり。
2. **ドメイン修飾された入力なら、ドメインから所属元テナントを 1 つに決めて、そのテナントだけを引く。**
3. **それでも空振りなら、参加中のゲストを横断走査する。** 従来どおり（曖昧なら拒む）。

2 の中身:

```
入力が local@domain の形で、domain が割り当て済み（テナント T、T は ACTIVE）なら
  a. T の登録簿を入力そのままで引く      … メール種別の識別子に当たる
  b. a が空振りなら local で引く          … UPN 形式（alice@corp.example → T の alice）
  解決できたら「要求テナントで ACTIVE なメンバーか」を確認する（is_active_member）
```

**この段では曖昧さが原理的に起きない。** 引くのは 1 テナントの登録簿だけで、その中では
1 正規化値が 1 人のものだからである（migration 0041）。横断走査を通らないので、同名のゲストが
何人参加していても互いに干渉しない。

**2 を 3 より先に置く。** ドメイン修飾は「どの組織の誰か」まで言い切った入力であり、
言い切っていない入力（裸のユーザー名）のための走査より precise である。

**b（ローカル部での解決）は、ドメインを割り当てたことの帰結である。** テナント T に
`corp.example` を割り当てるとは、`<識別子>@corp.example` が T の利用者を指す、と宣言することに
等しい。これは「メールでのログインはテナントが明示的に有効化したときだけ」（ADR-0025 §5）と
矛盾しない —— `alice@corp.example` は**そのアドレスにメールが届くこと**を意味しないし、
`users.email` を引きもしない。引くのは登録簿だけで、増えるのは principal ではなく**綴り方**である
（パスワードは従来どおり要る）。

a を先に引くのは、メール種別の識別子を明示的に登録している利用者を、UPN 解釈で別人へ振り替えない
ためである（T の中で `alice@corp.example` を持つ人と `alice` を持つ人は別人であり得る）。

**その裏返しとして、識別子の追加時にも UPN 解釈を見る。** ドメインを割り当てたテナントでは
`ローカル部@そのドメイン` は「ローカル部の利用者」を指す綴りでもあるので、その綴りを他人の識別子
として登録できてはならない —— 登録できると a が先に当たり、当人がその綴りで入れなくなる（横取り）。
参加先テナントの画面ではそれが唯一の入り口になり得るので、実害が出る。空き判定
（`login_identifier_management` の `ensure_available`）はログインの解決と**同じ範囲**を見る。

### 4. 要求テナントが自分でドメインを持っていてもよい

2 は「所属元 = 要求テナント」の場合も同じ経路を通る。要求テナント X が `x.example` を持つなら、
X の HOME 利用者は X のログイン画面で `alice@x.example` と打っても入れる。1 が入力そのままで
空振りしたあと 2 の b が拾う。ゲスト用の特別扱いにしないことで、規則が 1 本で済む。

### 5. 走査（3 段目）は残す

裸のユーザー名と、割り当てられていないドメイン（`gmail.com` 等の一般提供のアドレス）は
2 に掛からない。ここを落とすとゲストの多くが参加先の画面から入れなくなる（2026-08-23 に直した
問題に戻る）ので、走査は残す。**したがって本 ADR は加算的で、既存の識別子の使い勝手を変えない。**

締め出しが起きている同名ゲストの救済は、運用としては「所属元テナントにドメインを割り当て、
当人にはドメイン修飾で入ってもらう」になる。この運用手順は `docs/OPERATIONS.md` に置く。

## 影響

- ドメインを割り当てたテナントの利用者は、参加先テナントの画面から**曖昧さに関係なく**入れる。
- 認証のホットパスに増えるのは、入力が `local@domain` の形のときの**一意キー 1 本の等値検索**だけ
  （`tenant_domains_domain_uk`）。形が合わない入力（裸のユーザー名）では DB を引きすらしない。
- 解決の増分はテナント解決の TTL キャッシュに載せない。割り当ての取り消しが最大 TTL 分効かない
  状態を作らないためで、テナントの `ACTIVE` 判定（ADR-0009 §8）と同じ扱いである。
- 監査には `tenant.domain_added` / `tenant.domain_removed` を残す。ドメインの割り当ては
  「誰のログインをどのテナントへ向けるか」を決める操作であり、権限付与と同じ重さがある。

## 残る限界（承知のうえで受け入れる）

- **所有の検証がない。** 割り当てを誤ると、そのドメインを名乗る入力が誤ったテナントへ向く。
  誤った先で解決できなければ入れないだけ（3 段目へは落ちない＝ 2 で `NotFound` を返して終わる
  わけではなく、2 が空振りなら 3 へ進む）だが、**正しくないテナントに同じローカル部の利用者が
  居ると、その人として解決される**。root の system 管理者しか割り当てられないことと監査で担保する。
- **裸のユーザー名の締め出しは残る。** 3 段目の走査は依然として曖昧になり得る。これを完全に
  無くすには「参加先の画面では裸の識別子を受け付けない」まで進める必要があり、ドメインが
  行き渡っていない段階でそれをやると多くの利用者が入れなくなる。段階を分ける。
- **IDN は A ラベル（punycode）で登録する。** Unicode のドメインをそのまま受け付けない。
  入力側の `local@domain` も同様に扱うため、U ラベルで打たれた入力は 2 に掛からず 3 へ落ちる。

## 非対象（フォローアップ）

- DNS TXT による所有の検証（`verified_at` 列と、未検証を解決対象から外す判定）。
- テナント管理者が自テナントのドメインを**参照**する API（今は root だけが見られる）。
- ログイン画面で所属元テナントを選ばせる UI（ドメインが無い利用者向けの救済）。
