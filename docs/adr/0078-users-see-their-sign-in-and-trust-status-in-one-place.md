# ADR-0078: 本人が自分のログインと信頼している持ち物の状況を 1 か所で見られるようにする

- Status: Accepted
- Date: 2026-11-05
- 関連: task #896（親 #867「宅内への侵入に気付けるようにする」）、ADR-0071（自分の端末）、ADR-0073（ログイン履歴）、
  ADR-0072（SSH の鍵）、ADR-0074（DBSC）、ADR-0075（DPoP）、ADR-0076（見えない枠）、ADR-0077（認証アプリの承認）

## 背景

「アカウントのセキュリティ」には自分の端末・ログイン履歴・SSH の鍵・認証アプリ・ログイン状態・連携アプリが**別々の一覧**で
並んでいた。次のことはどこにも出ていなかった。

- このブラウザのログイン状態が端末の鍵に結び付いているか（DBSC）、そのため長さが 30 日か 7 日か、とその理由
- ログイン状態ごとの、登録した端末か・結び付きか・認証アプリで承認して入ったか
- アプリのリフレッシュトークンが DPoP で結び付いているか、Web 版はリフレッシュトークンを持たず見えない枠で続けていること
- 組織の設定（知らせ・SSH の鍵・長さ）が自分に何を効かせているか

持ち主（2026-11-05）:「それらを網羅的に確認できる手段がほしい」。

## 決定

1. **画面の先頭に「状況」の欄を 1 つ置き、下の既存の一覧はそのまま残す。** 読むだけで、変える操作は下の欄へのリンク。
   中身は「このブラウザ」「信頼している持ち物」「アプリとトークン」「組織の決まり」と、直近 30 日の注意（あれば上に赤で）。
   「ログイン状態」の表の各行にも、端末・結び付き・入り方・長さの根拠を添える。
2. **内部の口を 1 本足す（`POST /internal/account/security/status`）。** 既存の口（端末・履歴・SSH の鍵・認証アプリ）を web から
   束ねるのでなく、api の `SecurityStatusService` が 1 回で組み立てる。結び付き・承認・端末の登録はどれも
   `sso_session_contexts` の 1 行に集まっていて、ログイン状態ごとに突き合わせるには api の中で読むのが素直なため。
   読む表は既存のものだけ（読み取りモデル `SecurityStatusQuery`）。**migration は無い。**
3. **長さの根拠は、長さを決めるのと同じ判定から取る。** `session_key::lifetime_basis` を足し、`lifetime_for` もこれで長さを選ぶ。
   画面の説明（「結び付き かつ 登録済み → 30 日」）と実際の長さが別々の判定で食い違わない。根拠は 5 つ:
   結び付き＋登録済み（長い）・認証アプリの承認（長い）・結び付きだが未登録（短い）・結び付きなし（短い）・
   条件は満たすが組織の設定が延ばさない（短い）。承認と結び付きが両方あれば承認を採る（確立のときに長さを決めたのは承認）。
4. **「このブラウザ」の名乗り・接続元・国は、ログインしたときでなく今の要求から読む。** 国は ADR-0071 と同じく、信じてよい
   ときだけ（家の中からは無い、と明記する）。短い Cookie（`__Host-sso_bound`）の期限は web が値から読む
   （`session_key::bound_cookie_expires_at`。値は HMAC で守られ、DB に置かない）。
5. **アプリのトークンは「種別」を出す。** 有効なリフレッシュトークンの数と、そのうち `dpop_jkt` のある数から
   「なし（Web 版は見えない枠で続ける）」「DPoP で結び付き」「結び付きなし」「混在」を決める。並べるのは、同意したアプリ・
   有効なリフレッシュトークンのあるアプリ・直近 30 日にトークンを出したアプリ。アクセストークンは保存しないので説明だけ。
6. **注意は既にある記録から数える。** 使い回し（`sign_in_app_usage.refresh_reuse_detected_at`）・別の鍵の署名
   （監査 `sso_session.key_rejected` の `key_mismatch` と `refresh_token.dpop_key_mismatch`）・登録していない端末でのログイン
   （`sign_in_history.device_registered = FALSE`）・断られたログインが 1 日 5 回以上の日。
7. **本人だけ。** 利用者は SSO セッションの持ち主で決まり、利用者 id を受け取らない。他人の状況を見る管理者の画面は作らない。
8. **「状況」が読めなくても画面は出す。** 下の一覧はそれぞれ別の口で読めるので、欄の代わりに案内を出す。

## 理由

- 1 つの口にしたのは、ログイン状態ごとに「端末・結び付き・承認・長さの根拠」を突き合わせる処理を web に持たせると、
  web が DB の都合（`sso_session_contexts` の列の意味）を知ることになるため。
- 長さの根拠を別に書くと、長さの決まりを変えたときに画面だけ古い説明を出し続ける。

| 採らなかった案 | 捨てた理由 |
|---|---|
| web が既存の口を束ねて組み立てる | 結び付き・承認は既存の口のどれも返さない。結局 api に口が要る |
| 状況を別の画面にする | 「一か所で」を満たさない。下の一覧と行き来できない |
| 根拠を画面の側で推し量る | 長さの判定と二重になり、食い違う |
| OS の版を User-Agent Client Hints で取る | Chrome は名乗りの版を固定している。取るなら別の課題（範囲外） |

## 結果

- 「アカウントのセキュリティ」の先頭に「状況」が出る。下の各欄はそのまま。
- ⚠ SSH の鍵の「最後に使った時刻」は assay からは見えない（使われるのは各機器）。画面にそう書く。
- ⚠ パスキーが同期型か（端末をまたいで複製されるか）は出さない（登録の記録に残していない）。
