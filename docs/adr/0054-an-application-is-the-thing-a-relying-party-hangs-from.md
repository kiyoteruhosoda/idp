# ADR-0054: アプリという段を置く（アプリ ＞ 認証方法、アプリ ＞ 利用ユーザー）

- Status: Accepted（決定 7 のうち「サービスアカウントの扱い」は ADR-0059 の決定 4 で置き換え）

## 背景

assay に「アプリ」という実体が無い。あるのはプロトコルごとの設定が 2 本、独立して並んでいるだけである。

| | 表 | 鍵 | 本番の件数（2026-09-15） |
|---|---|---|---|
| OIDC の RP | `clients` | `(tenant_id, client_id)` | **23** |
| SAML の SP | `saml_service_providers` | `(tenant_id, entity_id)` | **0** |

2 つの間に関係が無い。`saml_service_providers` は `clients` を参照しておらず、独自の
`display_name` と `enabled` を持つ。**同じアプリが OIDC と SAML の両方で繋がる**という、ごく普通の
形が表せない。

### 欠けているのは利用者の割り当てだけではない

OIDC の client にだけぶら下がっていて、SAML からは使えないものが 5 つある。

- **認証ポリシー**（`authentication_policies.conditions` の `client_ids`）——**SAML のアプリには
  MFA を要求できない**
- `client_permissions`（機械の権限）
- `client_resources`（トークンの宛名。ADR-0042）
- `client_consents`（同意）
- back-channel logout の配信先（ADR-0053）

**「利用ユーザーの割り当て」を `clients` にぶら下げると、この一覧に 6 つ目が並ぶだけになる。**
先に上の段を作る。

### 誰がどのアプリを使ってよいかを決める場所が、どこにも無い

いまは RP が 7 本それぞれ自前の名簿で断っている。同じ判断が 7 か所にあり、作りが揃っていないので
（ADR-0049 の G10）、1 本で書いた直しは配れない。assay 側に場所が無いことが原因である。

### いま入れるのがいちばん安い

- SAML の SP は**本番に 0 件**。
- `authentication_policies` は**本番に 1 行だけ**で、条件は `{"requested_acr":["urn:assay:ac:mfa"]}`
  ——**`client_ids` を使っている行が 1 つも無い**。

つまり**移すデータが両方とも無い**。23 件の client をアプリ 1 件 ＋ OIDC binding 1 件へ開くだけで
済む。SAML を使い始めてからだと、両方を抱えたまま直すことになる。

## 決定

**アプリを上、プロトコルを下にする。利用者・ポリシー・停止はアプリの段に付ける。**

```
アプリ（applications）
 ├ 表示名 / 有効・無効 / 割り当てモード
 ├ 認証方法（application_bindings）
 │    ├ OIDC → clients
 │    └ SAML → saml_service_providers
 └ 利用ユーザー（application_assignments）
```

1 つのアプリに 0〜N の binding。プロトコルを足しても、利用者もポリシーも付け直さなくてよい。

### 1. 割り当てにロールを持たせない

割り当ては「使ってよいか」の **1 ビットだけ**である。アプリの中で何をしてよいかは RP が持つ
（ADR-0033 / ADR-0049 の I6）。列を用意すると、G7 で消した `groups` を別の名前で作り直すことになる。

**rewardpointsweb も例外ではない。** むしろいちばんはっきりした例である ——あのアプリのロール
（親／子）は完全にローカルの概念で、**子どものアカウントは assay に存在しない**（メールアドレスを
持たないので SSO で入れない）。assay が配れるロールは初めから無い。

⚠ **そもそもアプリごとに選べる類の設定ではない。** 割り当てにロールの列を持つか持たないかは
**モデルの形**なので、全アプリで一様になる。

### 2. 割り当てが無い相手は、assay の画面で断る（RP へ戻さない）

- 文言は「このアプリの利用が許可されていません」＋ **アプリ名** ＋ 管理者へ頼む導線。
- ⚠ **理由を伏せない。** 判定は認証の**あと**（認証するまで誰なのか分からないので、これは実装の
  都合ではなく順序の必然である）。隠す意味が無く、黙って弾くと利用者からは障害と区別が付かない。
- ⚠ **利用者からは「入れたのに弾かれた」に見える。** 認証は通っている、という事実を文言で埋める。
- 監査ログに 1 行（誰が・どのアプリへ）。

### 3. アプリごとに「全員 / 個別」を選べる。**既定は「個別」**

| 設定 | 意味 |
|---|---|
| **個別**（既定） | 割り当てられた利用者だけが使える |
| 全員 | そのテナントの利用者は誰でも使える |

- ⚠ **「全員」はテナントの中だけを指す。** 他テナントの利用者を含めない。
- ⚠ **既定を「全員」にしない。** 絞り忘れたアプリが全員に開いたままになる ——**開いていることに
  誰も気付かない**のが、この手の既定の怖さである。
- ⚠ **「個別」が既定だと、作った直後は誰も入れない。** 登録の画面で**「自分を割り当てる」を初めから
  チェックしておく**（作った本人が締め出される形にしない）。
- ⚠ **「個別」で名簿が空**は「全員」ではなく「誰も入れない」。**取り違えると全断**になるので、
  保存時に確認を挟む。
- ⚠ **既定が「個別」でも、自動生成の野放しは直らない。** blobshare は assay に居る人が SSO を押すと
  利用者が自動で生える。絞りたいアプリは明示的に割り当てを管理すること。

### 4. 移行は「最初から個別」。いま入れている人を data から書き出して割り当てる

この案の弱点は「書き出しに漏れた人が入れなくなる」ことなので、そこを手順で潰す。

1. **名簿を data から作る。** 記憶や台帳からではなく、**実際に入れる人**を 2 つの経路から集めて
   和を取る:
   - RP の `federated_identities` にある利用者（＝実際に assay で入ったことがある）
   - RP の有効なローカル利用者のうち、assay 側に対応する利用者が居るもの
     （⚠ **まだ結び付いていないが入れるはずの人**。ここが漏れやすい）
2. ⚠ **先に「記録するだけ」で動かす。** 判定は入れるが**断らない**期間を置き、「割り当てが無いのに
   来た人」をログに溜める。**漏れはここで全部出る。**
3. ログが静かになってから、断るように切り替える。
4. ⚠ **切り替えの前に、割り当てを足す操作が数秒で終わることを確かめておく**（締め出しが起きた
   ときの復旧経路）。

⚠ **切り替えは設定で行う**（`APPLICATION_ASSIGNMENT_ENFORCEMENT`）。コードの入れ替えにすると、
戻すのにデプロイが要る。

### 5. 認証ポリシーの条件は `application_ids` へ寄せる

`conditions.client_ids` を `conditions.application_ids` に置き換える。寄せない限り**SAML のアプリは
ポリシーの外に残り、MFA を要求できない**。

`client_ids` と `service_provider_ids` を並べる案は、**プロトコルが増えるたびに条件が増える**ので
取らない。

### 6. 判定は authorization code の発行地点に置く

判定は `CodeIssuanceService::issue` の中 ——**code を発行できる唯一の経路**——に置く。ログイン・
MFA・パスキー・外部 IdP・パスワード変更・同意・SSO 復元の 7 経路はすべてここへ集まるので、
**判定を通らずに code が出ることが構造的に起こり得ない**。認証ごとの経路に判定を書き写すと、経路が 1 つ増えるたびに
書き忘れが門を開ける。

### 7. 新しく登録した RP も、その場でアプリとして開く

> ⚠ **ADR-0059 で補った。** サービスアカウントはアプリではなく、アプリの**名乗り**か**使う主体**である。
> 本決定は登録時にアプリを作らないところまでで、移行 0054 が既存のサービスアカウントに作った
> アプリは残っていた。移行 0058 で消し、どのアプリの名乗りにするかは人が結び付ける。

管理 API で RP（`authorization_code` の client）を登録すると、**アプリ 1 件 ＋ OIDC binding 1 件**が
同時にできる。移行が既存の 23 件へしたのと同じ形で、割り当てモードは「個別」、登録した本人が
名簿に入る。

⚠ **開かないと、その RP は「誰が使ってよいか」の外に落ちる。** 判定はアプリを持たない client を
素通しするので（下の帰結）、登録しただけの RP は**全員に開いたまま**になり、しかも開いていることが
画面のどこにも出ない ——既定を「個別」にしてまで避けたはずの形が、新しい RP からだけ復活する。

開くのは**利用者がブラウザで入る RP だけ**。`client_credentials` のサービスアカウント（ADR-0038）
には入る利用者が居らず判定も走らないので、空の名簿を持つアプリが並ぶだけになる。

⚠ **アプリを開けなかったときも、RP の登録は成功として返す。** client は既に作られていて、ここで
失敗を返すと「エラーなのに RP は存在する」になる。アプリは画面から後で作れる。

## 捨てた案

### A. `clients` に割り当てをぶら下げる

いちばん小さく収まる。採らないのは、**OIDC 専用の口が 6 つ目になるだけ**だからである（背景の一覧）。
SAML を使い始めた日に、割り当てだけをもう一度上の段へ持ち上げることになる ——そのときには本番に
名簿が載っているので、いまより高く付く。

### B. 条件に `service_provider_ids` を並べる

`conditions` に `client_ids` と並べて `service_provider_ids` を足せば、SAML にもポリシーが効く。
採らないのは、**プロトコルが増えるたびに条件が増える**からである。条件の側はポリシーを書く人が読む
場所で、そこにプロトコルの都合を並べると「このアプリに MFA を掛けたい」が「このアプリの OIDC と
SAML の両方に MFA を掛けたい」という書き方に変わる。

### C. プロトコル表に `application_id` 列を足す（binding 表を作らない）

`clients` と `saml_service_providers` に nullable な `application_id` を足せば、join 表は要らない。
採らないのは、**`Client` 構造体・全 SELECT・管理 DTO・統合テストを巻き込む**ためである。この段階の
約束は「表と移行だけを入れて挙動を 1 つも変えない」ことで、ホットパスの構造体を触るとその約束が
確かめにくくなる。binding を独立させると、プロトコル設定の側は 1 文字も変わらない。

### D. アプリの一覧 API に「モード」を返す

RP から「このアプリは全員に開いているのか」を読めるようにする案。採らないのは、**RP 側に同じ分岐が
7 本できる**からである。一覧 API（#56）は、モードに関わらず**「このアプリを使ってよい利用者」を
同じ形で**答える ——「全員」ならテナントの有効な利用者、「個別」なら割り当てられた利用者。

## 帰結

- **停止がアプリ単位になる。** アプリを止めると、ぶら下がる binding が OIDC でも SAML でも一緒に
  止まる。プロトコルごとに止め方を覚えなくてよい。
- **移行した 23 件は、`clients.id` をそのまま `applications.id` として引き継ぐ**（binding も同じ）。
  別表なので値が重なっても衝突せず、移行が決定的・冪等になり、「このアプリはどの client から
  開いたか」を列を足さずに追える。⚠ **同一性を意味する制約は無い**（後からアプリ側だけを作り直せば
  当然ずれる）。
- **1 つのプロトコル設定は 1 つのアプリにしか属さない**（DB の UNIQUE）。両方に属せると、ポリシーと
  割り当てのどちらが効くのかが決まらない。
- **binding が無い client は、まだアプリを持たない。** 判定はこれを「割り当てが無い」とは扱わず、
  **移行漏れ**として区別する ——両者を混ぜると、移行の取りこぼしが「正しく断った」ように見える。
- **SAML 側の判定はまだ入っていない。** SP が 0 件のうちは掛ける相手が居ないためで、SAML を
  使い始めるときに `saml_sso` の発行地点へ同じ判定を置く。⚠ **これは意図して開けてある穴である。**
- **binding を外すと、その RP はまた判定の外へ出る。** 外した瞬間に「全員に開いた」状態へ戻るので、
  外すのは RP を別のアプリへ繋ぎ替えるときだけにする。
- **既に発行済みのトークン・セッションには効かない。** 割り当てを外しても、次に code を取りに
  来るまでは効き始めない。急いで止めるなら利用者かアプリを停止する（ADR-0053 の配信が走る）。
