# ADR-0014: ランタイム設定の反映は再起動で行い、未反映を画面で可視化する

- Status: Accepted
- Date: 2026-07-25
- 関連: `docs/adr/0010-zero-touch-deployment-and-configuration-provenance.md`（設定キーの出所区分）、
  `docs/adr/0013-web-shared-runtime-settings.md`（§1-a 起動時スナップショット、§5「反映タイミングは
  両サービスの再起動」・ホットリロードは MT27 で扱うとした）、`docs/Progress.md`（MT27）

## Context

ランタイム設定（`system_settings` の DB 上書き）は起動時にしか読まれない。設定画面で保存しても
api も web も挙動が変わらず、**運用者にはその事実が見えない**。保存が効いた前提で動作確認をすると
「保存したのに直らない」となり、原因が「反映していないこと」だと分からないまま設定値を疑い続ける。

ADR-0013 §5 はこの反映タイミングの扱いを本 ADR（MT27）へ送っていた。論点は 2 つある。

1. ホットリロード（再起動なしで反映）を導入するか。
2. しないなら、未反映であることをどう運用者へ伝えるか。

現状の性質を確認しておく:

- `Config` は起動時に一度解決され、`Arc<Config>` として全ハンドラ・全サービスへ注入される不変値である。
- ADR-0013 §1-a により、api が web へ配る共有設定は **api の起動時スナップショット**である。
  これは「web が api より新しい値を先取りしない」ことを構造的に保証している。
- SMTP 設定は参照のたびに DB を読むため既にホットである（`restart_required: false`）。
  再起動が要るのは TTL・Cookie 属性・HSTS といった、起動時に解決して配り切る値に限られる。

## Decision

### 1. ホットリロードは導入しない

反映は引き続き **api → web の順の再起動**で行う。理由:

- **ADR-0013 の不変条件を壊す。** api がリロードで新しい値を持つと、その瞬間から api の配る
  スナップショットが変わる。web は起動時にしか取りに行かないため「api だけ新しい値」の窓が
  リロードのたびに開く。web も追随させるには web 側にも配布・適用の仕組みが要り、
  ADR-0013 が避けた「両サービスの値が一時的にずれる」状態を自前で作り直すことになる。
- **不変値であることが安全性の根拠になっている箇所がある。** `COOKIE_SECURE`・`COOKIE_DOMAIN` は
  Cookie の発行と失効の両方で使う。発行時と失効時で値が変わると、消せない Cookie が残る
  （`Secure`/`Domain` が一致しない Cookie はブラウザが別物として扱う）。TTL 系も、発行済みトークンの
  寿命と新しい設定の関係を全ユースケースで定義し直す必要がある。
- **得られるものが小さい。** これらは日常的に変える値ではなく、変えるときは配置作業の一部として
  再起動できる。ホットにすべき設定（SMTP）は既にホットである。

### 2. 代わりに「保存済み・未反映」を設定画面で可視化する

再起動が必要なこと自体は避けられないので、**再起動し忘れが黙って残らない**ようにする。

- **api への未反映**: api の起動時スナップショット（`resolved_settings`）と、現在
  `system_settings` に保存されている値を突き合わせる。ずれていれば `pending_restart` として
  `GET /{tenant_id}/admin/system-settings` の応答に載せる。判定規則は
  `ResolvedSetting::is_pending_restart` を単一の出所とし、表示側で再現しない。
- **上書きの解除も未反映に含める。** 起動時に DB から採っていたキーの上書きを消しても、
  再起動するまで既定値には戻らない。ここを落とすと「解除したのに戻らない」が画面から見えない。
- **判定対象は `DbManaged` のキーだけ。** `EnvLocked` / `Builtin` は解決時に DB を一切参照しないため、
  `system_settings` に行が残っていても設定の解決には影響しない。これらを突き合わせると、出所区分を
  `DbManaged` から `EnvLocked` へ移したキー（`PUBLIC_WEB_BASE_URL`・`COOKIE_DOMAIN`。ADR-0012）の
  残存行がある環境で、**再起動しても消えない**警告が出続ける。しかも `editable` が false なので
  画面からその行を消すこともできず、警告が操作不能なまま居座る。
- **web への未反映**: web が起動時に受け取った共有設定と、api が現在配っている共有設定を
  設定画面の描画時に突き合わせる。ずれていれば「api は反映済みだが web が古い」状態で、
  これは **api だけを再起動した**ときに残る（ADR-0013 §Consequences が挙げた唯一のずれ方）。
- 画面には警告バナー（未反映のキー名と、api→web の順に再起動する手順）と、各行のバッジを出す。
- 各キーの説明には、api だけの再起動で足りるのか **api と web の両方**が要るのかを出す
  （`shared_with_web` を応答に載せる）。

### 3. 未反映の判定は補助表示であり、失敗しても画面は出す

web が api の共有設定を取りに行けなかった場合は「未反映なし」ではなく「判定できなかった」として
警告を出さずに画面を描画する。起動時の fail-fast（ADR-0013 §4）とは目的が違う。あちらは誤った設定の
まま動き続けないためで、こちらは設定画面そのものが見られなくなる方が運用上の害が大きい。

## Consequences

- 設定画面で保存した直後に「まだ効いていない」ことが分かり、どのサービスを再起動すればよいかも
  同じ画面から分かる。再起動後に画面を再読み込みして警告が消えることが、反映できたことの確認になる。
- 「api だけ再起動して web を忘れた」状態が検出できるようになる。これは ADR-0013 が構造的には
  防げないと認めていた唯一のずれ方で、可視化がその埋め合わせになる。
- 未反映の判定のために設定画面の描画で `/internal/runtime-settings` を 1 回呼ぶ。root の
  system 管理者しか開かない画面であり、負荷は問題にならない。
- secret（すべて `EnvLocked`）は起動時スナップショットに平文を残さないため比較できず、常に
  「反映済み」として扱う。現行の secret は DB 上書きを持ち得ないため実害は無い。
- ホットリロードが本当に必要になったら、まず対象キーを `restart_required: false` にできるか
  （参照のたびに DB を読める設計か）を個別に検討する。`Config` 全体をリロードする方向には進まない。

## Rejected alternatives

### `Config` を `ArcSwap` 等でホットリロードする

実装は可能だが、上記 §1 のとおり ADR-0013 の不変条件と Cookie の発行/失効の対称性を壊す。
設定の一部だけをリロード対象にするなら、それは「そのキーを `restart_required: false` にする」
のと同じことで、キー単位の判断に還元される。

### 設定保存時にサービスを自動再起動する

アプリが自分のプロセス管理へ介入することになり、配置形態（Compose・systemd・k8s）ごとに
別の仕組みが要る。設定画面の操作が無停止でなくなる副作用も大きい。

### 何もせず手順書だけで運用する（現状維持）

手順は既に `docs/OPERATIONS.md` にある。それでも「保存したが再起動していない」状態は
画面上まったく区別が付かず、手順を読んでいても取り違える。手順書は再起動し忘れを検出しない。
