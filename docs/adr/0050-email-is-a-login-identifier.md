# ADR-0050: メールアドレスを登録簿へ移し、ログインに使うかはテナントが決める

- Status: Accepted
- Date: 2026-09-13
- 関連: `docs/adr/0025-login-identifier-registry.md`（登録簿。AP8）、
  `docs/adr/0009-multi-tenant-architecture.md` §8（ログイン識別子）、
  `docs/adr/0049-attribute-ownership-and-the-federation-key.md`（属性の持ち主）、
  migration 0029（登録簿の導入）・0039（AP15b。主識別子の移送）・0041（種別非依存の一意性）

## 背景

要件が 4 つ出た。

1. メンバー一覧にユーザー ID（主たるログイン識別子）を出したい
2. メールアドレスでもログインしたい
3. メールアドレスを複数持ちたい
4. メールアドレスは一意にしたい

1 は独立した小さな変更で、先に入れた。残る 3 つは**同じ 1 つの歪みから出ている。**

いま利用者のメールアドレスは 2 か所にある。

| | 形 | 一意性 | ログインに使えるか |
|---|---|---|---|
| `users.email` | 1 利用者に 1 本・NOT NULL | `(tenant_id, email)`（`utf8mb4_unicode_ci` で大小無視） | **使えない** |
| `user_login_identifiers` の `email` 種別 | 何本でも | `(tenant_id, normalized_value)`（種別横断。0041） | 使える |

**この 2 つが同期していない。** 結果として次が成立する。

> A さんの `users.email` が `a@example.com` のとき、**B さんのログイン識別子として
> `a@example.com` を登録できる。** 登録簿には A の行が無いので一意制約に当たらず、
> `users` 側の一意制約にも当たらない（別の表なので）。

つまり要件 4（メールは一意）は、**いま既に破れている**。要件 2 と 3 は登録簿の側だけ見れば
今日でも満たせるが、この穴を残したまま「メールでログインできる」を広げると、
**他人のメールアドレスでログインできる識別子を作れる**状態が実際に使われる。

## 決定

### 1. `users.email` を登録簿の「主メール行」と同期する

主たるログイン識別子（ユーザー名）を AP15b で登録簿へ移したのと**同じ機構**を、メールにも当てる。

- 登録簿に `primary_email_of_user` 列を足す（`primary_of_user` と同型。`UNIQUE` で 1 利用者 1 行）
- `users.email` を書く経路（利用者作成・自己登録・管理者によるプロフィール編集）は、
  同じトランザクションで主メール行を同期する（`sync_primary_email_identifier`）
- 他人が同じ正規化値を持っていれば `Conflict`。判定は一意キーと同じ範囲（**種別で絞らない**）で行う

これで**一意性が登録簿の `(tenant_id, normalized_value)` 1 本に集まる**。要件 4 は
「メールどうしが一意」より強く、**ユーザー名・電話番号・社員番号とも衝突しない**形で満たされる。
同じテナントの中で、1 つの正規化値は 1 人のものになる。

### 2. 追加のメールアドレスは登録簿の行。主メールは基本的に有効

要件 3 は、登録簿に `email` 種別の行を足すだけで満たせる（画面も管理 API も既にある）。
主メール行は `is_active = 1` で作る（**プライマリアドレスは基本的に有効**）。

追加した行を有効にするかは、**今までどおり管理者が画面で選ぶ**。種別ごとの隠れた既定
（「メールだけは無効で作る」）は置かない —— 入り口の広さは決定 3 のテナントのスイッチが
1 か所で決めており、そこに 2 つ目の暗黙のつまみを足すと、なぜ一致しないのかを
2 か所調べることになる。

### 3. メールでログインできるかは**テナント単位のスイッチ**

`tenants.email_login_enabled`（既定 `false`。`self_registration_enabled` と同じ形）を足す。
解決時、`email` 種別の行は**このスイッチが入っているテナントでだけ**一致する。

migration 0029 は `users.email` を登録簿へ取り込まない理由をこう書いていた。

> 取り込むと「今日までメールでログインできなかった環境で、マイグレーションを当てた瞬間から
> メールでログインできる」ことになり、認証の入り口が黙って広がる。

**本 ADR はこの警告を捨てずに満たす。** 移行で行は入れる（要件 4 が即座に効く）が、
解決に参加するかはスイッチが決める。入り口が広がるのは、テナントの管理者が明示的に
開けたときだけである。

判定はテナントの行を見る 1 条件として解決の SQL に置く（`identifier_type <> 'email'` または
そのテナントのスイッチが入っている）。見るのは**識別子が載っているテナント**（＝利用者の
所属元）であり、要求元テナントではない。ゲストとして参加しているテナントの設定で、
所属元の入り口が開いたり閉じたりしない。

### 4. 主メールの付け替えが、通知の宛先の付け替えでもある

`users.email` は主メール行の写しであり続ける。パスワードリセット・メール検証・通知の送り先は
`users.email` を読む経路のままで、**どれも変更しない。** 主メールを差し替えれば宛先も動く。

「ログインの入り口」と「通知の宛先」を別々のつまみにしない。2 つに分けると
「届くけれど入れないアドレス」「入れるけれど届かないアドレス」が作れてしまい、
利用者から見て自分のアカウントの状態を説明できなくなる。

### 5. 主メール行は識別子単位では削除・変更できない

主たるユーザー名と同じ扱いにする（ADR-0025）。変えるならプロフィール編集、
止めるならアカウントの無効化である。個別に消せると `users.email` と登録簿が割れる。

### 6. 移行で「同じ値を自分が既に別の行で持っている」ときは、主メール行を作らない

ユーザー名を指定せずに作った利用者は、**ユーザー名がメールアドレスの文字列になっている**
（`user_management` / `register` の `unwrap_or_else(|| email.clone())`。ADR-0009 §8）。
この利用者は登録簿に `username` 種別で `a@example.com` の行を既に持っており、同じ正規化値で
`email` 種別の行を作ると一意制約（0041）に当たる。

**作らない。** その値は既にその利用者のものとして登録簿が守っており、要件 4 は満たされている。
行を 1 つに保つほうが、1 行へ 2 つの役割を負わせるより読める。

**この利用者はスイッチが `false` でもその値でログインできる**（`username` 種別として一致するため）。
不揃いに見えるが、**それは今日までの挙動そのもの**であり、本 ADR で新しく開く入り口ではない。
スイッチが約束するのは「メールアドレスという**種別**の識別子を解決に参加させるか」だけである。

他人が同じ正規化値を握っている場合は移行を**失敗させる**（0039・0041 と同じ方針）。
黙って 1 人を落とすと、その人だけが入れなくなる。

## 先行事例（Entra ID）

同じ問題に対する Microsoft Entra ID の形は、上の決定とほぼ一致する。裏付けとして残す。

| Entra ID | 役割 | 本 ADR での対応 |
|---|---|---|
| `id`（objectId。トークンの `oid`） | 不変の一意識別子 | `users.sub` |
| `userPrincipalName`（UPN） | ログイン識別子。メール形式だが**メールではない** | 主たるログイン識別子（ユーザー名） |
| `mail` | 主メールアドレス | `users.email` ＝ 主メール行 |
| `proxyAddresses` | **複数のメール。`SMTP:` が主、`smtp:` が別名。テナント内で一意** | 登録簿の `email` 種別の行 |
| Alternate login ID | **メールでのサインインをテナントのポリシーで有効化する** | `tenants.email_login_enabled` |

特に 2 点が同じである。**複数のメールを持ちつつ主を 1 つ決める**こと、そして
**メールでログインできるかをテナント単位で決める**こと。どちらも「そうしたほうが楽だから」
ではなく、そうしないと壊れるから各社が同じ形に落ち着いている。

Entra の運用で有名な躓きは **UPN と `mail` の乖離**である（ログインに打つ値と、名刺に書く値が
違う）。assay は「ユーザー名を指定しないとメールアドレスが入る」既定のおかげで初期状態では
乖離しないが、**その後メールを変更してもユーザー名は追随しない**ため、時間が経つと同じ乖離が
起きる。本 ADR は乖離自体は解消しない（ユーザー名は独立した識別子である、という立場を保つ）。
乖離した利用者が「メールでも入れる」ようになることで、実害のほうが小さくなる。

## 影響

- 移行後、登録簿の行数は利用者数ぶん増える（ユーザー名がメールと同じ利用者を除く）。
- `email_login_enabled` は既定 `false` なので、**移行を当てただけでは何も変わらない**。
- 管理コンソールのテナント設定にトグルが 1 つ増える。
