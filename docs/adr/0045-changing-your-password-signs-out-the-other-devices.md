# ADR-0045: 自分でパスワードを変えたら、他の端末とアプリを切る（自分は残す）

- Status: Accepted
- Date: 2026-09-08
- 関連: `docs/adr/0044-ending-a-session-revokes-its-refresh-tokens.md`（セッション終了と失効）、
  `crates/core/src/application/password_reset.rs`（リンク経由のリセット）、
  `crates/core/src/application/account_password.rs`（本 ADR の対象）

## 背景

パスワードを変える経路が 2 つあり、**片方だけが後始末をしていた**。

| 経路 | セッション | refresh token | 画面の文言 |
|---|---|---|---|
| メールのリンク経由のリセット（`password_reset`） | 全部消す | 全部落とす | 「既存のセッションはすべてサインアウトされています」 |
| **自分での変更（`account_password`）** | **何もしない** | **何もしない** | 「パスワードを変更しました。」 |

自分での変更は**嘘はついていない**（セッションについて何も約束していない）。問題は、
「漏れたかもしれないから変える」という動機で来た人にとって、**変えたのに前のパスワードで
入られた側が居座り続ける**ことである。パスワードを変える操作の目的が果たされない。

ADR-0044 でログアウトとセルフサービスの失効は塞いだが、この経路は残っていた。

## 決定

**自分でパスワードを変えたら、他の SSO セッションと、refresh token と、未消費の
authorization code を落とす。ただし今のセッションだけは残す。**

| 対象 | どうするか | 理由 |
|---|---|---|
| 他の SSO セッション | 消す | 前のパスワードで入った側を残さない |
| **今の SSO セッション** | **残す** | 消すと**変えた本人がその場で締め出される** |
| refresh token | **全部**落とす | アプリが持つ合鍵。手元のセッションが生きているので取り直しは SSO で素通りする |
| 未消費の authorization code | 落とす | リセット経路と揃える |

そのために `SsoSessionRepository::delete_all_for_user_except` を足した。

### なぜリセット経路と同じにできないか

`password_reset` が `delete_all_for_user` で全部消してよいのは、**あれが「パスワードを
忘れた人」の経路で、そもそも手元にセッションが無いから**である。設定画面からの変更は
ログイン済みの人が使うので、同じ関数を呼ぶと自分を締め出す。

### refresh token だけ「全部」なのはなぜか

SSO セッションは**ブラウザのログイン状態**で、いま操作している当人のものを消す理由が無い。
refresh token は**アプリが預かっている合鍵**で、パスワードを変えた以上は取り直させてよい。
手元のセッションが生きているため、取り直しは SSO で素通りする（利用者から見れば何も起きない）。

### 失敗したらどうするか

**fail-open**（警告ログのみ）。**パスワードは既に変わっており**、旧パスワードでのログインは
もうできない。ここで `Internal` を返すと「変わっていない」と読める応答になり、利用者は
変わったパスワードを知らないまま古いほうを使い続ける。リセット経路も同じ判断で
警告ログに留めている。

ADR-0044 のセルフサービスの失効を fail-closed にしたのと逆に見えるが、基準は同じ
——**失敗したときに利用者が取れる行動**で決めている。あちらは画面が残っていて押し直せる。
こちらは既にパスワードが変わっていて、押し直しても同じ結果にならない。

## 選択肢と理由

- **案A（採用）: 他を切り、自分は残す。**
- 案B: `delete_all_for_user` をそのまま呼ぶ（リセットと同じ）。**不採用。** 変更直後に
  自分が締め出される。「パスワードを変えたらログアウトさせられた」は不具合に見える。
- 案C: 何もしない（現状維持）。**不採用。** リセット経路との非対称が残り、変える動機を裏切る。
- 案D: refresh token も今のセッションぶんだけ残す。**不採用。** 合鍵を残す理由が無く、
  取り直しは SSO で素通りするので利用者の手間にならない。残す実装のほうが複雑になる。

## 影響

良い点:

- 2 つのパスワード変更経路が、**後始末について同じことをする**ようになった。
- 統合テストで「他端末は切れる・自分は残る・refresh token は落ちる」を実 DB で確かめている
  （`crates/api/tests/password_change_signs_out_other_devices.rs`）。**修正を外すと落ちる**
  ことも確認した。

トレードオフ:

- fail-open なので、DB が落ちている最中の変更は他端末を残す。警告ログには出る。
  **このとき画面は「この端末以外はサインアウトされています」と言ってしまう**——
  起きたことと食い違う唯一の窓である。DB が落ちている状況では他にも壊れているので
  ここだけ厳密にしても釣り合わない、と判断した。

文言も併せて直した:

- `user-settings-password-saved` を「パスワードを変更しました。**この端末以外は
  サインアウトされています。**」にした（en も同じ）。黙って他端末を切ると、**利用者は
  自分がやったことの結果を知らないまま**になる。リセット経路（`password-reset-success`）は
  元からこの一文を持っている。
