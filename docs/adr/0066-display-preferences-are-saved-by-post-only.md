# ADR-0066: 表示設定（言語・配色）の保存は CSRF トークン付きの POST に限る

- Status: Accepted
- Date: 2026-09-30
- 改めるもの: MT20 の「明示的な `?lang=` / `?theme=` があればログイン中はユーザー設定へ保存する」
  （`CLAUDE.md`「国際化」の言語決定順そのものは変えない）
- 関連: `docs/adr/0007-api-web-service-split.md` §4（管理コンソールの CSRF は web が閉じて扱う）、
  task #79（判断）・#118（設定画面・TOTP 設定の CSRF）

## 背景

表示言語と配色は web の `display_preferences` middleware が決める（決定順は `?lang=` > ユーザー設定 >
Cookie > `ui_locales` > ブラウザ > 既定。配色も同じ形）。この middleware は、有効な `?lang=` / `?theme=` が
あると (1) その画面の表示に使い、(2) Cookie を書き、(3) **ログイン中ならユーザー設定
（`users.language` / `users.theme`）へ保存していた**。

(3) は GET で、CSRF トークンも無い。SSO Cookie は `SameSite=Lax` なのでトップレベル遷移には載る。
つまり、署名済みの利用者に `?lang=en` を付けた assay の URL（どの画面でもよい。RP のログイン導線の
`/login?...&lang=en` も含む）を踏ませれば、誰でも保存済みの設定を書き換えられた。

実害は見た目だけ（資格情報・権限・セッションは動かず、利用者は設定画面で戻せる）だが、設計とも
ずれていた。

- `CLAUDE.md` の決定順の表では `?lang=` の用途は「**一時切替**」なのに、実装は保存までしていた。
- 同じ節で「RP の希望（`ui_locales`）を利用者の選択として残さない」と決めているのに、RP が `?lang=` を
  付ければ DB に残せてしまった。

加えて、設定画面の他の POST（表示名・パスワード）と TOTP の設定（確認コードの送信・削除）も CSRF
トークンを持たず、`SameSite=Lax` だけで守られていた（task #118）。

## 決定

### 1. GET の `?lang=` / `?theme=` は一時切替だけにする

middleware はユーザー設定へ書かない。`?lang=` / `?theme=` はその画面の表示と Cookie だけに効く。
ログイン中はユーザー設定が Cookie より強いので、一時切替は次の画面で保存済みの値へ戻る
（決定順の表の「一時切替」の意味どおり）。未ログインでは Cookie が前回選択として残る。

### 2. 保存は `POST /{tenant_id}/settings/display` だけ。CSRF トークンで守る

ユーザー設定へ書く経路はこの 1 本だけにする。受けるのは `lang` / `theme`（片方でよい）・`csrf_token`・
`return_to`。トークンはログイン後の他の画面と同じ `console_csrf_token`（SSO セッション id 由来の HMAC）で、
合わなければ何も保存せず、設定画面へ戻して `?error=csrf` のバナーで伝える。

保存したら Cookie も揃え（ログアウト後の前回選択として残る）、`return_to` の画面へ 303 で戻す。
`return_to` はこのテナント配下のパスだけを受け（step-up の `next` と同じ検査。オープンリダイレクトに
しない）、外れたら設定画面へ戻す。戻り先に残っていた `lang` / `theme` のクエリは落とす
（戻った先で一時切替が効き、保存が効いていないように見えるのを避ける）。

別端末への追随は従来どおり（保存先は DB で、ログイン中は DB が Cookie より強い）。

### 3. 管理コンソールのヘッダは、ログイン中は POST、未ログインは GET

ヘッダの言語ドロップダウンは共通レイアウト（`console/layout.html`）にあり、全画面から送られる。
トークンは `ConsoleAdmin`（ログイン中の全コンソール画面が共通レイアウトへ渡している struct）に
欄を 1 つ足して届ける。画面ごとのテンプレート struct には手を入れない。

戻り先（いまの画面の URL）は `assets/console.js` がフォームへ埋める。このドロップダウンは Bootstrap の
JS が無いと開かないので、JS を前提にして困らない。埋まらなければ設定画面へ戻る。

未ログイン（`admin` が無い画面）は従来どおり `?lang=` の GET（一時切替）で、Cookie だけで働く。

### 4. 設定画面と TOTP の設定の POST も同じトークンで守る

表示名・パスワードの変更（`/settings/name`・`/settings/password`）と、TOTP の確認コードの送信
（`POST /account/mfa/totp/setup`）・削除（`POST /account/mfa/totp/delete`）にも同じ
`console_csrf_token` を付けて照合する。合わなければ api へは何も送らない（設定画面・TOTP の設定画面・
認証器の画面へ `?error=csrf` で戻す）。TOTP は step-up より先に照合する（認証器の画面と同じ順）。

## 却下した案

- **GET は Cookie まで、保存は設定画面の POST だけ（ヘッダは Cookie だけ）**: 決定順は DB > Cookie
  なので、ログイン中にヘッダで Cookie だけ書いても次の画面で DB の値に戻る。ヘッダを設定画面への
  リンクに替える（手数が増える）か、決定順を Cookie > DB に変える（別端末への追随が弱まる）かの
  どちらかを伴い、使い勝手か設計のどちらかが後退する。
- **直さない（文書を実装に合わせる）**: 安いが、他人のリンクで保存済みの設定が変わる形と、RP が利用者の
  言語を決められる形が残る。

## 影響

- 外部の `?lang=` / `?theme=` リンクで保存済みの設定は変わらない。
- 利用者から見える操作はほぼ変わらない（設定画面のセレクタもヘッダのドロップダウンも、選べば保存されて
  別端末にも追随する）。
- 設定画面・TOTP の設定の古いタブ（トークンを持たないフォーム）から送ると、保存されずにバナーが出る。
  開き直せば送れる。
