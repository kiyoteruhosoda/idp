# ADR-0051: システム設定のうち SMTP だけは機械から入れられるようにする

- Status: Accepted
- Date: 2026-09-13
- 関連: `docs/adr/0037-management-api-access-tokens-and-permission-set.md` §4・§5（細粒度の権限セット。
  **本 ADR は §4 に例外を 1 つ足す**）、`docs/adr/0009-multi-tenant-architecture.md` §4（scope）、
  `docs/adr/0014-runtime-setting-rollout.md`（設定は画面から変える）、migration 0053

## 背景

SMTP を設定しないと、この IdP は**パスワード再設定のメールを送れない**。送れない間は、管理者が
利用者を作るたびに初期パスワードを本人へ手渡しすることになる。つまり「本人が自分で設定する」を
塞いでいるのは、設定が入っていないという 1 点である。

ところが、その設定を入れる経路が**人の手にしか無い**。

| | 保護 | 機械から叩けるか |
|---|---|---|
| `GET/PUT /{tenant}/admin/system-settings` | `idp.system.admin` | **叩けない** |

理由は 2 つあり、どちらも意図して置かれたものである。

1. ADR-0037 §4 — システム管理操作（テナントの作成・削除、**システム設定**、再起動、テナント横断の
   ログ参照）は細粒度へ分割しない。「root の権限を切り売りしない」
2. ADR-0037 §5 — クライアントへ `idp.system.admin` / `idp.tenant.admin` を**付与できない**
   （`client_permissions` の CHECK 制約 ＋ アプリ層の二重防御）

結果として、SMTP パスワードは**人が画面へ手で貼る**しかない。秘密が人の手とクリップボードを通り、
入れ直すたびに同じことを繰り返す。**秘密を運ばせないために作った仕組みが、秘密を運ばせている。**

## 決定

**システム設定のうち SMTP だけを、細粒度コードで開ける。**

### 1. `idp.smtp:read` / `idp.smtp:write` を足す（ADR-0037 §4 への例外）

分割するのは SMTP の 1 枚だけである。再起動・テナント作成・テナント横断のログ参照・SMS・ランタイム
設定は、引き続き `idp.system.admin` の完全一致だけが通る。

例外を認める理由は、**この 1 枚だけが「秘密を保管する場所」だから**である。他のシステム設定は
値を決めれば済むが、SMTP は資格情報そのものを預ける。機械から入れられないということは、
必ず人を経由するということで、それは §4 が守ろうとしている安全の逆を向く。

### 2. 口も別にする（`/admin/system-settings/smtp`）

既存の `PUT /admin/system-settings` を `idp.smtp:write` でも通るようにはしない。あの口は SMS と
ランタイム設定も同じ本文で受け取るので、**権限だけを細くしても、触れる範囲は細くならない**。

応答の型も分ける（`SmtpSettingsResponse`）。システム設定全体の型を使い回すと、将来その型へ足された
項目が、機械向けの応答からも一緒に出ていく。**開けた範囲を型で示す。**

パスワードは今までどおり**平文を返さない**（設定済みか否かのみ）。

### 3. この 2 つは root scope でしか持てない

`system_settings` はテナント列を持たない**システム全体**の表である。テナントの中で配れるように
すると、あるテナントの管理者が（機械を経由して）**全テナントのメール経路**を変えられる
——`idp.tenant.admin` では届かないところへ、その配下の細粒度コードで届いてしまう。

したがって:

- `TENANT_MANAGEMENT_CODES` に**入れない**（`idp.tenant.admin` は含意しない）
- `is_grantable_in_tenant` が root 以外で落とす（付与の側）
- エンドポイントも要求テナントが root でなければ 403（使う側。**二重防御**）

付与の側だけにしないのは、既に配られてしまった行と、将来テナントを増やしたときの取りこぼしが
残るからである。

### 4. 画面は今までどおり

管理コンソールの SMTP 欄（`idp.system.admin`）は変えない。**機械の口は人の口を置き換えない**
——idp が SMTP を入れられない状態のとき、復旧の手段が機械 1 本になるのは避ける。

## 選択肢と理由

- **案A（採用）: SMTP だけの細粒度コードと専用の口。** 開ける範囲が「メールの経路」で閉じ、
  型・経路・scope の 3 つで示せる。
- 案B: `idp.system.admin` をクライアントへ付与できるようにする。ADR-0037 §5 の二重防御を外すことに
  なる。機械の資格情報は人より長生きで失効の導線も弱い、という前提は変わっていない。
- 案C: SMTP を環境変数からも読めるようにする（`DB > env > 既定`）。宣言に置けて秘密も封印できるが、
  **「設定は画面から変える」（ADR-0014）から半歩外れる**。機械から入れたいという要求そのものは
  満たすので、案A を採らないならこれになる。
- 案D: 人が画面へ貼り続ける（現状維持）。秘密が人の手を通る回数が減らない。

## 影響

- `permissions` マスタに 2 行増える（migration 0053）。**既存の付与行は 1 行も書き換えない。**
- 付与の入口は既存のまま（`POST /{tenant}/admin/clients/{client_id}/permissions`、保護は
  `idp.clients:write`）。⚠ **`idp.clients:write` を持つ機械は、自分自身へこのコードを付けられる。**
  これは ADR-0037 が既に選んだ性質（細粒度コードは付与される側と同じ管理面にある）であり、本 ADR で
  変えていない。**root テナントに居るクライアントだけがその対象**である点が歯止めになる。
- 2026-09-13 時点で root テナントにクライアントは 1 つも無い。この口を使うには、まず root テナントへ
  機械のクライアントを登録する（公開鍵だけで登録でき、秘密は移動しない）。
