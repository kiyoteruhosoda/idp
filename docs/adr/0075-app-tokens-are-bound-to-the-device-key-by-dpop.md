# ADR-0075: スマホのアプリのトークンは DPoP で端末の鍵に結び付ける

- Status: Accepted
- Date: 2026-11-04
- 関連: task #893（親 #875「ログイン状態を端末の鍵に結び付け、長さを結び付けの有無で変える」・設計書 第 1 版の段 4）、
  ADR-0074（assay のログイン状態の DBSC。task #887）、ADR-0043（`acr`・`amr`）、ADR-0042（宛名）、
  RFC 9449（OAuth 2.0 Demonstrating Proof of Possession）、RFC 7638（JWK Thumbprint）

## 背景

スマホのアプリ（flutterbase 派生）は assay の public client として直接ログインし、リフレッシュトークン（30 日）と
アクセストークン（300 秒）を持つ。どちらも持っているだけで使える（Bearer）ので、バックアップ・root 化した端末・
ログへの書き出しなどでトークンが外へ出ると、別の端末からそのまま使われる。

設計書 第 1 版の段 4（持ち主の了承 11/04）: assay のトークンの口で `DPoP` ヘッダーを受け、アクセストークンに
`cnf.jkt` を入れ、リフレッシュトークンも同じ鍵に結び付ける。アプリは Android Keystore の取り出せない鍵（アプリごと）で
呼ぶたびに署名する。

## 決定

1. **DPoP を受けるのはトークンの口の `authorization_code` と `refresh_token` だけ。** `DPoP` ヘッダーに正しい証明が
   付いていれば、アクセストークンに `cnf: {"jkt": <鍵の指紋>}` を入れ、`token_type` を `DPoP` で返し、リフレッシュ
   トークンにも同じ指紋を記録する（`refresh_tokens.dpop_jkt`）。⚠ **証明が無ければ今までどおり**（Bearer・結び付け
   なし）。DPoP の無い今までのアプリは、写すまで何も変わらない。`client_credentials` は機械（サーバー）なので DPoP を
   見ない。認可の口の `dpop_jkt`（RFC 9449 §10）は受けない —— 認可コードは PKCE でそのアプリに結び付いている。
2. **証明の形。** `typ` は `dpop+jwt`、`alg` は **ES256 だけ**（Android Keystore の P-256 の鍵）。`jwk` は P-256 の
   公開鍵（`kty`・`crv`・`x`・`y`）で、秘密の値（`d`）を含むものは断る。中身は `jti`・`htm`・`htu`・`iat`、
   リソースの口ではさらに `ath`（アクセストークンの SHA-256 の base64url）。指紋は RFC 7638（`{"crv","kty","x","y"}`
   の SHA-256 の base64url）。
3. **nonce（`DPoP-Nonce`）は使わない。** nonce は「先に作っておいた証明を後で使う」ことを防ぐためのものだが、
   鍵は Keystore から取り出せないので、先に作るにはその端末の中で動いている必要がある。その場合は端末の中から
   いつでも新しい証明を作れるので、nonce を足しても守りは増えない。一方、nonce は往復を 1 回増やし、
   アプリと各サーバーに「nonce を受け取って作り直す」流れを持たせる。代わりに 4〜6 で受ける幅を狭くする。
4. **`jti` は鍵ごとに 1 回だけ。** 受けた証明の `sha256(jkt ":" jti)` を `dpop_proof_jtis` に、受ける幅（6）が
   過ぎるまで記録し、同じものが来たら断る（一意キーへの INSERT で判定するので、同時に 2 本来ても片方だけが通る）。
   期限の過ぎた行は期限切れの記録の掃除（`expired_record_purge`）が消す。
5. **`htu` は assay が discovery で名乗る URL と比べる**（`{issuer}/token`・`{issuer}/userinfo`）。要求の `Host`
   ヘッダーからは組み立てない（前段の proxy で変わる）。比べる前に、両方から問い合わせ（`?…`）と断片（`#…`）を外し、
   スキームとホストは小文字にそろえる。`htm` は大文字の HTTP メソッドと完全一致。
6. **時計のずれは、`iat` が「今より 120 秒前」から「今より 60 秒後」までを受ける。** スマホの時計は自動で合わせて
   あれば数秒以内。ずれている端末のために、アプリはトークンの口・各サーバーの応答の `Date` ヘッダーとの差を覚えて
   `iat` を直し、`invalid_dpop_proof` を受けたら 1 回だけ作り直す（flutterbase）。値は設定にしない（定常の運用で
   変えるものではない）。
7. **結び付けたリフレッシュトークンは、同じ鍵の証明でしか使えない。**
   - 結び付けあり・証明なし（または証明が壊れている）→ `invalid_dpop_proof`（400）。何も失効させない。
   - 結び付けあり・別の鍵の証明 → `invalid_grant`。何も失効させない。
   - ⚠ **この確かめは使い回しの検出より先に行う。** 鍵を持たない者が盗んだリフレッシュトークンを出しても、
     持ち主のアプリのログインは止まらない（止められるのは鍵を持つ者だけ）。
   - 結び付けなし・証明あり → 新しいトークンからその鍵に結び付ける（DPoP を入れた版へ更新したアプリが、
     ログインし直さずに移れるように）。
   - **使い回しの検出（同じ家族の一括失効）はそのまま残す。** 鍵を持つ者どうしの競り合い（同じ端末の二重の更新など）は
     今までどおり家族ごと止める。
8. **`/userinfo` は、`cnf.jkt` のあるトークンを `Authorization: DPoP <token>` と、`ath` の合う証明でしか受けない。**
   `Bearer` で来たら 401（`WWW-Authenticate: DPoP error="invalid_token"`）。逆に `cnf` の無いトークンを `DPoP` で
   出されたら 401。`/introspect` は `cnf` をそのまま返す（RFC 9449 §6.2）。`/revoke` は証明を求めない。
9. **discovery に `dpop_signing_alg_values_supported: ["ES256"]` を載せる。**
10. **アプリのトークンを受けるサーバー（RP）は、`cnf.jkt` のあるトークンで証明を確かめる**（docs/RP_INTEGRATION.md）。
    そのトークンでは assay の `/userinfo` を引けない（サーバーは鍵を持たない）ので、利用者のプロフィールが要る
    ときは、アプリが渡す ID トークン（`aud` がアプリの `client_id`）の署名を確かめて読む。

## 結果

- アプリのアクセストークン・リフレッシュトークンだけを別の端末へ写しても、assay の `/token`・`/userinfo` と、
  証明を確かめるサーバーでは使えない。
- 証明 1 つにつき DB の INSERT が 1 回増える（トークンの口・`/userinfo`）。アプリのトークンの口は 300 秒に 1 回程度。
- 防げないこと: 端末そのものを乗っ取られた場合（端末の中から鍵で署名できる）。Keystore が無い・壊れた端末では
  アプリが DPoP を使わず、今までどおり Bearer になる（アプリ側で決める。flutterbase の ADR）。

## 採らなかった案

- **nonce を使う**: 3 のとおり。将来、鍵を取り出せる端末（Keystore の無い環境）を受けるなら考え直す。
- **`jti` を覚えない（`iat` の幅だけ）**: 幅の中なら同じ証明を何度でも使える。ログや中継で証明が漏れたときの
  使い道を残さない。
- **使い回しの検出をやめる**: 設計書 第 1 版 3.5 のとおり残す（外すほうが手間で、鍵を持つ者どうしの競り合いには
  まだ効く）。
- **`/userinfo` で結び付けたトークンを Bearer でも受ける**: アクセストークンを盗んだ者が 300 秒の間プロフィールを
  読める。AC1（assay でも使えない）を満たさない。
