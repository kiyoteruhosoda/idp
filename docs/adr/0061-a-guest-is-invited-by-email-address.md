# ADR-0061: ゲストはメールアドレスで招く

- Status: Accepted
- Date: 2026-09-21
- 関連: `docs/adr/0009-multi-tenant-architecture.md` §3（招待とメンバーシップ）、
  `docs/adr/0025-login-identifier-registry.md`（ログイン識別子の登録簿。1 本の欄で読み分ける）、
  `docs/adr/0032-client-usage-drives-the-registration-form.md`（1 つの決定を 2 つの入力に分けない・
  制約だけを告げて逃げ道を書かない検証）、`docs/adr/0029-tenant-domains-and-home-realm-discovery.md`（ドメインからテナントを決める）

## 背景

ゲスト招待の画面（`/{tenant_id}/admin/invitations`）は、招く相手を**内部 ID（UUID）でしか
指せなかった**。

```
ゲストを招待
他テナント所属の既存利用者の内部 ID（UUID）を入力してください。
利用者 ID（UUID） *
```

⚠ **この画面は、assay のどこにも出てこない値を要求している。** 招く相手は所属元が他テナントの
利用者で、参加先テナントの管理者は**相手のテナントの名簿を見られない**（ADR-0009 §3。ゲストの
`users` レコードを触れるのは所属元の管理者と本人だけ）。つまり UUID の出どころは assay の外
——相手に「自分の内部 ID を調べて送って」と頼むしかない。

システムの他の場所で人を指すときの語彙とも揃っていない。

| 画面・経路 | 人の指し方 | 出どころ |
|---|---|---|
| ログイン | ユーザー名・メール・電話番号（登録簿。ADR-0025） | 本人が知っている |
| アプリの割り当て | 利用者 ID | **自テナントの名簿で引ける**（画面に案内がある） |
| パスワード再設定 | メールアドレス | 本人が知っている |
| **ゲスト招待** | **内部 ID（UUID）だけ** | **どこにも無い** |

招く側が確実に知っているのは、相手の**メールアドレス**である（招待メールの宛先も同じ値で、
すでに `users.email` から取っている）。

## 決定

### 1. 欄は 1 本のまま、メールアドレスと内部 ID の**どちらでも**受ける

```
招待する相手（メールアドレス） *
相手のメールアドレスを入力します。内部 ID（UUID）でも指定できます。
```

読み分けは application 層（`InvitationService::resolve_invitee`）に閉じる。UUID として読めれば
内部 ID、そうでなければメールアドレスとして検証してから引く。

**欄を 2 つに割らない。** 「メールで指す」「ID で指す」は同じ 1 つの決定であって、`email` と
`user_id` の 2 入力にすると「両方書いたらどちらが勝つのか」という**表せない状態**が生まれる
（ADR-0032）。ログイン欄が 1 本で複数種類の識別子を読み分けているのと同じ形にする（ADR-0025 ——
識別子が増えるのは「入力の読み方が増える」ことであって「利用者の引き方が増える」ことではない）。

API（`POST /{tenant_id}/admin/invitations`）の項目名は `invitee` にし、旧名 `user_id` も
受け続ける（`serde(alias)`）。内部 ID しか受け付けなかった頃の名前なので、値の意味が広がった
いまは名前のほうを直す。

### 2. メールで引くのは**テナントを跨いでちょうど 1 人**のときだけ

⚠ **`users.email` の一意性はテナントの中にしか無い**（`users_tenant_email_uk (tenant_id, email)`）。
同じアドレスの利用者が 2 つのテナントに居るとき、どちらを招くかは決められない。**誰も返さない。**

これはパスワード再設定（MT26 の `find_active_guest_by_email`）と同じ判断である。曖昧なまま片方を
選ぶと、**索引の都合で招待先が決まる**ことになり、招いた側にも招かれた側にも説明できない。

数えるのは **ACTIVE な利用者 × 所属元テナントが ACTIVE** だけ。招いても入れない相手は候補では
なく、数えると「同じアドレスの止まった利用者が 1 人居るだけで、唯一の招ける相手を招けなくなる」。

### 3. 曖昧だったことを**応答で言い分けない**

0 人でも複数人でも同じ「見つかりません」を返す。言い分けると、参加先の管理者に
**「このアドレスの利用者が他のテナントにも居る」ことだけが分かる** ——相手のテナントの名簿を
見せない設計（ADR-0009 §3）に、応答の差で穴を開けることになる。

ただし**逃げ道は書く**（ADR-0032）。画面の説明に「内部 ID（UUID）でも指定できます」と常に出し、
見つからなかったときのエラーにも同じ案内を添える。制約だけを告げて回避策を書かない検証は、
利用者を手順書探しへ追いやる。

## 影響

- **招待にメールアドレスが使えるようになった。** 相手に内部 ID を聞く手順が消える。
- **内部 ID での招待は従来どおり通る。** 旧項目名 `user_id` の呼び出しもそのまま動く。
- ⚠ **メールアドレスの存在が、招待の成否から分かる。** これは新しく増えた面である ——
  これまでは UUID を知っていること自体が「相手を知っている」ことの証明になっていた。
  招待は `idp.tenant.admin`（`MembersWrite`）を持つ管理者しか押せず、作成は監査ログ
  （`TenantInvitationCreated`）に残る。テナント管理者に対してこれ以上絞る価値は無いと判断した。
- ⚠ **`users` の索引（`(tenant_id, email)`）には乗らない引き方である**（先頭列がテナント）。
  招待は人が押す稀な操作で `users` の行数も小さいため、email 単独の索引は足していない。
  行数が増えて目に見えて遅くなったら足す。

## 却下した案

- **テナントを選ばせてから、そのテナントの名簿で選ばせる。** 参加先の管理者は他テナントの名簿を
  見られない（ADR-0009 §3）。選択肢を出した時点でそれを配ってしまう。
- **メールのドメインからテナントを決める（ADR-0029 のドメイン割り当てを使う）。** ドメインを
  登録していないテナントには効かず、効くときは横断で引いても答えは同じである。経路が 2 つに
  割れるだけで、決まる相手は変わらない。
- **複数人に当たったことを「曖昧です」と伝える。** 決定 3 のとおり、存在だけが漏れる。
- **`sub`（グローバル一意）も受け付ける。** UUID の種類が 2 つになり、「どちらの UUID か」を
  利用者が意識することになる。指せる値を増やしても、どこにも出てこない値であることは変わらない。
