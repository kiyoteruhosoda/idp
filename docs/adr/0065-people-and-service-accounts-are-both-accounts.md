# ADR-0065: 人とサービスアカウントを「アカウント」として同じ段に並べる

- Status: Accepted
- Date: 2026-09-25
- 改めるもの: ADR-0038 の決定 3 のうち「メンバーは動かさない」（一覧の置き場所。語の意味は変えない）
- 関連: `docs/adr/0038-registration-splits-into-accounts-and-relying-parties.md`（アカウントと連携先）、
  `docs/adr/0059-an-application-has-identities-and-principals.md`（使う主体は人とサービスアカウント）、
  `docs/adr/0063-member-notes-and-applications-on-the-member-page.md`（管理者メモと使えるアプリ）

## 背景

ADR-0038 は、登録を「アカウント（assay へ名乗る主体）」と「連携先」に分け、アカウントの中を
**種別**（人／サービスアカウント）で切り替えると決めた。ADR-0059 は、アプリを使う主体として
人とサービスアカウントを**同じ段に並べた**（`application_assignments.kind`）。

ところが管理コンソールでは、人とサービスアカウントは**別の場所に、別の作りで**置かれたままだった。
ADR-0063 で人の側に足したものが、サービスアカウントの側には 1 つも無い。

| | 人（メンバー） | サービスアカウント |
|---|---|---|
| 一覧の置き場所 | メンバー | 別メニュー（連携先の一覧を流用） |
| 一覧の列 | 誰か・状態・メモ | 名前・`client_id`・種別・状態・scope |
| 絞り込み | 名前・メール・メモ | 無い |
| 管理者メモ | ある | **無い** |
| 使えるアプリ | 人の画面から見て、出し入れできる | **アプリを 1 つずつ開いて探すしかない** |
| 作成時のメモ | 書ける | **無い** |
| 1 件の画面 | 基本・メモ・アプリ・直す・危険の枠 | 連携先と共用の定義リスト |

種別が違うだけなのに、同じ問い（「これは何者で、どこを使えるか」）への答え方が食い違っている。
しかも食い違いは**直すたびに広がる**。ADR-0063 のように人の側に何かを足すと、サービスアカウントの
側は置いていかれる。

原因は、メモが**利用者の表**（`tenant_member_notes.user_id`）に、使えるアプリの口が
**メンバーの経路**（`/admin/members/{user_id}/applications`）に、それぞれ人の形で作られたことにある。
割り当て（ADR-0059）だけが既に「種別＋主体」の形を持っていた。

## 決定

### 1. 「アカウント」は人とサービスアカウントの総称。一覧は 1 つにする

管理コンソールの一覧は「アカウント」1 つにし、種別（すべて／人／サービスアカウント）で絞る。

- ⚠ **「メンバー」の意味は変えない。** メンバーは今までどおり人のテナント参加（HOME / GUEST）を指す
  （ADR-0038 の決定 3 の理由 ——「ゲスト招待できないメンバー」を作らない ——はそのまま残る）。
  変えるのは**一覧の置き場所**で、HOME / GUEST は人の行の属性として出す
- 一覧の列は ADR-0063 の「誰か・状態・メモ」のまま。サービスアカウントの見出しは登録名、
  副題は `client_id`
- 状態の札は種別をまたいで同じ規則（普通でないものだけ）: 人は ゲスト・停止中・招待中・無効・ロック中・
  仮登録、サービスアカウントは 無効
- 絞り込みの言葉は、人はメール・氏名・ユーザー名・メモ、サービスアカウントは登録名・`client_id`・メモを見る
- 並びは見出しの昇順で、種別をまたいで混ぜる（種別で分けたいときは絞り込む）
- 旧 URL（`/admin/members`・`/admin/service-accounts`）は種別を絞った一覧へ転送する。1 件の画面の
  URL は種別ごとのまま（`/admin/members/{user_id}` と `/admin/service-accounts/{client_id}`）

#### 読める種別だけを並べる

管理 API は `GET /{tenant_id}/admin/accounts?kind=&q=&limit=&offset=`。
人を読む権限（`idp.members:read`）とサービスアカウントを読む権限（`idp.clients:read`）は別なので、
**呼んだ主体が読める種別だけを並べる**。

- `kind` 未指定: 読める種別をすべて並べる。1 つも読めなければ 403
- `kind` 指定: その種別を読めなければ 403（黙って空にしない ——空の一覧は「居ない」と読まれる）
- 応答に「並べた種別」を載せる。画面は読めない種別の絞り込みを出さない
- ⚠ 新しい権限コードは作らない。「アカウントを読む」権限を作ると、既存の 2 つとの含意を
  もう 1 本増やすことになる

### 2. 管理者メモは主体に付く（`account_notes`）

`tenant_member_notes` を `account_notes` に置き換える。移行 `0063` は expand だけで、新しい表を作って
既存のメモを写す。旧表を落とすのは本番に入った後の移行 `0064`（contract）。形は `application_assignments`
（ADR-0059 の決定 5）と同じで、`kind`（`USER` / `SERVICE_ACCOUNT`）と、`user_id` / `client_id` の
どちらか 1 つだけが埋まる。

- 人のメモは今までどおり**メンバーシップ**（テナント × 利用者）に付く。外部キーも同じ
  （メンバーシップが消えればメモも消える）
- サービスアカウントのメモは `clients.id` に付く。サービスアカウントは 1 テナントにしか属さないので、
  メンバーシップに当たる段は無い
- ⚠ **論理削除（ADR-0035）したサービスアカウントのメモは残る**（行は消えないので）。一覧にも
  1 件の画面にも出ない
- 上限（2000 文字）・正規化・監査に中身を載せないこと（ADR-0063 の決定 1）は種別を問わず同じ。
  監査の event_type は `account.note_updated` に改め、`reason` に種別と相手（`user=…` /
  `service_account=…`）を書く
- 既存のメモは移行でそのまま写す

口は種別ごとに分ける（`PUT /admin/members/{user_id}/note` はそのまま、
`PUT /admin/service-accounts/{client_id}/note` を足す）。書く権限が種別で違う
（`idp.members:write` / `idp.clients:write`）ためで、規則（上限・正規化・監査）は 1 つのサービスにしか無い。

作成時にも書ける（`POST /admin/clients` の `note`）。⚠ **サービスアカウントでない client
（連携先）にはメモを書かせない**（400）。メモはアカウントの経緯であって、連携先の設定ではない。

### 3. 使えるアプリは種別ごとの判定と同じ規則で答える

`GET /{tenant_id}/admin/service-accounts/{client_id}/applications`（`idp.applications:read`）。
人の口（ADR-0063 の決定 2）と同じ形の応答を返す。

- 載せるのは**宛名（`resource`）の名乗りを持つアプリだけ**。サービスアカウントが「使う」とは、
  そのアプリの API 宛のトークンを取ることである（ADR-0059 の決定 5）。人の口がログインの名乗りを
  持つアプリだけを載せるのと対になる
- 可否はトークン発行（`client_credentials` + `resource`）と同じ規則で決める。規則は
  `Application::admits_service_account` の 1 か所に置き、トークン発行もこれを呼ぶ
- ⚠ **「全員（`EVERYONE`）」のアプリでもサービスアカウントは含まれない**（ADR-0059 の決定 5 の 1）。
  したがって出し入れの口はモードを問わず出す（人の画面が「全員」のアプリで口を出さないのと違う）
- 1 件の画面には、使えるアプリとは別に「**どのアプリの名乗りか**」（binding）を出す。名乗りと
  使う主体を取り違えると管理トークンが出ない（ADR-0059）ので、2 つを同じ欄に混ぜない

### 4. 1 件の画面は同じ骨組みにする

人の画面（ADR-0063）の枠をそのまま使う: **基本 → メモ → 使えるアプリ → 見る → 直す → 危険**。
種別で違うのは枠の中身だけである。

| 枠 | 人 | サービスアカウント |
|---|---|---|
| 基本 | ユーザー名・氏名・種別・状態 | `client_id`・状態・認証方式・名乗りのアプリ・作成日 |
| 見る | 権限・ログイン識別子 | 管理権限（その場で付与・剥奪） |
| 直す | 無効化・ロック解除・パスワード・MFA・トークン | 編集・シークレット再発行 |
| 危険 | 削除 | 削除（論理削除） |

サービスアカウントの 1 件の画面は `/admin/service-accounts/{client_id}` に置き、`/admin/clients/{client_id}`
でサービスアカウントを開いたときはそこへ転送する。連携先の画面は今までどおり。

## 捨てた案

### A. 画面だけ揃える（サービスアカウント用のメモ表を別に足す）

データはそのままで、サービスアカウントにメモの別表と使えるアプリの口を足す。最短だが、
**機能ごとに 2 本の実装が並ぶ**。ADR-0063 と同じことが次に起きたとき、また片方だけに足される。
割り当て（ADR-0059 の捨てた案 C）と同じ理由で捨てた。

### B. サービスアカウントを `users` の 1 種別にする

表まで 1 つにすれば食い違いようがない。捨てたのは、**識別子・資格情報・権限の表・止め方が
実際に違う**からである（ADR-0038 の決定 2）。サービスアカウントは `client_id` と鍵（シークレット・
`private_key_jwt`）で名乗り、トークン発行・introspection・管理トークンの経路はすべて `clients` を
見ている。表を移すと、揃えたいもの（メモ・アプリ）の何倍もの経路を書き換えることになる。
揃えるべきは「アカウントについての事実」の置き方であって、名乗り方ではない。

### C. 「メンバー」にサービスアカウントを入れる

ADR-0038 の決定 3 が捨てたとおり、「ゲスト招待できないメンバー」ができる。語を広げるのではなく、
総称（アカウント）を上に置く。

### D. 「アカウントを読む」権限を新設する

一覧 1 本に権限 1 つで済むが、既存の `idp.members:read` / `idp.clients:read` との関係
（どちらを含意するのか）を決め直すことになる。読める種別だけを並べれば、今ある権限のまま済む。

## 帰結

- 「これは何者で、どこを使えるか」が種別を問わず 1 画面で分かる
- メモを持つ場所は 1 つになり、次に「アカウントについての事実」を足すときも種別で分かれない
- ⚠ 監査の event_type が `tenant_membership.note_updated` から `account.note_updated` に変わる。
  前者で数えていた問い合わせは両方を見ること（前者は 2026-09-24〜25 の間だけ出ていた）
- ⚠ 移行 `0063` の down はサービスアカウントのメモを捨てる（戻す先の表に置き場が無い）
