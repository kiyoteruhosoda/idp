### 詳細

**T39 — 認証の強度を予約語 2 つで名乗る**

方式は ADR-0043。`acr_values` は認証ポリシーの `requested_acr` 条件として**本当に強制して
いる**（SSO 復元時も `authorize.rs` が評価し直す）のに、満たしたことを RP へ返していない。
そのため、ポリシー行に入力した文字列と RP が送る文字列が 1 文字ずれると条件が外れ、既定効果
（`allow`）へ落ちて**単要素のログインが黙って通る**。RP には検出手段が無い。

やること:

- 予約語 `urn:assay:ac:mfa` / `urn:assay:ac:single` を組み込みで解釈する（ポリシーの有無に
  関わらず MFA を要求する）。実効要件は RP の要求とテナントのポリシーの強いほう。
- `AuthorizationCode` に列を 1 つ足す（`sid` と同じ `Option<String>` の形）。トークン発行時に
  認証の文脈が残っていないため。マイグレーション 1 本。
- `IdTokenClaims` に `acr` / `amr`。`amr` は `AuthenticationMethod::amr()`（定義済み・未使用）を
  繋ぐだけ。**強度の判断には使わせない**旨をコメントと `docs/OIDC_INPUT.md` へ明記する。
- discovery の `acr_values_supported` と `claims_supported` を埋める。テナント独自の文字列は
  載せない（保証できる値だけを公開する）。
- `prompt=none` で MFA を満たせないときは `interaction_required`（`max_age` 超過と同じ扱い）。

**RP 側が確認して初めて検出になる。** fastapitemplate に「要求した `acr` が返ってきたか
確かめる」を入れる話（あちらの ADR-0026）とセットで進める。

**T38 — 利用者を認証した grant にも `resource` を効かせるか**

ADR-0042 は宛名の登録を入れたが、`resource` を解釈するのは `client_credentials` だけのままに
してある（`authorization_code` に付けると `invalid_target`）。人の代理で他アプリの API を叩く
第三者クライアントが現れたときに要る話で、**そのときは scope（何を代理させてよいか）の議論と
セットになる**——宛先だけを人のトークンに載せても、リソースサーバは「その人が何をしてよいか」を
自分で決めるしかなく、いまと変わらない。現状そういう呼び出し元が居ないので開けていない。

**T34 — 表示設定が GET で利用者設定を書き換える**

`?lang=` / `?theme=` は `display_preferences` middleware が解釈し、**ログイン中なら
`users.language` / `users.theme` へそのまま永続化する**。GET で、CSRF トークンは無い。
SSO Cookie は `SameSite=Lax` なのでトップレベル遷移には載る —— つまり、署名済み利用者が
外部のリンクを踏むと表示言語や配色が変わりうる。

**実害は見た目だけである。** 資格情報も権限も動かず、利用者が設定画面で戻せる。それでも
「他人のリンクで利用者の保存済み設定が変わる」形自体は残しておく話ではないので、判断を残す。

直すなら **`?lang=` と `?theme=` の両方**である（`?theme=` は `?lang=` の形に合わせて作った
ので、片方だけ POST にすると設定画面に 2 つの流儀が並ぶ）。触るところ:

- 一時切替（Cookie だけ）と永続化（DB）を分け、**永続化のみ POST + CSRF トークン**にする
- 管理コンソールのヘッダにある言語ドロップダウンは全画面から送られる GET フォームなので、
  そこを POST にするなら CSRF トークンを共通レイアウトへ通す必要がある
- あるいは「GET は Cookie まで、DB へ書くのは設定画面の POST だけ」に線を引く（この場合、
  別端末で言語を変えても他端末に追随しない従来の挙動へ一部戻る）

**T35 — 設定画面のプロフィール二重取得**

`GET /{tenant_id}/settings` は 1 リクエストで `/internal/account/profile` を 2 回呼ぶ。
`display_preferences` middleware が言語・配色のために 1 回、`user_settings::page` が表示名・
ログイン識別子のために 1 回で、**配色に至っては同じ応答の同じフィールドを二度読んでいる**。

middleware が取得済みの応答をリクエスト拡張へ載せ、ハンドラがそれを読めば 1 回で済む。
ただしハンドラは `name` / `preferred_username` も要るので、middleware が持つ
`StoredPreferences`（いまは言語と配色だけ）を広げることになる。**表示設定の決定に要らない値を
決定用の型へ入れるかどうか**が判断点で、素直にやるなら「プロフィール応答そのもの」を載せて
`StoredPreferences` は middleware 内部の派生に留める。

**T36 — permissions マスタの全件読みをキャッシュする**

`whoami`（`handlers::admin::effective_permissions`）は含意の展開先として `permissions` マスタを
全件読む。**管理コンソールの画面描画ごとに 1 回**走り、`CachedUserPermissionRepository::
list_available_codes` は素通しで何もキャッシュしていない。

マスタはマイグレーションでしか変わらないので、TTL も invalidation も要らない（プロセス寿命で
持ってよい）。直す場所はキャッシュデコレータ側で、`whoami` は触らない。

**T37 — MFA 設定画面に戻る導線**

`mfa_totp_setup.html` には `<a>` が 1 つも無く、設定を終えても中断しても戻る先が画面に無い。
パスキーの 2 画面には左上の名乗りをホームへのリンクにする形（`page.html` の `brand` ブロック）を
入れたので、同じ形をあてる。

**T31 — 検証鍵を JWKS URI 以外でも登録できるようにするか**

いまの OIDC 外部 IdP は `jwks_uri`（URL）しか持てない。SAML 側は証明書を貼り付けられるので、
「OIDC も鍵そのものを貼りたい」という要望が出る。**既定は URL のままにする。** 相手が鍵を
入れ替えたとき、URL なら追随できるが、貼り付けた鍵は**入れ替えの瞬間にログインが止まる**
（SAML で証明書を配列にしたのと同じ問題が、こちらでは自動で解けている）。

足す価値があるのは、`jwks_uri` に**到達できない**相手だけである（閉域の IdP・JWKS を公開せず
鍵を手渡しする運用）。実際にそういう相手があるなら足す。判断してから着手する。

足す場合に触るところ:

- `external_identity_providers` に静的 JWKS の列を追加（`jwks_uri` と排他。どちらか一方）
- `domain::external_idp::OidcProviderConfig` を「URL か 鍵集合か」の enum に変える
- `infrastructure::external_oidc` の `fetch_jwks` を分岐させる
- 管理画面は SAML の証明書欄と同じ形（貼り付け）にする

**T32 — discovery からの取り込み**

SAML には IdP メタデータ XML の取り込みがあるが、OIDC には相当するものが無く手動入力だけに
なっている。`{issuer}/.well-known/openid-configuration` を読めば `authorization_endpoint` /
`token_endpoint` / `jwks_uri` が埋まる。**取り込みは登録ではない**（管理者が値を確認してから
登録する）という SAML 側の扱いをそのまま踏襲する。

api 側が外部へ HTTP を出す点が SAML の取り込み（XML を受け取るだけ）と違う。到達先は管理者が
入力した issuer なので、**リダイレクトを追わない**・タイムアウトを持つ等、`external_oidc` の
既存の作法に揃える。

## 優先度の算出

| 項目 | 小 (1) | 中 (3) | 大 (5) |
|---|---:|---:|---:|
| 影響度（修正範囲） | 単一機能・単一プロンプト | 複数機能 | システム全体・広範囲 |
| 重要度（セキュリティリスク） | なし | 社内情報への影響 | 個人情報・機密情報への影響 |
| 難易度 | 簡単 | 標準 | 難しい |

| 工数 | 補正値 |
|---|---:|
| 小 | 1 |
| 中 | 2 |
| 大 | 3 |

`優先度スコア = (影響度 × 重要度 × 難易度) ÷ 工数補正値`。同点はセキュリティリスク、
前提タスク、障害復旧性の順で先にする。

## 推奨モデルの基準

各タスクの **難易度（工数）× リスク（影響度）** で Claude モデルを割り当てる。リスクは
「テナント分離・認可境界・トークン検証・自動生成シークレット・データ基盤の整合」を重く見る。

| モデル | 割り当て基準 |
|---|---|
| **Opus 4.8** | 高リスク（セキュリティ境界・分離防御線・保証の要）または高難度（広範囲波及・設計判断を伴う） |
| **Sonnet 5** | 仕様が明確な機能実装・中程度の面。標準的な難度で判断も限定的 |
| **Haiku 4.5** | 定型・低リスク（確立パターンの反復、限定的な UI・文言・設定） |
