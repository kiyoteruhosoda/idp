### 詳細

1. **MT25: テナントにドメインを紐づけ、ゲストの所属元を識別子から決める（home realm discovery）**

   ログイン欄は 1 つで複数種別（ユーザー名／メール／電話番号／社員番号）を受ける（AP8）。
   曖昧な入力を「不在」と区別して拒む処置と、一意性を種別非依存にする処置（migration 0041）は
   入れた（CHANGELOG 2026-08-23（2））。**残っているのは、一意性の範囲と解決の範囲がずれている
   ことそのものである。**

   一意性はテナント内でしか担保していないのに、参加先テナントのログイン画面が解決する範囲は
   「そのテナントの HOME 利用者 ∪ 参加中のゲスト（各自の所属元の登録簿）」で、**所属元をまたぐ**。
   そのため同じユーザー名のゲストが 2 人参加した時点で、その 2 人とも参加先の画面から入れなくなる
   （なりすましではなく締め出し。所属元テナントの画面からは従来どおり入れる）。ゲストが増えるほど
   当たりやすい。

   **一意性を全体（クロステナント）へ広げるのは採らない。** ADR-0009 §1 のテナント独立が壊れ、
   あるテナントが `admin` を取ると全テナントで使えなくなる。Entra ID もそれはしておらず、UPN が
   グローバル一意なのは**ドメイン接尾辞を 1 テナントが所有している**ためで、ローカル部の取り合いは
   起きない。同じ形にする:

   - `tenant_domains`（`domain` はグローバル一意）でテナントにドメインを紐づける。まずは root
     管理者が排他的に割り当てるだけでよく、所有の検証（DNS TXT）は後続で足せる。
   - 参加先テナントの画面では、**ドメイン修飾された識別子**（メール／UPN）はドメインから所属元
     テナントを 1 つに決め、そのテナントの登録簿だけを引く。ゲスト横断の走査自体が要らなくなる。
   - 裸のユーザー名・未所有ドメイン（gmail 等）は従来どおり参加中のゲストを走査し、曖昧なら拒む。
     つまり本変更は**加算的**で、既存の識別子を壊さない。

   「1 アイデンティティに複数のメールアドレス」は新たに必要にならない —— `user_login_identifiers`
   は `email` 種別の行を 1 人が複数持てる（`users.email` は連絡先であって別概念）。ドメイン紐づけが
   足すのは「そのアドレスがどのテナントを指すか」だけである。

   規模が ADR 1 本ぶんあるため、着手前に ADR を起こす。

2. **MT26: ゲストのパスワード再設定を所属元テナントへ橋渡しする**

   ゲストは参加先テナントのログイン画面から入れるようになったが、同じ画面の「パスワードをお忘れ
   ですか？」は所属元テナント限定のまま（`find_by_email(要求テナント)`）で、ゲストが使っても
   メールは飛ばない。当面は再設定画面に案内文を出して行き止まりを避けている（2026-08-23）。

   本対応は「参加先の `/forgot-password` でもゲストを解決し、トークンは**所属元テナント scope**の
   まま発行して、メールのリンクは**所属元テナントの再設定 URL** を指す」形にする。`consume()` の
   テナントガードは変更不要（リンクが所属元を指すので自然に通る）。応答は常に `Accepted` のままで
   列挙も生じない。SMTP はシステム設定（テナント別ではない）なので、参加先が他テナントの利用者宛に
   メールを出す懸念も生じない。

   Entra ID も同じ考え方で、リソーステナントでは SSPR させず所属元へ寄せる（サインイン画面ごと
   所属元へリダイレクトするため、利用者から見ると行き止まりにならない）。

3. **MT28: 不存在・無効テナントの内部 API 拒否を、web の 404 画面へ写像する**

   `require_internal_tenant` が不存在・`DISABLED` を 400 で拒否するようになった（2026-08-23）が、
   web の `post_internal` は非 2xx を「web の実装/構成エラー」として `anyhow` で落とすため、
   `/{tenant_id}/login` の送信が素の 502 になる（エラー画面ですらない）。テナント経路の他の応答と
   揃えて 404 の画面に倒す。whoami が 404 を `AdminSession::NotFound` へ写像しているのと同じ扱いに
   する（`api_client` に「テナントを解決できなかった」を表す戻り値を足し、ログイン系ハンドラで
   `not_found` へ倒す）。

## 優先度の算出

| 項目 | 小 (1) | 中 (3) | 大 (5) |
|---|---:|---:|---:|
| 影響度（修正範囲） | 単一機能・単一プロンプト | 複数機能 | システム全体・広範囲 |
| 重要度（セキュリティリスク） | なし | 社内情報への影響 | 個人情報・機密情報への影響 |
| 難易度 | 簡単 | 標準 | 難しい |

| 工数 | 補正値 |
|---|---:|
| 小 | 1 |
| 中 | 2 |
| 大 | 3 |

`優先度スコア = (影響度 × 重要度 × 難易度) ÷ 工数補正値`。同点はセキュリティリスク、
前提タスク、障害復旧性の順で先にする。

## 推奨モデルの基準

各タスクの **難易度（工数）× リスク（影響度）** で Claude モデルを割り当てる。リスクは
「テナント分離・認可境界・トークン検証・自動生成シークレット・データ基盤の整合」を重く見る。

| モデル | 割り当て基準 |
|---|---|
| **Opus 4.8** | 高リスク（セキュリティ境界・分離防御線・保証の要）または高難度（広範囲波及・設計判断を伴う） |
| **Sonnet 5** | 仕様が明確な機能実装・中程度の面。標準的な難度で判断も限定的 |
| **Haiku 4.5** | 定型・低リスク（確立パターンの反復、限定的な UI・文言・設定） |
